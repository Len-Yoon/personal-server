## 3. 상세 내용

### 3.1 원복 대상별 경계

| 구분 | 적용 대상·기존 도구 | 바뀌는 상태 | 필수 선행 확인 | 종료 기준·중단 기준 | 비고 |
|---|---|---|---|---|---|
| K3s 앱 이미지 원복 | [k3s-app-upgrade.sh](../infra/k8s/tools/k3s-app-upgrade.sh)의 `patch_image`, `rollout_and_health` | Deployment 컨테이너 이미지 필드 | 이전/현재 canonical digest, AMD64 반입 이미지, 현재 이미지 일치, Ready·Service·Endpoint, DB 호환성 | 정상 rollout·health 확인. 대상 교체 후 실패하면 직전 digest로 1회 원복 시도하며 실패/불확실 시 재실행 보류 | 지원 대상은 `portal-web`, `crawler-worker`, `book-memo`임. YouTube까지 지원한다고 확대하지 않음 |
| DB 추가형 변경 뒤 이미지 원복 | [운영 기준의 추가형 DB 변경 절](operations-reference.md#추가형-db-변경compose-이미지-교체-시-확인-기준) | 앱 코드만 원복 | SQLite online backup·quick_check, 기존 컬럼 행 수/내용 해시, 이전 이미지 | 이전 코드로 기존 데이터를 읽고 서비스 검증을 통과함. 새 컬럼/테이블 삭제나 DB 덮어쓰기는 포함하지 않음 | 호환성 미검증이면 이미지 원복 가능 상태로 단정하지 않음 |
| K3s→Compose writer 원복 | [Book cutover](../infra/k8s/tools/book-memo-cutover.sh)의 `--rollback` 및 [운영 기준](operations-reference.md#book-memo-k3s-전환-승인검증) | writer 소유권·실행 주체 | 유지보수 조건, K3s writer 종료, 양쪽 데이터 digest·SQLite 검사, runtime marker·자동복구 제외 | 데이터 동등성이 확인된 경우만 Compose 복귀함. 다르면 K3s 복구 또는 `recovery_required` 판단으로 중단 | 역방향 데이터 복사는 별도 범위임 |
| 격리 데이터 복원 검증 | [Portal check_restore](../infra/k8s/tools/portal-backup-restore-check.py), 서비스별 `restore_snapshot` | scratch 데이터만 생성·검사·제거 | 유효 원본 증적, 암호문·평문 digest, 복호화 권한, 안전한 작업 공간 | archive 구조·대상 데이터 digest·SQLite/JSON 검사 성공, 임시 평문 제거 | 실제 운영 데이터 교체 아님 |
| 실제 서비스 데이터 복원 | 서비스별로 대상·복원점·쓰기 중단·적용/실패 복구 절차를 구체화해야 함 | 운영 DB/PVC 내용 및 복구 시점 | 별도 운영 승인, 단일 writer, 현 데이터 보존, 검증된 격리 복원, 호환 이미지·설정 | 데이터 정합성·업무 검증·Ready·외부 health·잠금 해제까지 확인 | 본 문서와 격리 복원 도구는 운영 PVC 덮어쓰기 실행 절차를 제공하지 않음. 확인 필요 |

`k3s-app-upgrade.sh`는 `--expected-current-image` 재조회 후 조건부 patch를 수행함. `rollback=PASS`가 출력되어도 목표 배포 자체는 실패 종료함. 이를 새 버전 배포 성공으로 집계하지 않음. 자동 원복의 코드상 1회 제한과 [AGENTS.md](../AGENTS.md)의 동일 원인 수정·재검증 최대 3회 기준은 서로 다른 제한임.

### 3.2 이미지·설정·권한·키·백업 의존성

| 점검 대상 | 원본에서 확인한 의존성 | 확보/대조할 증거 | 비고 |
|---|---|---|---|
| 실행 이미지 | [build](../infra/k8s/tools/k3s-app-image-build.sh) → [import](../infra/k8s/tools/k3s-app-image-import.sh) → upgrade 경로, Linux AMD64·OCI archive SHA-256·canonical digest | 정상/원복 이미지 소스 커밋, archive 체크섬, containerd에 실제 반입된 참조와 실행 이미지 일치 | Git에 Dockerfile만 있다고 장애 시 이미지를 확보한 것은 아님 |
| 백업·검증 이미지 | [Portal Dockerfile](../infra/k8s/backup-automation/Dockerfile)의 Python·age·rclone·sqlite·tar·kubectl 등 도구, 서비스별 백업 이미지 | immutable digest·검증 코드 버전·노드 이미지 존재·호환성 | [독립 Portal 복원 Job](../infra/k8s/tools/portal-backup-restore-job.py)의 `imagePullPolicy: Never`는 반입 이미지가 없으면 기동 불가함 |
| 앱 설정 | 현재 실행 설정·Secret 참조·환경 이름·마운트·네트워크·port binding | 이름/키 계약과 승인된 공급원 사용 가능 여부만 대조함 | 값·내부 주소·개인 접속 경로를 출력·복제하지 않음. 앱 데이터 백업을 인증/OAuth 백업으로 간주하지 않음 |
| Portal 저장소 | `portal-web-files-dynamic`, `portal-web-state-dynamic` 두 PVC와 실행 UID/GID `10001:10001` 권한 계약 | 대상 PVC UID·Bound·앱 접근 가능 여부·두 저장소의 동일 복원점 구성 | [운영 기준](operations-reference.md) 참조. 기존 권한을 임의 변경하지 않음 |
| Book/YouTube/Crawler 저장소 | 각각 `book-memo-data`, `youtube-memo-data`, `crawler-worker-data` | PVC UID·Bound·단일 writer·원본 데이터 구조 | [서비스 백업 manifest](../infra/k8s/backup-automation/book-memo-pvc-backup-cronjob.yaml)와 실행 시점 리소스를 대조함 |
| 백업 접근·복호화 | Portal `portal-pvc-backup-runtime`, Book `book-memo-pvc-backup-runtime`, YouTube `youtube-memo-pvc-backup-runtime`, Crawler `crawler-worker-pvc-backup-runtime` Secret 참조 | 각 `rclone-config`, `rclone-config-passphrase`, `age-recipient`, `age-identity` 키의 공급·사용 가능 여부 | 키 이름만 기록함. recipient만으로 복호화할 수 없으며 identity와 원격 접근이 모두 필요함 |
| 격리 Portal 복원 입력 | `portal-pvc-backup-evidence` ConfigMap, 검증 코드 ConfigMap, 위 Secret의 rclone 설정/암호와 age identity | 정확한 backup ID·암호문 digest·source digest·증적 시각·만료 | Job은 운영 PVC·API token을 mount하지 않음. `render`는 명세 생성 함수이며 생성·실행 성공 증거가 아님 |
| 원격 백업 위치 | 서비스별 백업 코드의 `REMOTE` 상수와 그 암호화 rclone 설정 | 서비스 scope와 원격 객체·원본 증적의 일치, 다운로드 가능 여부 | 실계정·객체 목록·경로 원문을 신규 문서/로그에 복사하지 않음 |
| 작업 공간 | Portal `check_restore`의 분리된 scratch·메모리 기반 rclone 설정 공간, 복원 Job의 emptyDir 용량/제한 | 암호문·tar·복원본 동시 보관 여유, plaintext 제거·권한·메모리 공간 분리 | 현재 데이터 용량과 실행 자원 충족 여부는 확인 필요 |
| 실행 권한 | 기존 제한 K3s 권한, 서비스별 백업 ServiceAccount/RBAC | 승인된 대상만 조회·scale·상태 갱신할 수 있는지 | 새 sudo 권한·외부 자격 증명 생성은 포함하지 않음 |
| 설정 복구 공급원 | 앱 runtime Secret과 rclone/age 키를 재공급하는 승인된 저장소 | 현재 노드/PVC/Secret을 잃어도 기존 절차로 공급 가능한지, 공급 소요 시간 | Git의 Secret 이름 존재만으로 재해 복구 준비 완료라고 판단하지 않음. 독립 접근·재공급 실측은 확인 필요 |

서비스별 Secret/PVC 계약은 [Portal](../infra/k8s/backup-automation/portal-pvc-backup-cronjob.yaml), [Book](../infra/k8s/backup-automation/book-memo-pvc-backup-cronjob.yaml), [YouTube](../infra/k8s/backup-automation/youtube-memo-pvc-backup-cronjob.yaml), [Crawler](../infra/k8s/backup-automation/crawler-worker-pvc-backup-cronjob.yaml)에서 확인함. 이 manifest는 설치 기본값의 근거이며 활성 운영 자원에 다시 적용하는 명령이 아님.

### 3.3 단일 writer·잠금·실패 경계

| 확인 지점 | 코드·운영 근거 | 점검 및 중단 기준 | 비고 |
|---|---|---|---|
| 실행 주체 | [운영 기준](operations-reference.md)의 root 소유 runtime marker와 K3s 소유 서비스의 Compose 재시작 제외 | marker 신뢰성·현재 writer·중지된 Docker 보존 여부를 확인함. marker 오류·양쪽 writer 실행 시 일반 재시작으로 해결하지 않음 | 초기 전환 절차를 현재 운영에 재실행하지 않음 |
| 순차 실행 소유권 | [pvc-backup-sequence.py](../infra/k8s/tools/pvc-backup-sequence.py)의 `local_lock`, `validate_cronjob`, `matching_job`, `terminal` | 공유 잠금·현재 Job 소유권·종료 여부 확인. 종료 불명확 시 다음 중복 실행을 하지 않음 | 기존 순차 실행기를 재사용함 |
| Portal 백업 | [portal-pvc-backup-verify.sh](../infra/k8s/tools/portal-pvc-backup-verify.sh)의 `acquire_lock`, `cleanup` 및 snapshot/restore 단계 | flock, 원 writer 중지·PVC snapshot·복귀/health·임시 평문 정리를 함께 확인함 | `--check` 성공은 `--go` 백업·복원 성공 아님 |
| 서비스별 백업 | [BookBackupController](../infra/k8s/tools/book-pvc-backup-verify.py)의 `_update_state`, `run_backup`, `_restore_writer`, `publish_success` | JSON Patch의 `lock_run_id` test, Deployment/PVC UID·resourceVersion, writer 종료·복귀를 확인함 | writer 복구·평문 정리 불확실 시 잠금 보존/수동 검토가 필요함. 임의 잠금 초기화 금지 |
| YouTube/Crawler 데이터 계약 | [YouTube restore_snapshot](../infra/k8s/tools/youtube-pvc-backup-verify.py), [Crawler check_crawler_data/restore_snapshot](../infra/k8s/tools/crawler-pvc-backup-verify.py) | 서비스 scope·전체 트리 digest·SQLite 검사 또는 JSON schema/참조 구조 검사 확인 | 단일 SQLite 파일 검사로 Crawler 전체 복원을 대체하지 않음 |
| 차량 DB | [backup.py](../car-care-worker/tools/backup.py)의 `snapshot_database`, `_execute`, `inspect_database` | SQLite online backup·원격 재다운로드·복호화·테이블 검사·snapshot digest 확인 | DB 전용 백업임. OAuth/자격 증명 재공급 증거와 분리함 |

Book의 `run_backup`은 snapshot 완료 후 암호화·원격 전송 전에 writer를 복귀시킴. 백업 Job 전체 수행 시간과 서비스 쓰기 중단 시간을 같게 기록하지 않음. Portal 등 다른 도구의 중단 구간을 Book과 동일하다고 추정하지 않음.

### 3.4 실제 실행 전후 점검표

아래는 승인된 실행 건별 확인 순서임. 체크 표시는 해당 건의 직접 증거를 확보했을 때만 수행함. 현재 모두 미수행 상태이며 실행 명령의 일괄 복사·자동 실행 목록으로 사용하지 않음.

| 순서 | 점검 항목 | 통과 기준 | 현재 상태 | 비고 |
|---:|---|---|---|---|
| 1 | 복구 목적·대상 확정 | 이미지 원복/격리 검증/운영 데이터 복원/writer 전환 중 대상, 복원점, 제외 범위, 실행 순서가 명확함 | 확인 필요 | 운영 승인 범위 확인 |
| 2 | 변경 전 현재 상태 보존 | 현재 커밋·이미지·PVC UID·writer·잠금·Job·Ready·외부 health·데이터 복원점 증거 확보 | 확인 필요 | 원격 응답 유실 시 재실행 전에 실제 상태 조회 |
| 3 | 이미지·설정·권한 확보 | 이전/목표 이미지 실제 사용 가능, DB 호환, 설정 공급원·자격 증명·작업 공간·실행 권한 확인 | 확인 필요 | 비밀값은 출력하지 않음 |
| 4 | 백업 선택 | 대상 scope·backup ID·artifact/source digest·원본 시각·증거 만료를 일치시킴 | 확인 필요 | 최신 객체명·Job 성공만으로 선택하지 않음 |
| 5 | 격리 복원 검증 | 다운로드 암호문 digest 일치 → age 복호화 → 안전한 archive 구조 → 데이터 digest·DB/JSON 검사 → 평문 정리 성공 | 확인 필요 | Portal은 `validate_evidence`, `extract_safe`, `check_restore` 기준 |
| 6 | 이미지 변경 또는 데이터 반영 판단 | 이미지 원복은 기존 image-only 도구로 제한함. 운영 데이터 반영은 별도 구체적 절차·승인·현 데이터 보존·writer 중단이 확보됨 | 확인 필요 | 준비가 없으면 운영 데이터 덮어쓰기 보류 |
| 7 | 복구 종료 검증 | 단일 writer·정합성·업무 검증·Ready·Endpoint·잠금 해제 확인. Portal과 변경 서비스 외부 health 각각 10초 간격 3회 성공 | 확인 필요 | 도구 내 health만으로 저장소 공통 운영 검증을 대체하지 않음 |
| 8 | 기록·실패 판정 | 시작/단계별/완료 시각, 실패 단계, 실행 범위와 미수행 항목 기록 | 확인 필요 | 적용 실패 후 자동복구 성공도 최초 배포 성공으로 기록하지 않음 |

Portal 독립 검증기의 `validate_evidence`는 백업 완료가 1일 이내인지와 명시 만료를 함께 검사하며, 복원 시각만 새로 기록해 오래된 백업을 유효하게 만들지 않음. 보관 중인 과거 복원점의 존재와 일일 운영 증거의 유효성은 구분함. 과거 복원점 선택은 현 검증기의 유효 기간 검사를 우회하는 방식으로 처리하지 않음.

### 3.5 RTO/RPO 측정 항목과 증거 누락

| 항목 | 필요한 시각·증거 | 계산/판정 | 현재 확인 수준·비고 |
|---|---|---|---|
| 준비 시간 | 이미지 확보 시작/완료, 설정·권한·복호화 공급 준비 시작/완료 | 장애 이후 처음 준비할 때 걸리는 시간을 각각 기록함 | 코드상 의존성만 확인함. 실제 독립 공급 시간 확인 필요 |
| 격리 복원 시간 | 원격 접근 시작, 다운로드 완료, 복호화 완료, 구조/DB 검증 완료, 평문 정리 완료 | 단계별 경과와 전체 경과를 측정함 | Job timeout/리소스 제한은 실측값 아님 |
| 서비스 중단 시간 | 실제 쓰기 중단 시작, writer 복귀, Ready·업무 검증·외부 health 종료 | 중단 구간과 백업 전체 시간을 분리함 | 기존 백업 성공 기록만으로 실제 중단 시간을 산출하지 않음 |
| 실제 RTO | 장애/서비스 중단 시작 시각과 사전에 정한 서비스 복구 완료 시각 | 완료 시각−시작 시각. 탐지·판단·준비·복원·검증 포함 여부를 함께 기록함 | 장애에서 서비스 복구까지의 연속 타임라인 미확보. 확인 필요 |
| 실제 RPO | 복원점이 포함한 마지막 확정 쓰기, 장애 직전 마지막 확정 쓰기, 복원 후 누락 기록 대조 | 마지막 복원 가능 쓰기와 장애 직전 쓰기의 시간·누락량을 측정함 | `backup_completed_at`은 원격 업로드/검증 완료 시각이며 snapshot 마지막 쓰기 시각과 같다고 가정하지 않음 |
| 목표 충족 | 서비스별 허용 중단·허용 손실 목표와 위 실측 | 승인된 목표와 실측을 비교함 | 목표 수치와 전체 실측은 확인 필요. 1일 백업·8일 증거 유효 기간을 RPO 보장으로 표현하지 않음 |
| 재해 복구 범위 | 노드/Secret/이미지 캐시/PVC 상실 가정에서 독립 공급·복원·서비스 검증 기록 | 동일 노드가 살아 있는 격리 검사와 전체 복구를 구분함 | 같은 Mac/V2 실습이나 기존 N100 격리 검사만으로 독립 환경 DR/HA 완료 처리하지 않음 |

[monthly-recovery-drill.sh](../infra/k8s/tools/monthly-recovery-drill.sh)는 백업 증적 검사·Telegram 확인 도구·격리 Pod 실습을 묶고 시작/완료 시각을 저장함. 이 시간은 해당 점검 실행 시간이며 실제 앱 데이터 복원 RTO가 아님. [운영 기준](operations-reference.md)에 남은 기존 당일 백업·격리 복원 기록도 최신 상태·직접 실습·알림 실제 수신을 대신하지 않음.

## 4. 검토 결과

| 항목 | 결과 | 비고 |
|---|---|---|
| 코드 경계 | 앱 이미지 변경, runtime 전환, 격리 복원, 운영 데이터 반영을 구분함 | 도구 지원 범위·실패 종료·재실행 조건 대조 |
| 기존 기능 재사용 | 순차 백업·서비스별 검증·암호화/보관·증적 검증을 참조함 | 신규 자동화·일정 변경 없음 |
| 보안·운영 보호 | 자격 증명 이름/키 계약만 기록함. 값·내부 주소·개인키 경로 미기록 | 운영 파일/자원 변경 없음 |
| 직접 학습 완료 | 확인 필요 | 사용자가 원복 경계를 설명하거나 준비 시간을 직접 측정한 증거 없음 |
| 최종 독립 검토 | 주 담당의 통합 검토 기록에서 관리함 | 본 문서 작성자는 독립 검토자를 겸하지 않음 |
