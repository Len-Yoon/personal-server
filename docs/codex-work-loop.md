# Codex 작업 완료 루프

승인·중단·작업 분담 기준은 [저장소 규칙](../AGENTS.md)을 따름. 이 문서는 실행 순서를 설명하며 별도의 승인이나 인원 기준을 추가하지 않음. CI artifact 확인·보존·결과 분류는 [작업 루프 증거 운영](agent-loop-evidence.md)을 따름.

## 1. 적용 범위

| 구분 | 내용 | 비고 |
|---|---|---|
| 적용 대상 | 개인서버 저장소에서 수행하는 코드·설정·문서 변경 작업 | Codex 작업에 적용함 |
| 적용 방식 | 작업 요청마다 수동으로 실행하는 문서형 루프 | 자동 실행 아님 |
| 적용 지침 | 사용자 지시·상위 지침과 저장소 `AGENTS.md`를 확인함 | 이 절차 문서에서 별도 분담 기준을 만들지 않음 |
| 제외 대상 | 서버 기동 영역 및 스케줄러 영역의 변경 | 기존 `AGENTS.md` 제한을 우선 적용함 |

## 2. 작업 절차

| 단계 | 수행 내용 | 완료 기준 |
|---:|---|---|
| 1 | 요청 목적, 변경 범위, 제외 범위, 성공 기준과 배포 여부를 확인함 | 요구사항과 금지 영역이 명확함 |
| 2 | 작업 규모에 맞춰 계획하고 기존 승인 또는 명시적 실행 요청의 범위를 확인함 | 동일 범위의 승인을 다시 요청하지 않음. 단순 문구·서식 변경은 PR에 기록함 |
| 2.1 | 화면·알림·외부 입력이 있는 기능은 표시 경로, 입력 형식, 저장 원본, 오류값 처리, 금지 영역을 사전 경계표로 확정함 | 서버·브라우저·기존 데이터 경로와 UTC/KST 등 시간 해석 기준이 한 표에 기록됨 |
| 3 | 새 작업은 최신 `main`에서 `codex/<작업명>` 브랜치를 생성하고 같은 목적의 보완은 기존 PR에서 진행함 | 한 목적의 변경을 한 브랜치·한 PR에서 마무리함 |
| 4 | 기능 변경은 필요한 회귀 테스트와 최소 구현을 수행하고, 문서 변경은 링크·이미지·문서 참조 계약을 확인함 | 변경 위험에 맞는 검사로 성공 기준을 확인함 |
| 5 | 관련 검사 성공 후 변경사항과 diff를 검토함. 기능·운영 변경은 AGENTS.md의 독립 검토 기준을 적용함 | 성공 기준, 금지 영역, 저장 원본 보존, 잔여 위험을 한 번에 확인함 |
| 6 | 기능 브랜치에 커밋·푸시하고 PR을 생성함 | PR CI와 Agent Review가 실행됨 |
| 7 | PR CI·Agent Review 성공과 자동배포 영향을 확인한 뒤 `main`으로 병합함 | 실제 운영 배포가 발생하면 병합 직전에 배포 승인을 확인하고, 관련 실패가 해소됨 |
| 8 | `main` CI·해당 배포 결과(배포 제외 포함)·작업공간 무변경을 확인한 즉시 작업 브랜치와 분리 작업공간을 정리함 | 사용자 파일과 미병합 작업은 보존하고 미정리 사유를 기록함 |
| 9 | 완료 또는 중단 결과를 정해진 양식으로 보고함 | 검증 결과와 확인 필요 사항을 기록함 |

`.superpowers/sdd/`는 Git 제외가 기본임. 이미 추적된 완료 작업의 `*-report.md`만 검증 보고서로 보관할 수 있으며, 임시 메모·초안은 추적하지 않음.

```text
요청 확인
→ 범위·성공 기준 확인
→ 표시 경로·입력·저장·오류 경계표
→ 작업 규모에 맞는 계획·기존 승인 범위 확인
→ 기능 브랜치 생성
→ 통합 회귀 테스트·최소 변경·정적 검사
→ 위험에 맞는 검토(기능·운영 변경은 독립 검토)
→ PR CI·Agent Review
→ 자동배포 영향 확인(운영 배포가 발생하면 병합 직전 승인)
→ main CI·N100 배포 확인
→ 성공: 브랜치 정리 및 완료 보고
→ 실패: 원인 분석 및 재검증
→ 승인 밖 동작·새 중대 위험·반복 실패: 해당 동작 보류 및 필요한 결정 확인
```

현재 개발 계획의 유효한 승인 범위는 [AGENTS.md 7절](../AGENTS.md#7-현재-개발-계획과-승인-범위)을 확인함. 같은 범위의 승인을 반복 요청하지 않으며, 일회성 승인 결과는 개발 계획의 이력에서 확인함.

### 2.1 브랜치 정리 기준

- 코드·설정·의존성 변경은 `main`에 직접 push하지 않고 기능 브랜치와 PR을 기본 경로로 사용함.
- 기능 브랜치명은 `codex/<작업명>` 형식을 사용함.
- `main` 직접 push는 긴급 복구처럼 PR을 거칠 수 없는 경우에만 사용자 명시 승인과 사유 기록을 전제로 허용함.
- 일반 개발 요청의 PR 병합은 중간 승인 없이 수행함. 병합이 운영 자동배포를 시작하면 실제 배포 대상·동작을 제시하고 병합 직전에 한 번 승인받음. 유효한 기존 배포 승인은 반복 요청하지 않음.

| 상태 | 처리 | 비고 |
|---|---|---|
| PR 병합 완료 | CI·해당 배포 결과와 작업공간 무변경을 확인한 즉시 해당 작업 브랜치·worktree를 정리함. 사용자 파일은 보존함 | GitHub는 병합 후 원격 head 브랜치를 자동 삭제함 |
| 작업 중단 | 재개 계획이 없으면 브랜치 삭제 여부를 확인함 | 중단 사유는 완료 보고에 기록함 |
| 미병합 작업 | 브랜치를 삭제하지 않음 | 검토·재작업에 필요함 |
| 재사용 예정 작업 | 브랜치를 삭제하지 않음 | 재사용 목적을 완료 보고에 기록함 |

- 병합 전, CI·배포 실패, 작업공간 변경 존재, 미병합 또는 재사용 예정 상태에서는 자동 삭제하지 않음.
- 작업 중단 브랜치 삭제는 사용자 승인 후 수행함.
- 완료 보고에는 브랜치명, 원격·로컬·분리 작업공간 삭제 여부, 미삭제 사유를 포함함.

## 3. 검증 기준

| 구분 | 기준 | 처리 |
|---|---|---|
| 관련 테스트 | 변경한 기능 또는 영향 범위의 테스트를 실행함 | 성공 시 검증 결과에 명시함 |
| 정적 검사 | 프로젝트에서 사용 가능한 린트·타입검사·구문 검사를 실행함 | 적용 가능한 항목만 실행함 |
| 변경사항 검토 | `git diff --check` 및 변경 파일 diff를 확인함 | 공백 오류와 범위 외 변경 여부를 확인함 |
| 검증 불가 | 테스트 또는 검사를 실행할 수 없음 | 성공으로 처리하지 않고 `확인 필요`로 보고함 |
| 테스트 부재 | 관련 테스트가 존재하지 않음 | 테스트 부재 사실과 잔여 위험을 `확인 필요`로 보고함 |

## 4. 실패 재시도 및 중단 기준

### 4.0 N100 자동복구 적용 전후 확인

N100 자동복구 변경은 적용 전후 `https://len.pe.kr/health`를 10초 간격으로 3회 호출해 모두 HTTP 200인지 확인함. Supervisor가 잠금을 획득하고 시작되면 `supervisor_started`를 기록함. `BootTrigger`에 의한 시작뿐 아니라 예약 작업의 재시작과 수동 `-Supervisor` 실행도 같은 이벤트를 기록하므로, 이 이벤트만으로 Windows 부팅을 증명하지 않음. 재시작 뒤 Supervisor의 `post_boot_check` 시작·완료·실패 이벤트와 기존 recovery event log를 확인함. BootTrigger 경로는 2026-09-23 승인된 유지보수 재부팅에서 두 예약 작업·WSL 시작, `post_boot_check=passed`, 외부 health 3회 HTTP 200으로 런타임 검증함. 이후 자동복구 변경이 이 경로에 영향을 주면 같은 검증을 다시 수행함. 이벤트는 기존 UTC timestamp와 최근 200건 보존 기준을 사용함. Windows·WSL·K3s 재시작 또는 초기 점검 자체에 대한 Telegram 알림은 추가하지 않으며, Telegram 알림은 Cloudflare Tunnel 장애·복구 전환 경로만 대상으로 함.

[AGENTS.md 2절](../AGENTS.md#2-연속-진행과-중단-기준)의 승인·재시도 기준을 적용함. 동일 원인의 실패에 대한 수정·재실행은 최초 실패 이후 최대 3회이며, 정상적인 최초·후속 검증과 PR·main 검사는 실패 재시도 횟수에 포함하지 않음. 같은 원인의 실패는 단계가 바뀌어도 합산함.

기존 승인 안의 보안·운영 작업은 영향이 있다는 이유만으로 다시 승인받지 않음. 승인 밖 동작·새로운 중대한 위험·파괴적 변경·조사로 해결되지 않는 필수 정보 누락은 해당 동작만 보류하고 필요한 결정을 확인함. 미해결 실패가 있는 변경은 병합하지 않음.

### 4.1 효율적 검토 루프

- 기능 변경은 동일 기능의 서비스별 검토를 순차 반복하지 않음. 경계표와 통합 회귀 테스트를 기준으로 구현 검증 1회와 독립 통합 검토 1회를 기본으로 함. 문서 변경의 단독 검토 허용 기준은 AGENTS.md에 따름.
- 검토에서 누락된 경계값이 발견되면 필요한 회귀 테스트를 보완하고 영향을 받는 부분을 다시 검토함. 같은 원인의 실패가 반복되면 설계·테스트 경계를 먼저 재검토하며 재시도 한도는 AGENTS.md에 따름.
- 검증 재사용 시 커밋 또는 작업 트리 diff·경로·환경·명령·결과를 기록함. 이후 변경의 영향을 받지 않는 결과만 재사용하고 필수 CI는 유지함.
- CI 정책, 작업 보고서, 증적 파일은 구현 전에 변경 범위 검증기에서 어떻게 분류되는지 확인함.
- CI 테스트 매트릭스의 Python 버전은 각 서비스 Dockerfile의 기준 버전과 일치시킴.

## 6. 하위 에이전트 운영 기준

인원과 필수 역할은 [AGENTS.md 6절](../AGENTS.md#6-검증과-작업-분담)을 따름. 기능 변경은 독립 검토를, CI/CD·보안·DB 마이그레이션·배포 영향 작업은 전문 검토를 필수로 적용함. 파일 수만으로 인원을 늘리지 않고 위험·의존성·병렬 진행의 이점을 판단함.

- 작업 시작 전 역할별 담당 범위와 성공 기준을 선언하고 같은 파일을 동시에 수정하지 않음.
- 검토 담당은 구현 담당과 독립적으로 diff·보호 대상·관련 테스트·잔여 위험을 확인함.
- 에이전트 운영 기록에는 인원 선택 근거·역할·검토 결과를 남김. 문서만 변경한 단독 작업은 미사용 사유를 짧게 기록함.

## 7. 제외 범위

- Codex 전역 설정, 전역 스킬, 자동화 일정은 변경하지 않음.
- CI/CD workflow, 서버 기동 스크립트, 스케줄러 코드는 본 루프의 자동 변경 대상에 포함하지 않음.
- 자동 재시도 스크립트, 외부 서비스 연동, 무인 배포는 포함하지 않음.

완료·소진된 일회성 승인은 [개발 계획의 승인 이력](20260921_프로젝트보완_개발계획.md#완료소진된-일회성-승인-이력)을 참조함. 새 작업에 대한 승인으로 재사용하지 않음.
