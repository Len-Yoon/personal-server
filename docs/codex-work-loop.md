# Codex 작업 완료 루프

CI artifact 확인·보존·결과 분류는 [작업 루프 증거 운영](agent-loop-evidence.md)을 따름.

## 1. 적용 범위

| 구분 | 내용 | 비고 |
|---|---|---|
| 적용 대상 | 개인서버 저장소에서 수행하는 코드·설정·문서 변경 작업 | Codex 작업에 적용함 |
| 적용 방식 | 작업 요청마다 수동으로 실행하는 문서형 루프 | 자동 실행 아님 |
| 전역 기본 기준 | `~/.codex/AGENTS.md`의 하위 에이전트 운영 기준을 모든 새 프로젝트·새 채팅에 적용함 | 저장소 규칙이 더 엄격하면 저장소 규칙을 우선 적용함 |
| 제외 대상 | 서버 기동 영역 및 스케줄러 영역의 변경 | 기존 `AGENTS.md` 제한을 우선 적용함 |

## 2. 작업 절차

| 단계 | 수행 내용 | 완료 기준 |
|---:|---|---|
| 1 | 요청 목적, 변경 범위, 제외 범위, 성공 기준과 배포 여부를 확인함 | 요구사항과 금지 영역이 명확함 |
| 2 | 변경 영향이 있는 경우 구현 계획을 작성하고 사용자 승인을 확인함 | 승인 또는 명시적 실행 요청을 확인함 |
| 2.1 | 화면·알림·외부 입력이 있는 기능은 표시 경로, 입력 형식, 저장 원본, 오류값 처리, 금지 영역을 사전 경계표로 확정함 | 서버·브라우저·기존 데이터 경로와 UTC/KST 등 시간 해석 기준이 한 표에 기록됨 |
| 3 | 최신 `main`에서 `codex/<작업명>` 기능 브랜치를 생성함 | `main` 직접 변경 없이 작업 범위가 격리됨 |
| 4 | 경계표의 대표 정상·기존·오류 입력을 포함하는 통합 회귀 테스트를 먼저 추가한 뒤 최소 변경을 수행함 | 서버·브라우저·기존 데이터의 같은 표시 계약을 하나의 검증 묶음으로 확인함 |
| 5 | 관련 테스트·정적 검사 성공 후 변경사항과 diff를 독립 통합 검토함 | 성공 기준, 금지 영역, 저장 원본 보존, 잔여 위험을 한 번에 확인함 |
| 6 | 기능 브랜치에 커밋·푸시하고 PR을 생성함 | PR CI와 Agent Review가 실행됨 |
| 7 | PR CI·Agent Review 성공 및 사용자 병합 승인을 확인한 뒤 `main`으로 병합함 | `main` 배포 대상이 검증된 변경으로 제한됨 |
| 8 | `main` CI·N100 배포 성공 및 작업공간 무변경을 확인한 뒤 브랜치와 분리 작업공간을 정리함 | 불필요한 원격·로컬 브랜치가 남지 않음 |
| 9 | 완료 또는 중단 결과를 정해진 양식으로 보고함 | 검증 결과와 확인 필요 사항을 기록함 |

`.superpowers/sdd/`는 Git 제외가 기본임. 이미 추적된 완료 작업의 `*-report.md`만 검증 보고서로 보관할 수 있으며, 임시 메모·초안은 추적하지 않음.

```text
요청 확인
→ 범위·성공 기준 확인
→ 표시 경로·입력·저장·오류 경계표
→ 계획·승인
→ 기능 브랜치 생성
→ 통합 회귀 테스트·최소 변경·정적 검사
→ 독립 통합 검토 1회
→ PR CI·Agent Review
→ 사용자 병합 승인
→ main CI·N100 배포 확인
→ 성공: 브랜치 정리 및 완료 보고
→ 실패: 원인 분석 및 재검증
→ 반복 실패·위험 판단: 중단 및 사용자 확인
```

### 2.1 브랜치 정리 기준

- 코드·설정·의존성 변경은 `main`에 직접 push하지 않고 기능 브랜치와 PR을 기본 경로로 사용함.
- 기능 브랜치명은 `codex/<작업명>` 형식을 사용함.
- `main` 직접 push는 긴급 복구처럼 PR을 거칠 수 없는 경우에만 사용자 명시 승인과 사유 기록을 전제로 허용함.
- PR 병합 권한은 사용자에게 있으며, CI·Agent Review 성공만으로 자동 병합하지 않음.

| 상태 | 처리 | 비고 |
|---|---|---|
| PR 병합 완료 | CI·배포 성공 및 작업공간 무변경을 확인한 뒤 원격·로컬 작업 브랜치와 분리 작업공간을 자동 삭제함 | GitHub는 병합 후 원격 head 브랜치를 자동 삭제함 |
| 작업 중단 | 재개 계획이 없으면 브랜치 삭제 여부를 확인함 | 중단 사유는 완료 보고에 기록함 |
| 미병합 작업 | 브랜치를 삭제하지 않음 | 검토·재작업에 필요함 |
| 재사용 예정 작업 | 브랜치를 삭제하지 않음 | 재사용 목적을 완료 보고에 기록함 |

- 병합 전, CI·배포 실패, 작업공간 변경 존재, 미병합 또는 재사용 예정 상태에서는 자동 삭제하지 않음.
- 작업 중단 브랜치 삭제는 사용자 승인 후 수행함.
- 완료 보고에는 브랜치명, 원격·로컬·분리 작업공간 삭제 여부, 미삭제 사유를 포함함.

## 3. 검증 기준

| 구분 | 기준 | 처리 |
|---|---|---|
| 관련 테스트 | 변경한 기능 또는 영향 범위의 테스트를 실행함 | 성공 시 검증 결과에 명시함 |
| 정적 검사 | 프로젝트에서 사용 가능한 린트·타입검사·구문 검사를 실행함 | 적용 가능한 항목만 실행함 |
| 변경사항 검토 | `git diff --check` 및 변경 파일 diff를 확인함 | 공백 오류와 범위 외 변경 여부를 확인함 |
| 검증 불가 | 테스트 또는 검사를 실행할 수 없음 | 성공으로 처리하지 않고 `확인 필요`로 보고함 |
| 테스트 부재 | 관련 테스트가 존재하지 않음 | 테스트 부재 사실과 잔여 위험을 `확인 필요`로 보고함 |

## 4. 실패 재시도 및 중단 기준

| 구분 | 기준 | 처리 |
|---|---|---|
| 재시도 | 실패 원인이 확인되고 최소 수정으로 해결 가능함 | 수정 후 관련 검증을 다시 실행함 |
| 재시도 한도 | 동일 작업의 재검증은 최대 3회까지 수행함 | 한도 초과 시 작업을 중단함 |
| 범위 불명확 | 요구사항, 변경 대상, 성공 기준이 확정되지 않음 | 구현 전 사용자 확인을 요청함 |
| 금지 영역 | 서버 기동 또는 스케줄러 영역 변경이 필요함 | 작업을 중단하고 사용자 확인을 요청함 |
| 위험 변경 | 보안·운영·배포 영향 또는 되돌리기 어려운 변경이 필요함 | 변경 전 사용자 확인을 요청함 |
| 반복 실패 | 같은 원인이 반복되거나 원인을 확인할 수 없음 | 시도 내역과 원인을 보고하고 중단함 |

### 4.1 효율적 검토 루프

- 동일 기능의 서비스별 검토를 순차 반복하지 않음. 경계표와 통합 회귀 테스트를 기준으로 구현 검증 1회와 독립 통합 검토 1회를 기본으로 함.
- 검토에서 누락된 경계값이 발견되면 해당 기능의 경계표와 통합 테스트에 추가한 뒤 한 번만 재검토함.
- 동일 유형의 재검토가 두 번 이상 필요하면 새 수정 전에 경계표·테스트 설계를 다시 검토하고, 원인이 구조적이면 사용자에게 보고함.
- CI 정책, 작업 보고서, 증적 파일은 구현 전에 변경 범위 검증기에서 어떻게 분류되는지 확인함.

## 5. 완료 보고 양식

| 항목 | 내용 |
|---|---|
| 변경 내용 | 변경 목적과 주요 변경사항 |
| 변경 파일 | 생성·수정·삭제한 파일 목록 |
| 검증 결과 | 실행 명령, 성공·실패 결과, 재시도 횟수 |
| 미검증 항목 | 실행하지 못한 검증과 사유 |
| 브랜치 정리 | 브랜치명, 원격·로컬 삭제 여부 또는 미삭제 사유 |
| 에이전트 운영 기록 | 역할별 사용 여부, 담당 범위, 검토·검증 결과, 미사용 사유 |
| 확인 필요 사항 | 사용자 판단, 후속 작업, 잔여 위험 |

## 6. 하위 에이전트 운영 기준

| 작업 구분 | 필수 역할 | 인원 | 적용 기준 |
|---|---|---:|---|
| 읽기 전용 조사, 단순 질문, 기능 영향 없는 문서화·문구·서식 변경 | 주 에이전트 | 1명 | 하위 에이전트 미사용 사유를 완료 보고에 기록함 |
| 단일 서비스 기능 변경·버그 수정 | 주 에이전트, 독립 검토 에이전트 | 2명 | 구현과 검토의 역할을 분리함 |
| 리팩터링, 2개 이상 서비스·모듈 변경, 3개 초과 기능 구현·테스트·설정 파일을 수정하는 변경 | 주 에이전트, 구현 에이전트, 검토 에이전트 | 3명 | 분업을 필수로 적용함 |
| CI/CD·보안·DB 마이그레이션·배포 영향 | 주 에이전트, 구현 에이전트, 검토 에이전트, 전문 검토 에이전트 | 최대 4명 | 전문 검토를 필수로 적용함 |

- 작업 시작 전 역할별 담당 범위, 같은 파일의 동시 수정 금지, 성공 기준을 선언함.
- 구현 에이전트와 검토 에이전트는 동일한 변경을 승인하지 않으며, 검토 에이전트는 diff·금지 영역·관련 테스트·잔여 위험을 독립 확인함.
- 하위 에이전트를 사용하지 않는 작업은 위 표의 단일 처리 조건에 해당하는 사유를 완료 보고에 기록함. 단순함만을 이유로 리팩터링·다중 모듈 변경의 분업을 생략하지 않음.
- 같은 파일을 수정하는 구현 작업은 병렬로 분리하지 않음.
- 전문 검토 에이전트는 고위험 변경에서 필수이며, 완료 보고에 검토 범위와 결과를 기록함.

## 7. 제외 범위

- Codex 전역 설정, 전역 스킬, 자동화 일정은 변경하지 않음.
- CI/CD workflow, 서버 기동 스크립트, 스케줄러 코드는 본 루프의 자동 변경 대상에 포함하지 않음.
- 자동 재시도 스크립트, 외부 서비스 연동, 무인 배포는 포함하지 않음.
