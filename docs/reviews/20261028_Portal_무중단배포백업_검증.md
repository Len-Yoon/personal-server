## 3. 상세 내용

### 3.1 적용 범위와 성공 기준

- 최초 구현의 운영 기본값은 Recreate·정지 백업이었음. 2026-10-29 별도 승인으로 같은 노드의 일시적인 두 Portal Pod·공유 상태·RollingUpdate와 Portal 온라인 백업만 적용함. 다른 앱의 writer·백업 방식은 유지함.
- 호환된 새 버전끼리의 배포·백업 중 인증·조회·저장·수정·업로드·삭제 확인의 연속성을 검증함. 단일 N100 자체 장애에 대한 HA는 이번 범위에 포함되지 않음.
- 기존 메모리 세션은 첫 새 Pod가 읽을 수 없음. 최초 전환의 재인증 가능성과 기존 Pod의 30초 초과 요청 완료 미보장 예외를 사용자가 수용함. 이후 호환 버전끼리의 연속성을 최초 전환의 무손실 증거로 확대하지 않음.

운영 구성을 늘리는 별도 DB 서버·상시 작업자는 추가하지 않음. 공유 세션은 기존 state PVC의 SQLite 파일 하나를 사용함. 일상 백업 진입점은 기존 `portal-pvc-backup-verify.sh --go`와 순차 실행 하나를 유지함. HTTP 연속성 시험은 기존 Portal 테스트에 통합하고, 별도 RO 런타임 도구는 이미지 CI에서 자동 실행함. 사람이 배포마다 따로 실행하는 절차로 추가하지 않음. 배포 patch 렌더는 최초 전환 준비용이고, 전환 후 일반 앱 갱신은 기존 image 변경으로 새 RollingUpdate 정책을 사용함. `portal-cutover.sh`의 Compose/PVC writer 전환은 일반 앱 갱신으로 사용하지 않음.

### 3.2 공유 인증·철회

`AUTH_SESSION_STATE_PATH=/var/lib/portal/auth/session-state.sqlite3`를 명시한 경우만 공유 DB를 사용함. scope·고정 만료·상한을 유지하고 token/payload의 hash만 저장함. DB 오류를 메모리 인증 성공으로 우회하지 않음. 전용 부모와 DB/sidecar의 소유·비공유 쓰기·비공개 권한·symlink/hardlink 경계를 검사함.

공유 WAL을 사용하는 앱은 SQLite의 WAL-reset 수정 버전(3.51.3 이상 또는 3.50.7/3.44.6 계열 backport)을 startup/readiness에서 요구함. 명시적 development/test 합성 시험 외 빈 값·prod·staging도 이 검사를 거침. Portal 이미지는 `sqlite-libs>=3.51.3`을 요구함. 로컬 Python의 3.45.1 시험은 기능 회귀이며 운영 가능한 패키지 증거로 확대하지 않음.

SQLite WAL 연결을 앱 lifespan 동안 유지하여 유휴 시간에도 읽기 전용 백업 독자가 필요한 sidecar를 사용할 수 있게 함. 연결은 열린 트랜잭션을 유지하지 않으며 앱 종료 때 닫음. 실제 RO mount의 active/idle PASS와 writer 종료 후 SAFE_FAIL을 정확한 이미지의 CI 런타임 시험으로 확인함.

정상 앱 배포에서는 세션을 폐기하지 않음. 자격 증명 회전은 이전 자격 증명을 가진 모든 Pod가 종료된 뒤 `python3 -m app.services.session_store --revoke-all`을 명시 실행하여 세션과 확인 grant를 한 트랜잭션으로 철회하고 새 로그인·이전 쿠키 거부를 확인해야 함. 이 명령은 설정된 공유 DB만 열며 토큰·경로를 출력하지 않음. 백업 복원 후에는 서빙 재개 전에 같은 철회를 수행하여 과거 백업이 철회된 세션을 되살리지 않도록 함. 이번 작업은 실제 Secret 교체·세션 철회를 실행하지 않음.

### 3.3 파일·DB 백업 계약

| 대상 | 캡처 방법 | 비고 |
|---|---|---|
| 업로드·휴지통 | 기존 root-directory flock 안에서 완성된 파일의 읽기 FD 고정 | hardlink 사용 안 함, quota·ctime 변경 안 함 |
| Portfolio·인증 JSON | 원자 교체된 최종 파일의 FD 고정 | 임시 파일 제외 |
| 보안 로그 | 캡처한 길이까지 복사 후 마지막 완결 행 보존 | append-only 전제 |
| HomeOps·북마크·공유 세션 DB | read-only source의 SQLite backup API | WAL/SHM/journal raw 복사 금지 |
| 알 수 없는 mutable state | 백업 실패 처리 | 앱 정지·추측 복사로 전환하지 않음 |

구성요소별 캡처 시각과 `per-store` 일관성을 기록하며 전체 파일·DB의 단일 전역 시점을 보장하지 않음. 파일 외부 in-place rewrite는 지원하지 않음. 정상 rename/delete의 ctime·nlink 변화는 내용 변조로 오판하지 않음.

FD 여유·항목 수·깊이·출력 총량·획득/유지 시간 예산을 검사하며 실패 시 본 실행의 FD와 출력만 정리함. 잠금 시간은 시스템 호출 사이에 검사하므로 개별 느린 파일시스템 호출의 250ms 내 선점은 보장하지 않음. SQLite는 남은 출력 예산으로 검사하며 증가 감지 전 한 배치가 최대 1MiB까지 복사될 수 있음. 스냅샷·tar·암호화·다운로드·복원 사본의 여유를 사전 계산하고 복사 중·각 후속 단계에서도 여유 공간을 확인함. 부족하면 백업만 실패 처리함.

온라인 모드는 in-cluster 실행·실제 read-only mount·새 앱 capability 표시를 요구함. 기본 quiesced 경로는 유지함. `PORTAL_BACKUP_SNAPSHOT_MODE=online`을 무시하는 구버전 이미지는 정확한 새 이미지 검증과 알려진 legacy digest 거부로 방지함.

### 3.4 배포 준비 도구

`infra/k8s/tools/portal-continuity-rollout.py`는 Deployment/PVC/PV/선택적 backup CronJob JSON과 digest-pinned image로 조건부 patch만 출력함. Kubernetes 호출은 하지 않음. UID·resourceVersion·현재 image·replicas 전제조건, Bound RWO·동일 노드·PV claimRef를 대조하고 네트워크 볼륨·RWOP를 거부함. 기존 환경 변수·자격 값은 patch에 복제하지 않음.

새 설정은 `maxUnavailable=0`, `maxSurge=1`, `/ready` startup/readiness, 10초 preStop, 300초 앱 graceful shutdown, 330초 Pod 종료 유예를 준비함. 무한히 긴 요청의 완료를 보장하지 않음. 기존 Recreate Pod에 새 종료 유예가 소급 적용되는 것은 아님.

선택적 backup patch는 기존 보안 계약으로 후보 template를 검증하고 개별 CronJob의 suspend를 유지함. 순차 백업 서비스에만 `PORTAL_BACKUP_ONLINE_IMAGE`를 지정하는 drop-in을 준비하며 timer 일정은 바꾸지 않음. 이 값 또는 `--portal-online-image`가 없으면 기존 image/env 계약을 유지함.

## 6. 후속 조치

아래는 2026-10-29 사용자가 두 예외와 함께 승인한 실행·복귀 계획이며 결과는 4.4절에 기록함. 이번 운영 승인과 기존 검증 CI 확장·PR/main 실행 승인은 사용 완료이며 새 배포·추가 롤링·수동 백업에 재사용하지 않음. 최초 전환의 재로그인 가능성·기존 Pod의 30초 초과 요청 완료 미보장은 이후 호환 버전끼리의 연속성과 구분함.

승인 시 순서는 PR 병합·main CI 확인 → 사용자 파일을 보존한 N100 fast-forward → 정확한 AMD64 Portal/backup OCI 체크섬·digest 반입 → 기존 timer 일시 중지·기존 sequence 잠금 획득·service/Job/상태 재확인 → 조건부 Portal RollingUpdate·공유 세션 적용 → 조회/저장/수정·인증·외부 health 확인 → 검증한 동일 공유 세션 이미지에 소스 기록 annotation을 추가하는 호환 버전 검증 롤링 1회 → 조건부 backup main/init image·online mode 적용 → 해당 CronJob에서 소유 수동 Job 1개를 만들어 기존 `portal-pvc-backup-verify.sh --go`의 online 백업·격리 복원 검증 → PASS일 때만 순차 서비스 전용 image drop-in·daemon-reload·잠금 해제·기존 timer 재개 순서임. 검증 롤링과 백업 구간에 같은 쿠키로 합성 항목의 조회·저장·수정을 계속 실행하여 실패·ack 손실을 기록함. 주기적 재생성은 추가하지 않음. 기존 앱·백업 Secret은 승인된 시험과 백업 중 메모리/기존 mount에서만 참조하며 출력·복제하지 않음. 시험은 소유한 합성 항목만 사용하고 정리하며, 사용자 데이터·Secret 값·Caddy·Tunnel·다른 서비스·timer 일정은 변경하지 않음.

실패 시 새 쓰기가 반영된 PVC를 과거 복원점으로 덮어쓰지 않음. 실행 중 Job·Pod 상태를 먼저 확인하고, 이미지/설정만 UID/resourceVersion 조건으로 복귀함. legacy 이미지 복귀도 재로그인이 필요할 수 있음. 실패한 online 백업은 추가 자동 실행을 보류하고 원인을 보고하며, 서비스를 정지시키는 기존 quiesced 백업을 조용히 재활성화하지 않음. 운영 전후 외부 health는 10초 간격 3회씩 확인함.

timer를 중지한 뒤 기존 `pvc-backup-sequence.py`의 `local_lock`을 실제 획득하고, service inactive·모든 활성 백업 Job 부재·기존 백업 상태 잠금 해제를 다시 확인함. 일회성 `--check-lock`으로 대체하지 않으며 Portal/backup patch·수동 검증·실패 복귀까지 같은 잠금을 유지함. 정상 완료 시 잠금 해제 뒤 기존 timer를 재개하고, 검증 실패 시 자동 백업을 보류한 채 잠금을 해제하여 원인을 보고함. 새 잠금·스케줄러는 추가하지 않음.
