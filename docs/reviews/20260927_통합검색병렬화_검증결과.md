### 3.2 학습 포인트

1. **동시 시작**: 순차 처리에서는 각 서비스 대기가 누적됨. 병렬 처리에서는 세 요청을 먼저 생성하고 함께 기다림.
2. **전체 시간 예산**: HTTP read timeout만으로는 본문이 조금씩 계속 오는 상황을 제한하기 어려움. `asyncio.wait`로 전체 fan-out 대기를 제한함.
3. **부분 성공**: 완료 task의 결과만 수집하고 미완료 서비스는 unavailable로 남김. 정상적인 빈 목록은 ok임.
4. **취소와 회수**: 미완료 task를 cancel한 뒤 gather하여 클라이언트 종료 전에 정리함. 단순히 기다리기만 중단하지 않음.
5. **DNS 경계**: 요청마다 `asyncio.run`을 호출하면 종료 과정에서 DNS executor를 기다릴 수 있음. 실제 route를 async로 연결하여 서버 루프를 재사용함.

1.5초는 HTTP 병렬 조회의 대기 예산임. 클라이언트 초기화·JSON 파싱·템플릿 렌더링·OS 스케줄링을 포함한 브라우저 응답의 엄격한 실시간 상한은 아님. 취소는 진행 중인 OS DNS 함수를 강제로 종료하지 않으며, 응답이 DNS worker 종료를 기다리지 않도록 처리함.

### 3.3 로컬 전후 측정

Python 3.11.9에서 로컬 ThreadingHTTPServer로 기존 코드와 최종 코드를 각각 실행함. 각 조건·버전당 5회이며 p95는 nearest-rank 방식이므로 이 표에서는 표본 최댓값과 같음. 실서비스 부하 테스트나 운영 SLO 측정이 아님.

| 조건 | 변경 전 평균 | 변경 후 평균 | 변경 전 p95 | 변경 후 p95 | 비고 |
|---|---:|---:|---:|---:|---|
| 세 서비스 각각 0.10초 지연 | 0.3141초 | 0.1298초 | 0.3175초 | 0.1394초 | 모든 서비스 ok, 실패 0/5회 |

기준 코드는 `git show b9d7729:portal-web/app/services/global_search.py`로 읽었으며 데이터는 `{ "results": [] }`만 반환함. 최종 비동기 함수는 측정 스크립트에서 asyncio.run으로 실행하였으므로 루프 시작·종료 비용도 포함됨. 실제 대시보드는 서버 루프를 재사용함. 원시 실험 스크립트·JSON은 개발기 `/tmp/parallel-search-benchmark.py`, `/tmp/parallel-search-benchmark.json`에 임시 보관되며 영구 증적은 본 표임.
