## 2. 핵심 요약

동일 생성 초의 최신 백업들을 모두 보존하도록 수정한 소스를 네 후보 이미지에 포함함. 2026-10-11 02:30~02:39 기존 이미지의 순차 백업·복원 검증·보존 처리는 모두 성공함. 이 결과를 신규 후보의 실제 실행 성공으로 사용하지 않음. 새 이미지 운영 적용은 준비 중이며 아직 완료로 판정하지 않음.

## 3. 적용 범위와 복구 설계

| 항목 | 허용 범위 | 비고 |
|---|---|---|
| 이미지 | 검증된 네 OCI archive 반입·정확 digest alias 확인 | 기존 이미지와 모든 종속 콘텐츠 보존, prune 금지 |
| 운영 CronJob | suspended 상태의 init/main 이미지 각 두 필드, 총 여덟 필드만 CAS 교체 | 전체 manifest 적용 금지 |
| 소스 | 정확 CI 검증된 병합 커밋으로 fast-forward | 강제 reset·untracked 덮어쓰기 금지 |
| 실행기 | 네 Stage 이미지 상수와 세 서비스 production-state 이미지, Portal 설치 참조 이미지 | 총 아홉 literal만 변경하며 실행 로직은 유지함 |
| 잠금 | 기존 순차 백업 flock 한 번 소유 | 정상·원복·검증 전 구간 유지, 중첩 획득 금지 |
| 제외 | 수동 백업·삭제·Secret/PVC·앱 이미지·Caddy·정책·일정·timer·bootstrap | 다음 기존 정기 실행으로 실제 동작을 확인함 |

사전 main 병합·CI 검증된 정방향 C2와 그 후손인 역방향 C3를 함께 준비함. 운영 변경 도중 PR/CI를 새로 기다리지 않고 즉시 원복할 수 있도록, 적용 PR과 독립 원복 PR을 위험 경계에 따라 분리함. C3는 원복 준비용 커밋이며 병합 자체를 실제 원복으로 표현하지 않음. 적용 직전 origin/main=C3와 C1→C2→C3 ancestry·정확 변경 경로·파일 바이트를 확인함. 새 실행 도구의 명시적 계약은 검증된 main 이력의 정확 C2를 배포하는 것으로, 기존 일회성 source-sync helper의 FETCH_HEAD==TARGET 조건을 바꾸거나 우회하지 않음.

정상 적용 시 N100=C2이고 저장소 main=C3인 일시적 차이를 실제 결과에 명시함. C2 이전 실패는 기존 소스와 정확 원래 여덟 이미지 필드로 복구함. C2 이후 실패는 같은 잠금에서 C3로 fast-forward하여 기존 이미지 참조와 일치시킴. 응답 유실은 재실행 전에 HEAD·tracked/index/worktree와 UID/spec을 조회하여 분류함. 알 수 없는 변경·원복 실패 시 잠금을 소유한 프로세스를 유지하고 추가 변경을 중단함. 외부 변경을 덮어쓰지 않음.

| 신규 이미지 정기 백업 | 미수행 | 새 실행의 복원·보존·잠금 해제 증거로 확인함 |

최초 제한 환경의 Portal·Book·Car 로컬 socket 검사는 해당 세 묶음을 허용 환경에서 다시 실행해 모두 통과함. maintenance의 프로세스 종료 검사는 허용 환경에서 성공했고, 신규 테스트 등록 중 발생한 검사 목록 불일치는 CI 목록과 계약 기대값에 같은 모듈 한 개를 추가한 뒤 영향받은 실행 계약 28건을 통과함. 기존 k8s 1,002건 전체 결과에 최신 신규 도구 39건을 결합하고, 변경 영향이 없는 성공 결과를 재사용함. 문서 29건·구문·공백 검사도 통과함. PR/main 필수 CI는 이 로컬 결과와 별도로 실행함.

전송·반입 전용 절차와 신규 도구는 운영·보안 전문 검토 담당이 구현과 독립적으로 검토함. 주 담당은 이미지 pin·문서·실제 실행·검증 통합을, 구현 담당은 교체 도구와 회귀 검사를 맡음. 두 하위 담당은 gpt-6.1-sol/high를 사용했으며 운영 복구와 보호 경계의 실패 비용을 고려함. 같은 파일 동시 수정과 하위 담당의 운영 조작은 없었음.
