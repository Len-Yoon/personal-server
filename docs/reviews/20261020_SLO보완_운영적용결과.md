## 2. 핵심 요약

사용자가 적용 범위·순서·검증·복구 계획 확인 후 “진행하고 배포까지 해”로 승인함. N100 fast-forward 동기화와 검증 이미지 3종 반입 후 relay → 감사 3종 → 단일 ConfigMap 조회 권한 → 수집기 순서로 적용 완료함. 검증용·공식 감사 각 1회, 격리 장애·자동 복구, Telegram 수신, 임시 자원 정리를 확인함. 이번 배포 승인은 해당 실행에 사용 완료함.

오늘 기존 기준 기록은 보존함. 새 기준 `freshness-1800-v1`의 실제 운영 저장과 다음 정기 실행은 아직 확인 필요함. 기존 SLO 실패·관측 불가 이력을 정상으로 재작성하지 않음.

## 4. 검토 결과

| 역할 | 담당 | 결과·독립성 |
|---|---|---|

| 운영 전문 독립 검토 | `slo_deployment_independent` | gpt-6.1-sol high, 운영·권한·복구 실패 비용에 따라 선택. 구현·적용 파일과 운영 상태를 수정하지 않고 실제 원본·전후 증거 대조함. 별도 fresh 원격 조회로 보호 대상·실행 이미지·복구·전달·정리를 직접 대조하여 PASS함. 신규 날짜 저장은 검토 범위에서 미검증으로 유지하며 최종 판단은 PR 완료 기록에 고정함 |

같은 파일 동시 수정 없음. 원래 코드의 최종 독립 검토·하네스와 PR CI는 [PR #429 완료 기록](https://github.com/Len-Yoon/personal-server/pull/429#issuecomment-6280196640)을 따름. 이 문서의 CI는 문서 계약 검증이며 운영 코드 전체 재검증으로 표현하지 않음.

## 5. 복구 기준

새 기준 기록 생성 후 구 runner·collector로 원복하지 않음. 구 collector는 기준 버전을 제거할 수 있음. 수집기 장애 시 해당 collector CronJob만 임시 suspend하여 새 Job 생성을 막고 활성 Job·실행 중 Pod 종료를 확인한 뒤 버전 보존 호환 writer로 복구함. RBAC 원복은 이번 추가 규칙만 UID·현재 규칙을 전제로 제거함. 전체 K3s 재시작·다른 일정 변경·운영 데이터 덮어쓰기를 수행하지 않음. 이번 적용에서는 복구 조치를 사용할 실패가 발생하지 않음.

## 6. 확인 필요 사항

- 다음 정기 수집: **2026-10-21 02:15 KST**. 기존 오늘 행을 덮어쓰지 않았으므로 신규 기준 행의 실제 저장·30일 보존·기존 기준 행 버전 보존은 이 실행 후 확인 필요함.
- 현재 감사 SLO는 과거 15분 기준 30일이며 정상 0일·관측 불가 1일을 그대로 보고함. 30일 시간 기반 가용성·에러 버짓이나 SLO 전체 통과를 뜻하지 않음.
- 신규 기준이 섞이면 혼합 기준임을 표시하며 동일 기준 30일 통과로 처리하지 않음.
