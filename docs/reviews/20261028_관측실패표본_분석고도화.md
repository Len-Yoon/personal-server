## 2. 핵심 요약

`slo-sample-summary.py --episodes`가 실패·미관측의 연속 평가 표본을 상태·판정 사유별로 출력함. 기본 실행은 기존 JSON과 완전히 같은 결과를 유지하며 archive 수집·검증의 기존 호출은 새 필드를 받지 않음.

기존에 확인한 실제 실패4표본은 한국시간10/27 14:30:15~14:30:30 및10/28 02:31:15~02:31:30의 두 구간으로 확인됨. 후속 조사에서 각각 승인된 Portal Recreate 배포와 정기 백업 후 writer 복귀의 준비 공백으로 연결 확인함. 각 구간2평가점은 같은 원본 scrape를 재사용함. 원시 실패4를 제거하지 않으며 표본 간격과 개수로 정확한 장애 시간을 계산하지 않음.

### 3.2. 실제 원본 대조

기존 `slo-observation-health` Pod의 읽기 전용 `/archive` 마운트에서 완료 UTC 일자2026-10-27 파일을 읽음. 기존 archive 검증기로 전체 canonical payload SHA와 저장된 SHA를 대조하고, 이전 수집 기록의 `512fae5c559eb3d6ce12f1c9a9ccb9f5e8205abf2a9a223083d8226c94446823`와 일치함을 확인함. replica 질의4개만 선택하고 허용된 label만 유지한 로컬 분석 입력의 SHA는 `0c84c6080b0849ac2cf46d88dd7477222075602d5e46d7b4dc1a722d90325666`임. 원본 날짜·SHA 확인을 생략한 임의 JSON을 실제 자료로 사용하지 않음.

| 첫·마지막 평가 표본 UTC | 한국시간 | 표본 수 | 판정 근거 | 비고 |
|---|---|---:|---|---|
| 2026-10-27 05:30:15~05:30:30 | 2026-10-27 14:30:15~14:30:30 | 2 | 신선한 available0·desired1 | 직전05:30:00·직후05:30:45는 available1 |
| 2026-10-27 17:31:15~17:31:30 | 2026-10-28 02:31:15~02:31:30 | 2 | 신선한 available0·desired1 | 직전17:31:00·직후17:31:45는 available1 |

전체5,760표본 중 정상5,756·실패4·미관측0, desired0 후보0으로 기존 요약과 일치함. 후보0은 계획 작업이 없었다는 증거가 아님. 후속3.4절에서 배포·백업과 연결했으며 두 평가점의 원본 scrape 시각이 같음을 확인함. 평가 표본 수를 독립 장애 횟수로 해석하지 않음.

최초 읽기 조회는 마운트 경로를 `/archive/observations`로 가정한 전제 검사에서 중단됐으며 실제 manifest의 `/archive` 읽기 전용 마운트를 대조한 한 번의 보완 후 성공함. 파일 쓰기·잠금·Pod 생성·재시작은 수행하지 않음.

### 3.4. 실패4표본의 원인 후속 대조

| 실패 평가 구간·한국시간 | 확인된 원인 | 직접 연결한 근거 | 비고 |
|---|---|---|---|
| 10/27 14:30:15~30, 2표본 | 승인된 Portal 이미지 교체의 Recreate 전환 | 새 ReplicaSet `portal-web-757fb76b56` 생성14:30:04, 이미지 digest150aeb918c…가 기존 배포 기록과 일치. 이전 RS의 요구 수1→0과 새 RS/Pod 생성, UTC05:30:16에 저장된 배포 결과의 Ready1을 연결함 | 파일명에 UTC를 기록하는 실행기와 원본 결과를 대조함. 배포 전략은 Recreate·replicas1 |
| 10/28 02:31:15~30, 2표본 | 정기 Portal 백업의 writer 정지 후 재기동·준비 공백 | 같은 날짜 Job UID `8092283b-aaf2-4816-8b49-3662a749e20e`의 로그에 writer_pause02:30:34.616·snapshot36.941·restore_validation56.148. 같은 RS의 복귀 Pod 생성02:30:57·Ready02:31:09·백업PASS02:31:18.869·Job 성공 종료02:31:21을 연결함 | 새 버전 배포가 아닌 동일 RS의 Pod 재생성. 전체 백업 순서도 Portal 포함4단계 passed |

원본 scrape는 각각 `2026-10-27T05:30:04.368Z`·`2026-10-27T17:31:04.368Z`에 available0을 관측함. 15초 평가 grid가 같은 값을 두 번 사용하여 총4개 평가 표본이 남음. 백업 후 Pod는02:31:09에 Ready였지만 다음 정상 scrape02:31:34.368 이전의 평가15·30초에는 앞선0이 사용됨. 따라서 이 두 평가 시각에 실제 Pod가 계속 미준비였다고 해석하지 않음.

백업 직전 scrape02:30:34.368은 writer_pause 로그34.616보다 앞섰고, 다음 scrape02:31:04.368 때는 이미 desired1로 복귀한 뒤였음. desired0 정지 구간을 수집이 놓친 것이므로 후보0만으로 계획 정지를 부정하지 않음. 백업 스크립트의 writer_pause→scale0·검증 후 원래 replica 복귀 경로와 같은 날짜 로그·Pod 신원을 함께 대조함.

두 조회 창의 관측된 컨테이너 restart counter는0이고 OOMKilled 시계열은 없었음. 이를 모든 오류의 부재로 확대하지 않음. 확인된 원인은 계획 작업에 따른 준비 공백이며, 당시 사용자 요청의 실패 수와 정확한 중단 시간은 별도 자료 없이는 산정하지 않음. 계획된 작업도 원시 가용성 실패 표본에서 제외하거나 성공으로 재작성하지 않음.

후속 원본은 `dist/20261028_실패4표본_원인조사/`에 보존함. 두5분 창의 허용 지표·Job 소유 UID·필터링한 단계 로그·현재 RS/Pod 신원과 Ready 전환 시각·기존 배포 결과의 SHA를 구분함. Secret·환경 설정·원시 로그 전체·계정·내부 주소를 보존하지 않음.

## 4. 검토 결과

root가 구현·회귀·원본 읽기·자기 검증·문서를 담당함. 구현 미참여 `reliability447_final_review`가 계산·분류·출력 비공개·호출 호환·실제 원본/문서·잔여 위험을 독립 검토함. 공용 archive 소비 계약과 운영 관측 해석의 실패 비용을 고려해 `gpt-6.1-sol` high 검토자1명을 두며, 같은 공용 함수를 다루므로 병렬 구현자는 추가하지 않음. 같은 파일 동시 수정 없음. 최종 검토 대상과 PASS는 실제 diff·작성 이력에 고정된 receipt 및 PR 기록에서 확인함.

이전 경보 시험의 복구6개도 사용자가 도착·문구 정상을 명시 확인하여 기존 기록을 발생·복구12개 실제 수신으로 보완함. 해당 확인을 새 시험 실행이나 자연 장애 검증으로 확대하지 않음.

3.4절 후속 원인 조사는 주 담당1명이 읽기 전용으로 수행하고 근거·시각·소유 관계를 자기 검증함. 실행 코드·운영 설정 변경 없는 조사·문서 보완이므로 하위 에이전트를 사용하지 않았으며 해당 후속 결과를 이전 기능의 독립 검토 PASS에 합산하지 않음.
