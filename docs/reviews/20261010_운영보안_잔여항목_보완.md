### 외부 송신 제한의 별도 설계·경계

준비 중인 수신 정책은 일반 Pod의 직접 접속을 제한하도록 설계하며 송신은 유지함. Caddy 경유 네 앱에 제어된 health 요청 48/48 성공과 앱 측 노드 인터페이스 source를 관측하여, 노드 경유 요청은 수신 정책의 차단 범위 밖임을 확인함. 이를 Caddy 전용 접근 제어나 전체 네트워크 격리로 표현하지 않음.

현재 CNI에 FQDN 정책 CRD가 없고 기존 forward/egress proxy·관련 proxy 환경 설정도 없음. Book 외부 검색은 `aiohttp.ClientSession(trust_env=False)`와 c-ares를 사용하므로 proxy 환경 변수만 추가하는 방식은 충분하지 않음. 유지 가능한 후속 후보는 별도 HTTP CONNECT proxy와 앱별 허용 FQDN·고정 TCP443 정책임. 각 연결마다 DNS 해석 후 모든 주소가 public인지 검사하고 검증한 IP에 연결하여 DNS rebinding을 방지하며, 사설·노드·loopback·link-local·metadata 목적지는 거부해야 함. 앱 송신은 DNS·확인된 내부 peer·proxy로 한정하고 proxy만 외부 송신을 허용하는 구조임.

이 후보는 신규 네트워크 서비스·Book 클라이언트 명시 proxy 지원·다른 클라이언트 및 `NO_PROXY`·Drive/rclone/OAuth 백업 통신까지 바꾸므로 이번 일반 Pod 수신 제한과 분리함. 프록시 장애 시 앱/백업 영향, 우회 차단, SSRF·redirect·DNS rebinding·TLS CONNECT·외부 provider 및 백업 복원 계약을 검증하고 정확한 새 대상과 순서를 준비한 뒤 운영 승인 범위를 확인해야 함. 이번 작업에서 단발 DNS-IP 목록·넓은 CIDR로 이를 대신하지 않음.

### CNI 증거의 cluster UID 결합 보완

최초 격리 enforcement 성공은 같은 N100 K3s 실행 경로와 운영 spec 보존으로 확인했지만 당시 cluster UID 전후 기록은 없었음. 신규 정책 생성기의 cluster-bound 증거 요구를 충족하기 위해 전문 검토 후 UID 전후 대조만 추가한 같은 검사를 2026-10-10 20:33~20:34에 한 번 더 수행함. HTTP/DNS baseline·차단·선택 허용·정리 PASS, cluster UID 전후 동일, 운영 네 Deployment spec 불변·임시 namespace 부재·운영 정책0을 확인함. 최초 성공 기록에 당시 측정하지 않은 UID 증거를 소급하지 않음.
