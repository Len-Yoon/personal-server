## 2. 핵심 요약

계획 정지의 설명과 원시 SLO 판정을 분리함. 백업의 성공 결과는 계획 정지 후 복귀가 검증된 완료 시각 기준으로 설명하며, 감사의 과거 SLO 집계는 현재 상태 점검과 구분함. SLO 일회성 알림은 실제 관측 표본과 성공한 Portal 백업 Job의 소유·시간·실행 명세가 맞을 때만 계획 정지 구간 일치로 설명함.

기존 `portal_ready=failed`, 기준 버전, 정상 일수와 과거 결과는 변경하지 않음. 새 예약·주기·알림 횟수·Secret·권한·ConfigMap 스키마는 추가하지 않음. Alertmanager의 실제 `PortalUnavailable` 알림은 억제하거나 계획 정지로 재분류하지 않음.

## 3. 입력·표시·보존 경계

| 경로 | 근거 | 표시·제한 |
|---|---|---|
| Portal 백업 성공 | status/stage가 completed/completed 또는 unchanged/unchanged | 계획 정지 후 가용 상태 복귀 확인, 백업 완료 시각 기준 |
| 모순된 백업 성공 | success status와 실패 stage의 조합 | 성공·복귀 통과로 표시하지 않으며 전달 원장도 갱신하지 않음 |
| Portal 백업 실패 | 원격 복원 검증 실패 또는 Portal 복귀 확인 실패 stage | 실패 종류를 분리하며 원격 복원 실패를 현재 Portal 장애로 단정하지 않음 |
| 백업 정리 실패 | 새 백업·복원 검증과 오래된 백업 정리 결과 | 이미 성공한 백업을 실패로 덮어쓰지 않음 |
| 감사 | 기존 health_audit와 과거 SLO 집계 | 과거 관측에 계획 정지가 포함될 수 있음을 표시. 개별 원인 근거 없이 계획 정지로 확정하지 않음 |
| SLO 검증 | 수집 시각에 고정한 실제 Prometheus 24시간 matrix와 Kubernetes 읽기 | 계획 백업 구간 일치·설명되지 않는 무가용·원인 확인 필요를 구분 |

## 4. SLO 보조 진단과 테스트 기준

`available`·`desired` 실제 단일 시계열의 원본 표본을 사용함. 양끝과 표본 간격의 관측 공백은 90초 이내여야 하며 두 메트릭의 표본 시각이 같아야 함. 90초 이내 관측 사이에 짧은 장애가 없었다는 보장은 하지 않음. 복수 KSM 시계열·누락·오래된 기록·재생성된 Deployment/CronJob·원시 판정과의 모순은 원인 확인 필요로 처리함.

성공 백업 Job은 현재 CronJob UID의 단일 controller owner, 동일 Pod spec, Complete·succeeded 1·실패/활성 0, 수집 전 24시간 내 시작·종료가 필요함. 삭제되거나 증거가 부족한 과거 Job을 이름만으로 대체하지 않음.

연속 무가용 구간의 첫 표본에서 desired 0·available 0이 함께 관측되어야 계획 정지 시작 근거로 인정함. 이후 복귀 대기의 desired 1·available 0은 같은 연속 구간으로 취급할 수 있으나 첫 available 1 표본에서 종료함. 정상 복귀 후 다시 발생한 무가용을 같은 백업에 포함하지 않으며 중복된 백업 시간 창도 모호한 증거로 처리함. 일치 표시는 인과 관계 확정이나 SLO 예외 처리로 확대하지 않음.

추가 진단은 고정된 읽기 5회·각 8초·응답 2MB·시계열 10,000표본으로 제한함. 확인 기한 마지막 45초 안에는 진단을 생략하여 기존 정리·통지 여유를 보존함. 진단 예외는 원인 확인 필요로 수렴하고 기존 검증 PASS·자기 정리·1회 전송을 실패시키지 않음. 결과에는 작은 분류·조회 시각·표본 수만 저장하며 원시 라벨·주소·오류 본문은 포함하지 않음. 복구 뒤 재사용되는 설명에도 조회 시각을 표시함.

정상 백업·복귀 중 전이·복귀 후 재발·백업 전 장애·실패/삭제/외부 소유 Job·중복 시간 창·표본 누락/NaN/시각 불일치·원본 모순·현재 가용성 부족·조회 실패·기한 임박을 회귀 검사함. relay의 성공 모순·실패 종류·과거 집계/현재 점검·기존 중복 전송 방지도 검사함. 최종 실행 수와 CI 결과는 해당 PR에 기록함.

| 역할 | 담당·모델 | 범위·선택 이유 |

| relay 구현 | maintenance_relay_implementation, gpt-6.1-sol medium | 독립적인 기존 메시지·테스트 2파일, 일반 기능 구현 |

같은 파일을 동시에 수정하지 않음. 구현자가 실행한 테스트는 자기 검증으로 기록하고 최종 독립 검토는 실제 diff·관련 원본·검사 결과를 직접 대조함.

## 6. 운영 적용·복구 경계

저장소 병합은 운영 적용과 별도임. 정확한 CI 커밋을 N100에 fast-forward하고 relay 이미지만 반입·교체하는 범위가 예상되며, Secret·PVC·백업/수집 일정·감사 이미지·권한은 보존함. 완료된 4df 지문 실행 코드·결과 JSON·전송 원장을 변경하거나 일회성 예약을 다시 설치하지 않음. 새 SLO 도구는 이후 별도 승인된 검증 작업에 사용함.

적용 직전에 이미지 보안 검사·대상 지문·검증 결과·실행 순서를 제시하고 한 번 승인받음. 승인 범위 밖 운영 전송은 수행하지 않음. 기존 원장·offset·중복 방지 상태를 보존하고 필요 시 직전 relay 이미지로 되돌림. 전후 Portal·대상 relay health 및 독립 운영 검토로 확인함.

## 7. 후속 조치

테스트·PR CI·독립 검토·자동배포 제외를 확인한 뒤 병합하고 main 검사·브랜치 정리를 완료함. 최종 운영 적용은 별도 승인 직전까지 준비하며, 승인 전 변경된 Telegram 메시지가 이미 운영 중인 것으로 보고하지 않음. 계획 정지를 30일 SLO에 포함할지에 대한 정책은 이번 표시 변경으로 확정하지 않음.
