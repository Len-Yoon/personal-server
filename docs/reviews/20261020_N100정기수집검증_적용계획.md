## 2. 핵심 요약

N100의 기존 systemd 사용자 관리자는 running, Linger는 yes로 읽기 확인됨. 날짜를 고정한 사용자 timer/service를 추가하여 맥·Codex 실행 없이 검증함. 새 sudo·Secret·RBAC·컨테이너 이미지나 기존 수집 일정 변경은 필요하지 않음. 결과 통지는 기존 relay 컨테이너 안에서 등록된 자격 파일을 메모리로만 읽는 고정 명령을 사용함.

검증 결과 JSON과 지문별 실행 코드 1개는 N100에 보존함. 실행 코드는 Linux home의 `.local/lib/personal-server/slo-followup-verification/<SHA256>.py`에 0600으로 설치함. 기존 저장소가 있는 Windows 마운트는 파일 모드가 0777이므로, 저장소 권한을 바꾸거나 안전 검사를 완화하지 않고 별도 Linux 파일의 소유·권한·지문을 검증함. 임시 baseline·schema·예약 파일·Persistent 타이머 스탬프는 정리함. 알림 API 응답이 불명확하면 중복 전송을 막기 위해 재전송하지 않고 `unconfirmed`로 기록함. API 전송 수락과 사용자의 실제 수신은 구분함.

## 3. 적용 범위와 실행 순서

| 단계 | 실행 내용 | 보존·제한 사항 |
|---:|---|---|
| 1 | PR·main CI 및 독립 검토를 통과한 정확 커밋을 N100에 fast-forward | tracked clean·기존 사용자 파일·hook 확인, 강제 reset 없음 |
| 2 | 기존 CronJob·증적·relay UID/spec 및 30일 원본의 새 snapshot 확보 | 검토한 원본 해시와 다르면 설치 차단 |
| 3 | 지문별 Linux 실행 파일 1개·전용 사용자 unit 2개·전용 작업 경로 설치 | 기존 systemd·K3s·백업·수집 예약 수정 없음 |
| 4 | 서비스의 부팅 재개 경로와 날짜 고정 timer 활성화 | 조기 실행 조건으로 02:20 전 검증·알림 금지, 최대 3회 복구 |
| 5 | 실제 NextElapse·활성/enable·실행 경로·source 지문을 별도 검토자가 확인 | 맥 종료와 무관한 실행 주체 확인 |
| 6 | 기존 맥 임시 예약 `slo` 삭제 | N100 활성 확인 후에만 교체하여 감시 공백 방지 |
| 7 | 10/21 정기 Job·Pod·ConfigMap을 읽기 검증 | 수동 수집·Kubernetes 객체 변경·정기 Job 삭제 금지 |
| 8 | 자기 예약·임시 파일 정리, 결과를 기존 relay를 통해 Telegram 1회 전송 | 결과 증거 보존, 비밀값 호스트 반출·파일/환경 변수 복제 없음 |

위 범위는 2026-10-20 별도 사용자 승인 후 적용됐고, 10/21 실행까지 완료됨. 아래 기준은 당시 적용·검증 경계이며 완료된 승인을 새 설치·재실행에 재사용하지 않음. 병합의 자동배포 분류가 제외임을 확인했으며 실제 설치와 구분함.

## 4. 검증 기준

| 항목 | 통과 기준 | 비고 |
|---|---|---|
| 실행 주체 | N100 기존 사용자 systemd, Linger=yes | 맥 앱·새 자격 증명 불필요 |
| 예약 | 2026-10-20 17:20 UTC = 10/21 02:20 KST, 특정 날짜 1회 | Persistent로 실행 전 놓친 예약 보완 |
| CronJob | 기존 UID·전체 spec 동일 | `15 2 * * *`, Asia/Seoul, suspend=false, Forbid 보존 |
| 실제 Job | controller 소유관계와 scheduled-timestamp가 10/21 02:15 KST에 일치 | 이름·수동 Job·과거 성공으로 대체하지 않음 |
| 실제 실행 | Complete, succeeded=1, failed/active=0, Pod 종료 0·restart 0·정확 imageID | 기준 이미지 `0dc15788788a8500de9f6906543b8a6f1b61f598c26598af19f35b667a57c4a3` |
| 신규 행 | 2026-10-21 한 개·`freshness-1800-v1`, collected_at이 실제 실행 시간 안 | 시간대 인식 비교 |
| 기존 행 | 9/22~10/20의 29개 모든 필드 동일 | 9/21 한 건만 30일 보관 만료로 정상 제외 |
| 판정 | 수집 성공과 Portal/Crawler 등의 측정 실패를 구분 | 과거 실패를 PASS로 수정하지 않음 |
| 보호 | Kubernetes는 GET만, 통지 단계는 기존 relay의 고정 exec 명령만 | collector/main/update_configmap·Secret GET 금지 |
| 정리 | 자기 unit·baseline/schema·Persistent stamp 제거, 다른 파일 보존 | 결과 JSON·지문별 실행 코드만 보존 |

사전 읽기 시험에서 실제 정기 Job의 scheduled-timestamp annotation과 `@sha256` imageID 형식을 확인함. 오늘 Job은 새 이미지 배포 전 실행이므로 이전 이미지이며, 현재 CronJob과 이미지 외 Pod spec은 동일함. 이를 내일 새 이미지 실행 성공으로 확대하지 않음.

## 5. 중단·복구·알림 계획

검증·정리·전송 단계를 결과 파일에 기록하고 단독 실행 잠금으로 중복 실행을 막음. 검증 도중 중단되면 기한 안에서 재개하고, 기한이 지났으면 확인 불가로 정리·통지함. 부분 삭제 뒤에도 남은 자기 파일만 해시와 소유자를 확인해 정리함. 실행 소스는 지문을 확인하며 검토 후 코드가 달라지면 차단함.

전송은 `attempting` 저장 뒤 한 번만 시도함. 이 단계 이후 중단·응답 유실이 있으면 재전송하지 않음. 새 Secret을 복제하거나 분기 감사의 상태·전달 원장을 임시 통지 수단으로 오염시키지 않음. relay 또는 Telegram에 접근할 수 없으면 N100 결과 JSON과 journal에 확인 불가 상태를 보존함.

예약 활성화 직전 최소 120초 여유를 다시 확인함. 설치 실패 시 이번 timer를 해제하고 서비스가 inactive/failed로 확인될 때만 이번 소유 파일을 정리함. 활성화 응답이 유실되거나 실행 중·상태 불명이면 파일을 보존하고 `installation_state_uncertain`으로 보고함. 재사용한 기존 지문별 실행 파일은 원복 시에도 보존함. 기존 수집기 이미지·기준·기록·스케줄·서비스는 원복하거나 중지하지 않음. 예약 취소도 동일한 소유·해시 경계를 따름. N100 자체가 꺼져 있는 동안 실행·전송할 수는 없으며, 재가동 시 기한을 판단함.

검증 도중의 프로세스 중단은 단계별 기록과 최대 3회 재시도로 보완함. 최종 자기 service 해제·파일 삭제부터 통지 종료까지의 짧은 구간에 N100 전원까지 끊기면 자동 부팅 재개를 보장하지 못함. 이 경우 보존한 실행 코드·결과 JSON의 지문을 확인하여 수동 재개하며, `attempting` 이후는 중복 전송하지 않음. 맥 종료와 N100 자체 정전은 구분함.

## 6. 검토 결과·확인 필요 사항

| 역할 | 담당 | 구분 |
|---|---|---|
| 주 담당 | root | 최초 검증 로직·테스트·문서·통합, 자기 검증 |
| 복구 구현 | n100_slo_recovery_implementation | gpt-6.1-sol medium, 단계 복구·systemd 3파일 전담, 자기 검증 |
| 운영·보안 독립 검토 | n100_slo_verifier_review | gpt-6.1-sol high, 대상 작성·수정 미참여 |

동시에 같은 파일을 수정하지 않음. 최초 독립 검토의 중단 후 재개 불가·고정 임시 파일 충돌·부분 정리 재개 문제를 보완하고 다시 검토함. 최종 대상 커밋·자기 검증·독립 검토·CI 결과는 PR 완료 기록에 고정함.

사용자 승인 후 실제 systemd 시험의 예약 발화·조건 차단·Persistent stamp 정리·종료 후 GC를 확인함. 10/21 정기 검증의 실제 결과와 사용자 수신도 확인됨. 모의 검사·실제 설치·실제 실행·수신 증거는 [완료 결과](20261021_N100검증완료_Portal판정_확인결과.md)에서 구분함.

승인 범위에는 실수집·Telegram 전송 없이 별도 시험용 사용자 service/timer를 1회 생성하여 조기 실행 차단·Persistent stamp 제거·unit 해제와 삭제를 검증한 뒤 즉시 정리하는 시험을 포함함. 시험 이름은 실제 예약과 분리하고 해당 시험이 만든 파일만 정리함. 본 작업은 예정 시각 전 실제 검증 service를 실행하거나 수집기를 수동 재실행하지 않음.

## 7. 후속 조치

구현·검사·독립 검토·PR/main 검증 및 최종 운영 승인을 거쳐 설치를 완료함. 설치 전후 Portal 외부 health를 10초 간격 3회 확인하고 N100 활성 증거를 독립 검토함. 10/21 정기 실행·신규 기록·29행 보존·자기 예약/파일 정리·Telegram 실제 수신이 확인되어 일회성 후속 작업을 종료함. 결과 JSON·지문별 검증 코드는 보존하며 새 예약은 만들지 않음.

Persistent stamp 정리는 [systemd 공식 timer 문서](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html#Persistent=)의 `systemctl clean --what=state` 절차를 따름.
