## 핵심 요약

뉴스 freshness의 24시간 조회가 복수 시계열을 반환하여 단일 결과 계약에서 실패함. 바깥 `min` 집계를 추가한 수정안은 실제 Prometheus에서 단일 결과 반환을 확인했으며, 로컬 관련 테스트 24건을 통과함. 운영 수집기는 아직 변경하지 않음.

## 원인 판단

`slo-daily-evidence.py:329-332`는 Prometheus·공개 health·Portal ready·Crawler freshness 중 하나라도 `unobservable`이면 ConfigMap 기록 후 exit 1로 종료함. CronJob은 `backoffLimit: 0`이므로 collector의 첫 exit 1이 바로 `BackoffLimitExceeded`로 나타남.

**직접 원인은 `crawler_freshness` PromQL이 단일 scalar 대신 3개 series를 반환한 것임.** `_prometheus_scalar`은 결과가 정확히 1개가 아니면 `ValueError`를 발생시킴(`slo-daily-evidence.py:194-213`). `status_for`는 이를 `crawler_freshness=unobservable`과 `missing`으로 전환함(`:284-292`). `BackoffLimitExceeded` 자체는 Kubernetes 재시도 정책 결과임.

승인된 원격 읽기 전용 ConfigMap whitelist 결과에서 2026-09-19~21은 모두 `missing=['crawler_freshness']`였음. 각 원시 crawler 지표(`initialized`, `last_success`, `consecutive_failures`)의 현재 Prometheus 결과는 각 1개인데, 24시간 `min_over_time` freshness 표현식은 3개였음. 이는 24시간 subquery 구간에 복수의 과거 label series가 존재함을 뜻하며, 재배포·Pod/instance label 교체·counter 재생성과 같은 구간 내 series 교체가 가능한 원인임. 정확한 label 값은 내부 정보 비노출 원칙에 따라 조회·출력하지 않았음.

현재 read probe에서는 crawler Deployment desired/ready/available=1/1/1, Service 존재, ready Endpoint 존재, Pod Ready=True, Prometheus Pod Ready=True였음. 따라서 현재 가용성 문제와 과거 24시간 증적 query의 다중 series 문제를 구분해야 함. `public_health`와 `portal_ready`는 `failed`로 기록됐으나 `missing`에는 없었으며, 문서 계약상 관측된 비정상 상태는 Job 실패가 아닌 evidence 상태임.

## 최소 수정·검증 제안

1. `_QUERY_CRAWLER_FRESHNESS`를 `min(min_over_time(...[24h:]))`로 최소 변경해 label series 전체의 최솟값을 단일 scalar로 집계함. 여러 series 중 하나라도 freshness 조건이 거짓이면 `0`이므로 fail-closed 의미는 유지됨. series가 전혀 없거나 Prometheus 응답 오류이면 결과가 단일 scalar가 아니어서 기존처럼 `unobservable`·Job 실패가 유지됨.
2. 단위 테스트에 (a) query 문자열의 바깥 `min` 집계, (b) 3개 historical crawler series가 있을 때 최솟값 `0`으로 단일 scalar가 되는 Prometheus 응답, (c) series 0개·응답 오류는 여전히 `crawler_freshness=unobservable` 및 `missing`임을 추가 필요함.
3. 코드 반영 뒤 승인된 수동 Job 1회에서 `missing` 상태 분류와 Job 종료 상태만 whitelist 조회해 확인 필요함. 현재 이미 수집된 `public_health`·`portal_ready`의 `failed`는 관측 실패와 구분해 evidence로 보존함.

원인과 최소 수정 방향은 확정됨. 다만 운영 적용·CronJob 재실행은 별도 승인 필요함.

## 확인 필요 사항

현재 서비스 가용성과 24시간 내 과거 장애 기록은 구분함. 수정 후에도 증적의 `failed`는 실제 관측값으로 유지되며, 누락·잘못된 응답은 `unobservable`로 실패 처리됨. 과거 시계열을 만든 개별 배포·label 변경의 정확한 이력은 이번 조사에서 확정하지 않음.

## 후속 조치

수집기 소스와 관련 회귀를 저장소에 반영하고 새 collector 이미지를 빌드·반입한 뒤, 기존 스케줄·권한·증적을 유지하며 이미지 한 항목만 교체하고 수동 Job 1회로 실제 증적 수집을 검증하는 절차를 제안함. 이번 승인은 조사였으므로 이 운영 변경·Job 실행은 추가 확인 전 수행하지 않음.
