## 2. 핵심 요약

기존 legacy profile·거절·소진된 현장 재시도는 유지함. 새 profile은 앱·worker를 비관리 신원으로 실행하고 DB 서버가 직접 SQL까지 차단하며, Windows는 전용 관리 경계를 보유한 고정 VM만 실시간 관측함. 현재 원본의 앱 내부 lease 검사·직접 DML 허용과 단일 shared blob 파일은 새 profile의 강제 소유권 근거가 될 수 없음.

전용 `enforced-vm-v1` 설치의 추가 권한 변경은 아래 범위로 제한함. 기존 N100·기존 실험 자원에는 적용하지 않음.

실제 수용 기록은 각 기록의 고정 소스 해시에 적용함. 최종 권한 검사 파일의 끝 빈줄 제거는 [Python AST 동일성](evidence/20261109_ha_privilege_format_equivalence.json)으로 별도 대조했으며, 이전 실행의 바이트 해시를 최신 파일 해시로 바꾸지 않음.

| 전체 2초 | 실제 Windows 전후 조회와 DB barrier/WAL/peer 검증 전체를 동일 실행에서 측정함 | 개별 adapter 단위 시험으로 수용하지 않음 |
| 최초 운영 등록 | 원본 7앱 writer·재생성 주체의 동결/폐기, 기존 제공자 자격·캐시의 회수 또는 이전 실행 경계의 지속적 fencing, 마지막 일관 snapshot을 확인함 | 설치 권한 발급·새 writer open 전의 신뢰된 등록 선행 조건임. 이 오프라인 도구가 실제 운영 주체를 조회하거나 기존 자격을 회수한 것은 아님 |
| 기존 앞단 연결 | 실제 앞단의 upstream 주소·7개 내부 Host·동일 TLS SNI·서버 검증·클라이언트 인증서 결합을 확인함 | `review.json`에 필수 계약을 출력함. 기존 공개 Host를 그대로 전달하면 거절되며, 현재 운영 앞단 설정은 변경하지 않음 |
| 외부 writer | 서비스 SQL 역할과 실제 background worker·외부 자격 증명·송신 경계를 결합함 | 캐시한 토큰·진행 중 요청·응답 유실은 DB lease로 취소되지 않음 |
| 복원 용량 | 현재 archive 상한 128MiB와 blob 저장 상한 1GiB의 차이를 실제 운영 데이터로 대조함 | archive의 blob 참조 중복까지 포함한 최대 복원 수용은 미검증 |
| 만료 transaction | 새 statement는 만료 시 거절하고 이미 승인된 transaction은 세대 공유 잠금을 완료까지 보유함 | 모든 commit이 만료 전에 끝난다는 보장은 아님. 세대 잠금은 유지하고 불필요한 control 행 공유 잠금은 제거함. 실제 PG에서 admitted write와 동일 권한 갱신의 공존을 검증함 |
| Portal 임시 공간 | 500MiB 일괄 archive·32MiB snapshot·업로드 임시 공간을 위해 Portal에만 640MiB on-demand tmpfs를 구성함 | 실제 점유 예약이 아니며 동시 부하·여유 공간·메모리 피크는 대상 호스트 수용 필요 |
| 신뢰 경계 | EA/터미널의 관리자 권한 여부와 VM·DB 관리자 권한을 확인함 | 관리자 신원을 비신뢰 writer로 격리했다고 주장하지 않음 |

## 7. 후속 조치

현재 제어기는 명시적인 initialize/advance/serve 전환과 고정 plan/세대를 대상으로 함. 임의의 미래 장애마다 자동으로 새 세대·자격·앱 설정을 발급하는 무제한 자동 failover 수용으로 확대하지 않음.

맥 구현·직접 SQL/파일/7앱 이전·복원·실패 시험·독립 검토·배포 제외 병합과 실제 적용 번들을 준비함. guest layout은 자동 활성화하지 않으며 각 앱 readiness·현재 DB lease·미해결 외부 효과·전체 2초를 대조한 뒤에만 route/writer 전환을 허용함. fencing한 이전 VM은 계속 Off로 보존하고, 동기 복제 peer는 새로 구성한 standby여야 함. 새 쓰기 이후에는 과거 V1로의 무손실 자동 복귀를 보장하지 않으며 forward recovery와 불확실 효과 대사를 수행함. Hyper-V 구성요소 활성화와 별도 승인된 정상 재부팅 1회는 완료함. 추가 실제 적용은 5.4절에 기록한 이번 이중화의 명시적 위임 범위에서 독립 운영 검토·전후 보호 점검을 거쳐 수행하며, 미수용 항목을 완료로 처리하지 않음. 이번 초기 부팅 검사 실패를 현재 7앱 복구 성공으로 덮지 않으며 전체 coldboot·2초 HA·거래 기능 수용과 구분함.
