## 2. 핵심 요약

Portal 로그 디렉터리 조회 수정과 system-agent의 손상 UTF-8 백업 증적 처리 수정을 운영 이미지에 반영함. Portal 백업 이미지에도 동일 검증기가 포함되므로 해당 CronJob의 init/main 이미지와 순차 실행 도구의 pin을 함께 교체하는 후속 적용을 준비함. 감사 이미지의 보안 차단은 해결된 것으로 처리하지 않음.

Portal 백업 후보는 원래 Dockerfile과 정확한 Git 소스로 제작함. Trivy OS·Python HIGH/CRITICAL 0건이며, OCI→Docker 포맷 변환은 config bytes와 모든 RootFS diff ID 보존을 대조함. 기존 실행 이미지를 외부로 내보내는 동작은 자동 승인 검토가 거절하여 수행하지 않음.

system-agent 최초 교체에서 브리지 주소 환경 전달이 누락되어 loopback/wildcard 포트 충돌이 발생함. override를 이전 이미지로 복원하고 정상 서비스의 기존 바인딩과 기본 Docker bridge gateway를 메모리에서 대조하여 복구함. 프로세스 강제 종료·daemon/network 재시작 없이 복구 후 독립 health·metrics·Portal 연결 검증을 수행함. 이후 교체는 동일 gateway, 현재 정상 구성의 환경 의미, HostConfig, mount, network, 여섯 Compose 파일과 override UID/GID/mode 보존을 강제함.

## 4. 검토 결과

운영 독립 검토에서 실제 두 서비스의 이미지·소스, Portal Ready 및 재시작 0회, system-agent healthy·필수 endpoint·Portal bridge, Prometheus 수집 성공과 최신 표본을 직접 확인함. Portal 외부 health는 2026-10-19 21:51에 10초 간격 3회 HTTP 200임. Deployment 16개(Portal 이미지 제외), StatefulSet 2개, CronJob 8개, PVC 8개, Secret 32개의 원본 UID/지문과 다른 Docker 실행 주체 및 기존 미추적 파일 두 개의 지문이 보존됨. 서비스 임시 파일과 시험 컨테이너 잔존은 0건임. 이 독립 PASS는 Portal 백업 CronJob 후속 적용과 감사 이미지 차단을 포함하지 않음.

구현자 시험은 자기 검증으로 분류함. 독립 운영 검토는 실제 SSH/Kubernetes/Docker 상태와 연결을 직접 확인하며, 엄격 코드 receipt와 별도 증거임. 예비 코드 검토자는 미지원 읽기 명령으로 하네스의 잠재 작성자 분류 가능성이 있어 최종 receipt 담당에서 제외하고 순수 읽기 검토자를 재배정함. 모델 선택은 운영·공급망·복구 경계의 높은 실패 비용을 기준으로 함.

저장소 검사는 서비스별 `.venv/<suite>/bin/python`과 `tests/run_ci_tests.py --fail-on-skip`, K8s shard 및 필수 promtool로 수행함. 최초 일반 Python/제한된 sandbox 실행의 루프백 포트 실패는 PASS로 계산하지 않으며 준비된 격리 환경과 로컬 루프백 허용 환경에서 재검증함. 최종 고정 커밋·전체 결과·receipt·PR/main CI 및 운영 후 결과는 해당 PR 완료 기록에서 대조함.

## 5. 확인 필요 사항

- 복구 이전 전체 Config는 지문만 보존했으므로 이전 환경값의 완전 동일성은 증명하지 못함. 단순 배열 순서 차이라고 단정하지 않음. 현재 정상 구성과 이후 이미지 교체 전후의 의미 보존·서비스 정상 증거와 구분함.
- 감사 작업 세 CronJob은 이전 이미지를 유지함. Debian 후보 HIGH 44건이 남아 보안 게이트 미통과이며, Alpine 전환 제안은 자동 승인 검토가 별도 승인을 요구하여 테스트·빌드·커밋·운영 적용하지 않음.
- 격리 검증은 백업 강제 실행 또는 다음 정기 백업 성공을 뜻하지 않음.

## 6. 잔여 적용 순서와 복구

Portal 백업 pin PR의 필수 CI·독립 검토·병합을 완료한 뒤 정확한 main 커밋을 기준으로 적용함. 기존 순차 백업 `local_lock()`을 전체 변경 구간에 유지하고, 정기 백업 시간 밖·활성 Job 없음·상태 lock 해제·네 CronJob 일치·기존 원본 보존을 확인함. Portal CronJob UID/resourceVersion/spec를 CAS 검사하고 이미지 두 필드만 변경한 뒤 같은 잠금 안에서 저장소를 fast-forward함. FF 오류 시 실제 HEAD와 spec를 조회하고 source가 이전 커밋이면 이미지 두 필드를 원복함. 전체 manifest 재적용·일정/중지 상태·다른 백업 이미지 변경은 수행하지 않음.

배포 도구의 네 이미지 동시 교체 전제에 맞추려고 무관한 Book/YouTube/Crawler 이미지를 바꾸지 않음. 최소 Portal 전용 실행의 안전 조건과 복구는 운영 독립 검토자가 별도 대조함. Secret/PVC/운영 데이터·소유권·scheduler·bootstrap·Caddy/Tunnel은 변경하지 않음.

## 7. 후속 조치

최종 독립 운영 검토에서 보호 대상 UID/지문, 외부 Portal health 10초 간격 3회, 실제 system-agent endpoint/Portal bridge/수집 상태, 전용 시험 파일·컨테이너 잔여 없음과 반입 임시 archive 정리를 확인함. 새 운영 이미지와 기존 원복 이미지는 유지하며, 지속 Compose override는 운영 설정이므로 삭제하지 않음. 감사 기반 전환은 새 승인 전 보류함.
