## 핵심 요약

Kubelet의 구형 구성 오류 지표는 미지원 안내로 표시하고 storage 오류율은 현재 histogram count의 fail-* 상태를 사용함. Multi-Cluster 표에는 실제 cluster 라벨을 바꾸지 않는 표시용 결합 키를 사용하고 단일 Cluster 링크의 빈 필터를 보존함. namespace 기본값은 실제 앱이 있는 personal-server로 선택하며, 다른 namespace·Pod·Workload 선택을 제한하지 않음.

미수집·버전 미지원·기간 내 표본 없음·수집/질의 오류를 구분하도록 상단에 이유를 항상 표시함. 결측을 정상값 0·성공률 100%로 바꾸지 않음. [PR #468](https://github.com/Len-Yoon/personal-server/pull/468)의 PR/main CI·보안 검사와 엄격 작성 이력 독립 검토를 통과한 main `8d6c996393041cdc942176159d1a53d4714e38cb`으로 N100을 동기화하고 기존 19개 data key를 CAS 적용함. 실제 화면·API와 기존 자동 관측 갱신을 분리한 최종 보호 검증 결과를 아래에 기록함.

### 소스·소유권과 유지 관리

- [대상 정책](../infra/k8s/monitoring/dashboard-data-states.json)은 정확한 ConfigMap 이름·data key·대시보드 UID·Helm 소유 여부·원본 및 검토한 적용 후 해시를 고정함. 이미 적용된 모양이어도 미검토 질의·패널 변경을 noop으로 수용하지 않음.
- [변환 모듈](../infra/k8s/tools/monitoring-dashboard-data-states.py)은 순수 변환·계획 생성·경로별 기대값만 제공함. CLI는 payload 대신 변경 수·공개 UID·해시를 출력함.
- Git 소유 Portal 두 YAML도 같은 안내·현재 표본 설정을 유지함. 기존 Helm ConfigMap의 소유권을 제거하거나 동일 dashboard UID의 새 ConfigMap을 만들지 않음.
- 후속 Helm upgrade가 기존 ConfigMap을 원본으로 되돌릴 수 있음. 차트나 원본 해시가 달라지면 현재 정책은 무조건 덮어쓰지 않고 거부하며 별도 대조가 필요함. 이 작업은 전체 Helm upgrade를 수행하지 않음.

### 적용·원복 절차

1. 정확한 PR/main 소스·정책·검사·독립 검토를 확정함. N100 main의 clean·hook·원래 미추적 파일을 확인한 뒤 검증 커밋으로 fast-forward함.
2. 실제 ConfigMap UID·원본 key·metadata·Git/LF 해시와 기존 Grafana API를 읽어 대조함. 사전·사후 Portal/Book 외부 health와 Grafana 내부 DB health는 각각 완료 간격 10초 이상으로 3회 확인함. Grafana 내부 조회를 외부 공개 경로 검증으로 확대하지 않음.
3. 0700/0600 journal에 before/after와 소유 UID를 기록하고, 기존 UID·현재 resourceVersion·원본 data 세 조건의 JSON Patch로 해당 key만 교체함. 응답 유실은 실제 GET으로 판정하며 무조건 재적용하지 않음.
4. 기존 sidecar의 자동 provisioning을 기다린 뒤 실제 API의 UID·패널·질의·링크·필터·안내를 대조함. Grafana/Prometheus 재시작·저장 API import·새 자원 생성은 수행하지 않음.
5. 실제 브라우저에서 두 표의 행/열·상세 링크, 기본/변경 필터, 미지원/무표본 이유를 확인함. 로컬 응답 주입 미리보기와 실제 운영 원본 검증은 별도로 기록함.
6. 실패 시 같은 UID의 현재 after data hash·metadata·다른 key를 확인하고 최신 RV 조건으로 before bytes를 역순 복원함. 충돌 자원은 보존하고 다른 안전한 자원의 복원을 계속하며, 충돌이 있으면 최종 실패로 기록함. 삭제 후 재생성·외부 편집 덮어쓰기는 하지 않음.
7. 원복 후에도 실제 API/UI·기존 17개 UP target·워크로드/Pod UID·재시작·PVC·Secret metadata·비대상 ConfigMap 보존을 확인함.

### 최초 미완료 관측과 비대상 자동 갱신

초회 브라우저 관측에서 표의 빈 화면과 namespace 조회 timeout/미완료를 확인해 완료 판정을 보류함. 변수·질의 시간·실제 응답을 확인하고 원격 변경 없이 같은 운영 원본을 다시 조회하여 두 표의 실제 값·6개 열·링크 및 기본/URL namespace의 실제 질의·결측 0을 확인함. 초회 관측의 원인을 특정 운영 결함으로 확정하지 않으며, 불완전한 결과를 성공 근거로 합산하지 않음. 로컬 미리보기도 실제 운영 근거와 구분함.

사후 원본 비교에서는 personal-server/car-care-backup-state의 status_json과 resourceVersion이 기준선과 달랐음. 기존 전체 ConfigMap 동결 검사의 실패는 그대로 보존함. 별도 검토자가 기존 5분 monitor timer의 실제 Git 템플릿·실행 코드 일치, 성공 종료, CM/로컬 관측 시각 일치 및 서비스 실행 시간 내 관측을 직접 확인함. 현재 백업 proof의 복원 검증·업로드 확인·정리·알림 상태도 정상임. 최초 기준선은 해당 data의 해시만 보유하므로 변경된 leaf가 시각 하나뿐이라고 단정하지 않음.

이 기존 observer 소유 key의 정상 갱신만 제한적으로 구분하도록 임시 검사 도구를 보완함. 기존 monitor-result와 같은 정상 관측, 10분 이내·미래 30초 이내 시각, 고정된 원래 기준선 digest·최초 apply 완료 시각, Git과 같은 기존 네 소스의 읽기 전용 snapshot 전체 payload 일치를 요구함. 정확한 단일 key·metadata/binary와 나머지 보호 항목을 모두 대조하고 역행·추가 key·오래된 값·변조를 거부함. baseline 원본은 수정하지 않고 0600 별도 audit에 해시·시각·허용 범위만 남김. 기존 제어 경로를 원래 해시로 복원 대조하고 최종 fixture 61개와 작성 미참여 전문 재검토를 통과함.

실제 post에서 기존 자동 관측 key 1개의 정상 전진을 확인했으며 원래 baseline digest는 유지됨. post의 protected_unchanged는 이 명시적인 observer 범위를 제외한 보호 항목의 일치를 뜻하며, 전체 ConfigMap bytes가 전혀 바뀌지 않았다는 뜻으로 확대하지 않음. 자동차 모니터·일정·ConfigMap 값의 운영 수정은 수행하지 않음. 실제 운영 원복은 불필요했으며 원복 절차 자체는 fixture 검증 결과로 구분함.

작성 미참여 전문 검토자가 이후 실제 GET/READ로 정확한 main·clean·기존 미추적 파일, 19개 CM의 현재 해시/UID/metadata, 17개 UP와 동일 target, 원래 기준선 digest·post 성공·미원복을 확인함. 기존 strict 전체 비교의 차이를 보존하고 현재 observer payload의 읽기 snapshot 전체 바이트 일치와 나머지 보호 항목의 엄격 일치를 확인해 최종 PASS함. 검토 전후 원격 journal/audit bytes도 동일하며 검토자는 원격 쓰기를 수행하지 않음. 선행 실제 Grafana API 19개·1,762개 경로 결과는 현재 해당 CM이 변하지 않았음을 확인한 뒤 재사용함.

## 확인 필요 사항

- 변경 대상 19개·246개 패널의 최종 관측에는 여전히 결측 46개가 있음. 전용 미수집 제어 평면 41개, TCP DNS 표본 2개, 쓰기 5xx 표본·CPU 제한/CFS 표본·storage 실패 표본 각 1개로 상단 안내와 함께 해석함. 전체 29개 모든 패널의 결측이 제거됐다고 확대하지 않음.
- 로컬 미리보기는 실제 수집 값을 읽지만 운영 provisioning 성공의 대체 근거가 아님.
- namespace의 Running Pod·Deployment, cluster 라벨 부재, storage success 표본을 적용 직전에 다시 확인함. 환경 전제 실패는 적용을 막지만 안전한 원복을 막지 않음.
- 수집 범위 확장·Windows 물리 호스트 지표·제어 평면 전용 scrape·앱/이미지·PVC/Secret·Caddy/Tunnel·scheduler 변경은 제외함.

## 후속 조치

주 담당은 구현·통합·자기 검증·실제 원본 UI/health·운영 실행과 결과 문서를 담당함. 임시 적용/원복 및 관측 상태 검사 도구 작성은 별도 gpt-6.1-sol high가 담당함. 작성 미참여 gpt-6.1-sol high가 전문 사전/실제 원격 사후 검토를 수행하며, 별도의 순수 읽기 전용 gpt-6.1-sol high가 source diff·검사·작성 이력의 최종 strict 검토를 담당함. 운영 실패 비용과 작성 이력 경계를 고려한 배정이며 자기 검증·CI·실제 원격 독립 검토를 합산하지 않음. 자문 세션은 최종 strict 승인으로 확대하지 않으며 같은 파일의 동시 수정은 하지 않음.

소스 main 선검증 후에만 운영 적용할 수 있으므로 적용 뒤 확정된 결과 기록은 문서 전용 후속 PR로 분리함. 결과 문서의 maintenance 731개와 최종 문서 링크 검사 2개를 확인하며, 영향 없는 기능 검사 결과는 재사용함. 실제 운영 적용·독립 사후 확인은 완료됐으며 이번 운영 승인은 완료·소진됨. 전체 Helm upgrade나 새로운 수집 범위에는 재사용하지 않음. 사용자가 지정하지 않은 추가 수집·운영 변경은 수행하지 않음.
