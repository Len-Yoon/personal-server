# N100 WSL 메모리 상한 조정 기록

**최종 메모리 상한: 5GB를 실제 적용하고 단기 운영 수용함. 새 승인으로 4GB를 먼저 시험했으나 지속 메모리 압박 기준을 초과해 5GB로 전환함. 서비스와 자동복구 작업은 복구됐으며, 기존 bootstrap 재시도 오류·재생성 부하 미검증과 주식 프로그램 미실행은 별도 확인 필요함. 2~6절은 앞선 원복 시도, 8절은 이후 새 승인 결과임.**

## 2. 핵심 요약

- 현재 WSL의 메모리 용량은 약 7.63GiB이며 명시적 `.wslconfig`는 존재하지 않음을 확인함.
- 최근 24시간 관측의 `MemTotal - MemAvailable` 최대는 3,403,046,912바이트, 약 3.17GiB임. 캐시를 제외한 수요의 근사치이며 프로세스 전용 메모리 합계나 미래 최대 수요가 아님.
- 30초 원시 표본의 최대 MemTotal과 최소 MemAvailable로 산출한 보수적 상계는 3,460,706,304바이트, 약 3.223GiB임. 1분 부분 질의가 놓칠 수 있는 피크를 고려해 감축 판단에는 이 값을 함께 사용함.
- 사용자는 5GB 가능성을 검토하고 4GB도 가능하면 적용하도록 요청함. 4GB는 현재 관측 대비 예상 여유가 약 0.41GiB로 좁아 제외하고, 적용 후보를 `[wsl2] memory=5GB`로 정함. CPU·스왑·네트워크·캐시 회수·서비스 설정은 변경하지 않음.
- 상한은 예약량이 아니며 5GB 설정이 Windows RAM 2GB 반환을 보장하지 않음.
- 설정 저장과 실행 중 상한 적용은 별도 단계임. WSL 재기동 전에는 적용 완료로 기록하지 않음.

### 3.2. 최소 설정과 보존 범위

```ini
[wsl2]
memory=5GB
```

CPU 개수·스왑·pageReporting·autoMemoryReclaim을 추가하거나 변경하지 않음. WSL 업데이트, 캐시 강제 삭제, 기존 실습/모니터링 삭제, 앱·Secret·PVC·데이터·Caddy·Tunnel·bootstrap·scheduler 변경을 포함하지 않음. `.wslconfig`는 해당 Windows 사용자 아래 WSL2 배포판에 영향을 주므로 파일 부재·동일 실행 환경·동시 변경 여부를 적용 직전에 다시 확인함.

명목 상한 5GB와 적용 후 Linux MemTotal은 예약·커널 영역 때문에 일치하지 않을 수 있음. Linux에서 정확히 5GiB가 보이거나 특정 용량이 즉시 Windows로 반환된다고 보장하지 않음.

### 3.3. 4GB와 5GB 비교

| 명목 상한 | 예상 Linux MemTotal | 관측 상계 대비 예상 여유 | 판단 |
|---|---:|---:|---|
| 4GB | 약 3.63GiB | 약 0.41GiB | 변동·백업·업데이트 여유가 좁아 운영 적용하지 않음 |
| 5GB | 약 4.63GiB | 약 1.41GiB | 시범 적용 후 실제 예약·압박·서비스 상태 확인 필요 |

현재 명목 8GiB와 Linux MemTotal의 차이가 유지된다고 가정한 추정치임. 적용 후 실제 용량으로 재판정하며, 작업 집합·캐시·미래 피크를 보장하는 수치가 아님.

### 3.4. 준비·적용·원복 절차

1. 맥 저장소에서 설정 원본·기록을 준비하고 관련 검사·독립 운영 검토·PR CI를 완료함.
2. N100 저장소의 현재 브랜치·작업공간·hook·대상 커밋을 확인하고 검증된 정확한 커밋만 fast-forward 동기화함. 강제 reset·기존 미추적 파일 삭제는 하지 않음.
3. Windows 설정 파일이 여전히 부재인지 확인하고, 검증된 원본과 같은 바이트의 파일을 신규 생성함. 파일이 새로 생겼거나 원본 상태가 달라졌으면 덮어쓰지 않고 보류함.
4. 재기동하지 않을 경우 파일 해시·구문·기존 boot ID·MemTotal·서비스 상태를 대조하고 `설정 저장 / 다음 기동 적용 대기`로 기록함. 상한이 즉시 내려갔다고 표현하지 않음.
5. 사용자가 이번 설정 변경에 한정해 서비스 일시 중단·적용·복구 검증을 명시 승인함. 진행 중인 백업·배포·DB 작업이 있으면 대기하고, 설정을 먼저 저장한 뒤 WSL 종료를 한 번 수행함. Windows·주식 프로그램은 종료하지 않음. 기존 KeepAlive·Supervisor의 자동 기동 경로를 유지하며 별도 bootstrap·daemon을 중복 실행하거나 스케줄러를 비활성화하지 않음. 종료 응답 유실 시 실제 boot ID·실행 상태부터 조회함.
6. 최대 5분의 초기 복구 관측 동안 재시작을 반복하지 않고, 기존 자동 기동·프로세스·K3s 상태를 조회함. 기한 내 정상화되지 않으면 원인을 구분하여 1회 원복 여부를 판단함. Windows 재부팅으로 승격하지 않음. 재기동 후 MemTotal·MemAvailable·스왑·OOM·메모리 압력·K3s Ready·Pod 재시작·Compose 상태·Windows 가용/커밋·외부 health를 확인함. 캐시 재형성 후와 바쁜 시간의 추가 관측이 필요함.
7. 설정 저장 원복은 삭제 직전에 이번에 생성한 파일의 해시·메타데이터와 다른 작성자의 변경 징후를 다시 확인한 뒤 조건부 삭제하여 기존 부재 상태로 복원함. 검사와 삭제 전체가 원자적인 비교·삭제는 아니므로 경합 가능성을 완전히 제거한다고 보장하지 않으며, 동시 작성 징후가 있으면 보류함. 실행 상한까지 원복하려면 다시 WSL 재기동이 필요하므로 같은 중단·원복 범위에서 판단함.

설정만 저장하는 경우 외부 health는 전후 Portal과 Book을 각각 10초 이상 간격으로 3회 조회함. 실제 WSL 재기동을 별도 승인받은 경우에는 영향받는 전체 운영 서비스로 검증 범위를 확대함. 공개 health가 있는 앱은 각각 3회 조회하고 공개 경로가 없는 서비스는 내부 readiness·실행 상태를 확인함. 원격 응답 유실 시 파일·실행 상태부터 조회하며 쓰기 명령을 즉시 반복하지 않음.

## 5. 확인 필요 사항

- 보완 조회로 WSL 2.7.10.0·커널 6.18.33.2를 확인함. 버전 확인과 별개로 캐시 회수 기능은 이번 변경에 추가하지 않음.
- 사전 Windows 커밋은 14.38 / 17GiB로 여유가 좁았고, 복구 직후 별도 순간 조회는 11.36 / 17.62GiB였음. 부팅·프로그램 상태가 달라졌으므로 이 차이를 5GB 감축 효과로 해석하지 않음. 상한은 적용되지 않았음.
- 5GB 환경의 실제 업무 피크·백업/복원·업데이트 중 메모리와 응답 품질은 적용 후 확인 필요함.
- 새 Linux VM 설치 가능 여부와 완전한 이중화·물리 호스트 장애 대비는 이번 작업의 완료 범위가 아님.

| 항목 | 확인 결과 | 비고 |

| 부팅 | 새 Linux boot ID와 Windows 새 부팅 시각 확인 | 단순 앱 재시작과 구분함 |

### 6.3. 남은 조치와 승인 경계

- 메모리 감축은 미완료이며 4GB는 시도하지 않음. Git의 5GB 파일은 검토 원본으로만 남고 현재 적용 설정이 아님.
- 추가 감축·재시작은 보류함. 다음 점검 전 WSL 종료 지연과 가상 디스크 잠금, 유지보수 중 기존 자동복구의 Windows 재부팅 승격을 함께 검토해야 함.
- 이번 WSL 종료·관리 서비스 강제 복구 1회 승인을 새 작업에 재사용하지 않음. Windows 재부팅·다른 VM/HCS 종료·거래 프로그램 조작은 별도 범위임.
- 서버 복구와 별개로 MetaTrader의 로그인·EA·거래 상태는 사용자 직접 확인 필요함.
- 실제 운영 후에만 확정된 원복·자동 재부팅 경과는 설정 준비 PR #485와 구분한 문서 후속 변경으로 기록함. 저장소 검사·N100 동기화·설정 저장/원복·서비스 복구·외부 health를 합쳐 배포 성공이라고 표현하지 않음.

## 8. 새 승인 — 계획된 Windows 재부팅으로 4GB 우선 시험

### 8.1. 범위와 설정 원본

사용자가 이전 시도 이후 “재시작 해도 되니 지금 마무리”, “1차로 4기가 먼저 하고 문제없으면 적용, 문제가 생기면 5기가”라고 명시 승인함. 아래는 앞서 소진된 승인과 별개의 새 실행 범위임.

| 항목 | 계획 | 비고 |
|---|---|---|
| 1차 후보 | [시행 당시 4GB 원본](https://github.com/Len-Yoon/personal-server/blob/72331056f2f5ddc7c44183f75776cd93bd84893a/infra/k8s/host/n100.wslconfig) | 실제 기동·운영 부하를 시험하며 기존 추정만으로 통과 판정하지 않음 |
| 최종 정본 | [운영 5GB 설정](../infra/k8s/host/n100.wslconfig) | 실제 수용 상한과 정본을 일치시킴 |
| 실패 시 후보 | [5GB fallback](../infra/k8s/host/n100-fallback.wslconfig) | 검증된 동일 목적 원본에서 선택함 |
| 공통 설정 | `[wsl2] memory` 한 항목만 변경 | CPU·네트워크·스왑·캐시 회수 키를 추가하지 않음. 스왑 등 기본값의 유효 크기는 상한에 따라 달라질 수 있어 실제 값을 관측함 |
| 재기동 | 후보별 정상 Windows 재부팅 1회 | WSL 단독 종료·관리 서비스/VM 강제 종료를 반복하지 않음 |
| 주식 프로그램 | Windows 재부팅에 따른 중단 포함 | 실행 여부만 확인하고 로그인·EA·거래 설정은 조작하지 않음 |
| 실패 시 원복 | 원래 설정 부재 상태로 복원 후 정상 Windows 재부팅 | 4GB·5GB 모두 불안정하면 유지하지 않음 |

### 8.2. 자동 재부팅 승격 방지

1. 기존 Supervisor 작업 `personal-server-autostart`와 `PersonalServer-EmergencyReboot`의 Enabled·정규화 XML 해시·실행 상태를 메모리에 읽고 비밀 없는 선택 필드만 점검 증거에 저장함. 등록 정보·자격 증명·정책 코드는 수정하지 않음.
2. 이번 점검 동안 Emergency 작업과 Supervisor 작업을 일시 비활성화함. 실행 중 Supervisor를 먼저 중지하고, 단계별 새 스냅샷의 정확한 스크립트·역할·PID·부모관계·생성시각·명령 해시에 부합하는 잔존 Daemon만 종료해 각각 0개인지 확인함. 잠금 파일은 삭제하지 않음.
3. WSL KeepAlive 작업은 원래 Enabled·정의를 유지하여 Windows 부팅 후 기존 WSL·systemd 경로가 동작하게 함. 이번 점검에 기인한 예약 재부팅이 없는지 확인함.
4. 후보 설정으로 기본 검증을 통과하면 Supervisor만 원래 Enabled로 복원하고 기존 작업을 1개 시작함. Emergency 작업은 아직 비활성화하여 bootstrap 부하 중 자동 재부팅 승격을 막음.
5. 기존 Supervisor 시작 경로는 Compose 앱 재생성·Caddy build·maintenance 및 post_boot_check를 포함할 수 있으므로, 이 경로 이후 메모리·서비스를 다시 확인함. 기존 코드·이미지 정책을 변경하지 않음.
6. 최종 후보가 안정화되면 Emergency 작업도 원래 Enabled로 복원하고 두 작업의 정의 해시와 실행 수·복구 실패 수를 확인함. 실패 시 Supervisor를 다시 점검 상태로 두고 5GB 또는 원래 설정으로 이동함. 자동복구를 비활성 상태로 남긴 채 완료 보고하지 않음.

### 8.3. 실측 판정 기준

아래는 이번 소규모 시험의 초기 운영 기준이며 장기 SLO·모든 미래 부하를 보장하지 않음. 부팅 직후 일시 압박과 지속 압박을 구분함.

| 검사 | 통과 조건 또는 fallback 조건 | 비고 |
|---|---|---|
| 실효 상한 | 새 Windows/Linux 부팅과 설정 해시, Linux MemTotal·K3s allocatable을 함께 확인 | 명목 4GB와 Linux MemTotal은 일치하지 않을 수 있음 |
| 서비스 | 노드 Ready·MemoryPressure 없음, 기존 앱의 desired/ready/available 및 Docker health 정상 | 초기 복구 5분 안에 정상화되지 않으면 원인 확인 후 fallback |
| OOM·재시작 | 새 OOM 또는 메모리 부족 eviction이면 실패 | 정상 부팅으로 증가한 1회와 이후 반복 crash를 구분함 |
| 여유 메모리 | 워밍업 뒤 MemAvailable 512MiB 미만이 60초 지속되면 fallback | 현재 관측 기준으로 4GB가 빠듯할 수 있음을 인정함 |
| 메모리 압력 | 워밍업 뒤 full avg60 1% 초과 또는 some avg60 5% 초과가 2분 지속되면 fallback | 단일 부팅 표본만으로 실패 판정하지 않음 |
| 스왑 | 워밍업 뒤 사용량이 256MiB 이상 늘고 계속 증가하면 fallback | 스왑이 조금 사용됐다는 이유만으로 실패로 보지 않음 |
| 응답 | Portal·Book·YouTube health 각각 10초 이상 간격 3회 정상 및 기존 readiness 확인 | 실제 업무 쓰기·거래 요청은 생성하지 않음 |
| 관측 범위 | 기본 기동 후와 Supervisor/bootstrap 복원 후를 포함해 약 10분 관측 | 단기 시험 결과이며 이후 실제 피크·백업 시간 추가 관측 필요 |

Windows 정상 재부팅은 `/r /t 0`을 사용하고 `/f`를 추가하지 않음. [Microsoft 재부팅 명령 문서](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/shutdown)상 `/t`가 0보다 크면 강제 종료가 암시되므로 지연 재부팅을 비강제 종료라고 표현하지 않음. 응답이 끊겨도 명령을 즉시 반복하지 않고 Windows 부팅 시각으로 실제 수행을 확인함.

### 8.6. 확인 필요 사항과 후속 조치

1. 기존 bootstrap 실제 up 오류 원인과 컨테이너 재생성 경로의 부하는 확인 필요함. 이번 작업에서 보호된 bootstrap 코드·Secret·이미지 정책을 임의 수정하지 않음.
2. 주식 프로그램이 실행되지 않은 상태에서 측정한 Windows 가용 RAM을 원래 주식 동시 부하의 여유나 감축 효과로 일반화하지 않음. 사용자 로그인·프로그램/EA 상태 확인 후 실제 동시 부하 관측이 필요함.
3. 단기 표본은 하루 전체·정기 백업·TSDB 작업·미래 피크를 보장하지 않음. 추가 VM 설치도 이번 검증 범위가 아님.
4. 새 승인 범위의 4GB→5GB 시험·두 정상 Windows 재부팅·Task 일시 정지/복원은 완료·소진됨. 추가 재부팅·강제 종료·bootstrap 수정·거래 프로그램 조작에 재사용하지 않음.
