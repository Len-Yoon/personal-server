## 2. 핵심 요약

아래 답변은 프로젝트 설계와 관측 근거를 설명하는 연습문임. “제가 구현했다”는 표현은 본인이 코드를 이해하고 책임 범위를 설명할 수 있을 때 사용함. 에이전트의 구현·자동 실행 도움을 공개하며 개인의 수동 장애 해결 실적으로 바꾸지 않음.

## 3. 답변 연습

### 3.1 약 3분 프로젝트 소개

“개인 데이터를 관리하는 서비스를 N100 한 대에서 운영하는 프로젝트를 만들고 있습니다. 서비스별 SQLite와 파일 저장을 선택했고, 웹 앱과 호스트 보조 작업의 실행 위치를 구분했습니다. 단일 호스트이므로 다중 노드 고가용성 경험으로 설명하지는 않습니다.

최근에는 에이전트의 도움을 받아 성능 측정, 장애 재현, 배포 검증 도구를 구현해 자동 실습으로 검증했습니다. 첫째는 통합 검색입니다. 느린 대상이 전체 검색을 붙잡지 않도록 서비스별 결과와 상태를 분리했습니다. 로컬 샘플 HTTP 서버와 실제 검색 함수를 연결해 1,080개 표본을 측정했고, timeout에서도 다른 두 대상의 결과가 남는지 확인했습니다. 동시성을 높여도 처리량이 비례하지 않아, 원인 프로파일링 없이 성능 개선이라고 주장하지 않았습니다.

둘째는 SQLite 쓰기 실패입니다. 별도 프로세스가 실제 잠금을 잡은 상태에서 제품 함수를 호출했습니다. 코드 5가 발생한 뒤 논리 데이터가 바뀌지 않았는지 확인하고, 잠금을 해제한 뒤 같은 요청을 두 번 보내 최종 반영은 한 번인지 검증했습니다. 페이지 제한으로 만든 코드 13과 구분했고, 약 5초의 대기는 제품 연결의 기본 timeout과 연결해 설명했습니다.

셋째는 배포 검증입니다. 실제 앱 프로세스의 health와 readiness를 따로 확인했습니다. health가 200이어도 설정한 readiness 경로가 404면 후보 성공으로 판정하지 않았고, 후보를 종료한 뒤 이전 릴리스를 다시 검증해 구동했습니다. 기존 실습은 같은 앱 코드의 릴리스 교체였습니다. 추가로 서로 다른 두 Git 앱 버전의 Docker 이미지를 실제 빌드해 교체·왕복·readiness 실패를 각 세 번 검증했습니다. v2에서 쓴 데이터를 v1이 읽고 다시 쓸 수 있는지 확인했으며, schema가 바뀌지 않는 지정 경로의 결과로 제한했습니다.

이 경험에서 중요하게 다룬 것은 성공 표시의 근거입니다. 저장소 CI, 로컬 재현, 운영 배포, 외부 접근 정상은 각각 다른 증거로 관리했습니다. 재전송 뒤 데이터와 요청 기록, 자식 프로세스 정리까지 확인했고, 자동 실습 시간은 사람의 장애 대응 시간으로 제시하지 않습니다.”

### 3.3 추가 질문 답변

| 질문 | 답변의 핵심 | 비고 |
|---|---|---|
| health와 readiness 차이는? | 프로세스 응답과 서비스 수용 조건을 분리함. 기존 실습은 health200·설정한 readiness 경로404를 실제 HTTP로 관측함 | DB 쓰기 가능성 등 모든 조건을 readiness가 보장하는지는 구현별 확인 필요 |
| BUSY와 FULL을 어떻게 구분했는가? | 코드 5와 실제 잠금 소유 연결, 코드 13과 page_count·max_page_count를 대조함 | FULL만으로 OS 디스크 고갈 확정 불가 |
| 무조건 재시도하면 되는가? | 같은 요청 ID·본문 해시·결과 기록과 트랜잭션이 필요함. 다른 내용의 요청을 같은 ID로 보내는 경우도 구분해야 함 | 이번 측정은 지정 메모 수정의 동일 요청 재전송 |
| request ID가 데이터 보존 근거인가? | ID만으로 부족함. version·revision·write_request 수와 실제 내용·기존 자료·무결성을 함께 확인함 | 모든 경로의 exactly-once 보장 아님 |
| 언제 롤백하는가? | 후보 readiness 실패 등 명시 조건에 한정하고 실패 후보 종료 후 이전 artifact·데이터 호환성을 검증함 | 호환되지 않는 schema migration은 별도 계획 필요 |
| digest와 Docker image ID는 같은가? | 실습 manifest·payload digest는 정한 파일·바이트의 해시이며 Docker image ID는 로컬 이미지 구성 객체 식별자임. 레지스트리 배포 digest와도 구분함 | 이미지 ID만으로 공급망 검증 완료 아님 |
| 소스 출처는 어떻게 증명하는가? | 고정 Git 커밋·파일 해시·깨끗한 작업공간·실제 실행 artifact의 연결을 확인함 | tag·이름만 믿지 않음 |
| 두 버전 Docker 실습도 완료했는가? | 별도 신규 원본에서 실제 두 코드 버전 Docker의 upgrade·왕복·readiness 실패 각 3회, 총 9회를 확인함 | 지정 경로·schema 불변, 운영 배포 아님 |

## 5. 확인 필요 사항

개인 수행: [실습지](20261018_DB잠금_실습지.md) 작성, 직접 명령 실행·원본 해석·구두 설명은 확인 필요함. 본인 역할·직접 수정한 코드·설계 판단은 면접 전 사실에 맞게 확정함. 운영 이력의 최신성은 별도 확인 필요함.

## 6. 후속 조치

DB 잠금 신규 1회와 Docker 9회 원본을 반영함. 전체 로컬 검사·PR/main CI·병합 결과는 해당 PR의 최종 기록으로 별도 확인함. 답변을 소리 내어 읽어 시간을 조정하고, 설명하지 못하는 코드는 먼저 학습함. 원본 없이 개인 경험·숫자를 보강하지 않음.
