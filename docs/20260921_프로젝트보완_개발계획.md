## 2. 핵심 요약

먼저 사용자 기능 장애와 데이터 손실을 수정하고 검증 체계를 보강함. 이후 운영 자동복구·데이터 처리·문서를 정리하며, 대규모 고도화는 기존 결함 수정 뒤에 설계함. 단계별로 구현, 관련 테스트, 정적 검사, 독립 검토, 하네스 결과를 기록한 뒤 다음 단계로 이동함.

1차는 이미 원인과 수정 경계가 확정된 F01을 실행함. 2차 HomeOps는 F02 단독 활성화 시 F03·F04 위험을 드러낼 수 있으므로 하나의 안전성 묶음으로 취급함. 운영·보안 영향이 있는 2차는 구체 범위를 제시한 뒤 2026-09-21 사용자에게 로컬 코드·테스트 변경 승인을 받았음. 실제 운영 적용은 승인 범위에 포함하지 않음.

## 3. 공통 작업·승인 기준

- 저장소 `AGENTS.md`와 `docs/codex-work-loop.md`를 준수함.
- 실제 운영 데이터·PVC·Secret·Caddy·Tunnel ingress·Compose writer 변경을 포함하지 않음.
- 서버 기동·스케줄러 코드는 기본 변경 금지이며, 일반적인 “차례대로 진행”을 예외 파일의 운영 변경 승인으로 확대하지 않음.
- 회귀 테스트에서 먼저 문제를 확인하고 최소 수정함. 같은 수정의 재검증은 최대 3회로 제한함.
- 변경 전 하네스에서 필수 검사와 다음 조치를 확인하고, 실제 검사 결과를 전달해 다시 판정함.
- 주 에이전트는 계획·경계·통합 검증, Luna는 구현·단위 검증, Terra는 설계·운영·보안·rollback 독립 검토를 맡음. 동일 파일의 동시 수정은 금지함.
- 기능·설정 파일 3개 초과 또는 복수 서비스 변경 시 주·구현·검토 3명으로 분리함. 운영·보안 영향은 전문 검토를 포함함.
- 사용자 화면의 주소·응답 계약을 보존함. 시간 신규 저장은 UTC aware ISO 8601, 표시·날짜 판단은 Asia/Seoul, 표시 형식은 `YYYY-MM-DD HH:MM`을 유지함.
- 테스트 성공, 저장소 반영, N100 적용을 별개 상태로 기록함. 커밋·push·PR·병합·운영 적용을 한 번에 완료로 처리하지 않음.
- 기존 테스트 환경 실패는 원인과 비연관 근거를 기록함. 관련 실패가 남아 있으면 해당 단계는 완료 처리하지 않음.

## 프로젝트 보완 개발 계획의 연속 진행 승인

- 사용자가 2026-09-21 `docs/20260921_프로젝트보완_개발계획.md`의 단계별 진행에 대해 수정 → 관련 테스트·정적 검사 → 독립 검토 → 커밋·push·PR → CI·Agent Review 확인 → 병합 → 다음 단계 진행을 일괄 승인함.
- 해당 계획의 승인된 일반 앱 수정과 문서·테스트 변경은 같은 범위의 승인을 매 단계 다시 요청하지 않음. 1·2차 검증 완료 변경도 이 저장소 반영 승인에 포함함.
- 새 운영 영향, 금지 영역, 승인 범위를 벗어나는 변경은 별도로 확인함. 관련 테스트·CI·검토 실패가 있으면 병합하지 않고 원인 확인·범위 내 보완 후 재검증함.
- N100 운영 배포는 이번 일괄 승인에 포함하지 않음. 병합 전에 기존 자동 배포 분류를 확인하며, 병합이 운영 배포를 자동 유발하는 단계는 PR·검증까지 준비하고 운영 승인 전 병합하지 않음. 승인 회피를 위해 workflow를 끄거나 분류 정책·변경 묶음을 조작하지 않음.
- 검증·저장소 병합·N100 적용을 별도 상태로 기록함. 각 단계의 변경 파일·테스트·검토·PR·병합 커밋·다음 단계를 개발 계획에 갱신함.
