독립 구현 작업이 있어 주 담당(Portal·배포·통합), 메모 담당(Sol medium), 수집 담당(Sol medium), 독립 전문 검토(Sol high)의 4명으로 분담함. 같은 파일을 동시에 수정하지 않음. 하위 담당은 commit/push를 수행하지 않으며 주 담당이 한 PR로 통합함.

배포 직렬 큐는 `queue: max`로 기존 pending 실행의 교체 취소를 방지함. 큐의 100건 한도·사용자 취소·CI 실패까지 자동 복구를 보장하지 않음. 배포 목표 실패 뒤 원복 성공을 workflow 성공으로 표시하는 기존 동작과 전역 rollback 기준은 이번 10건 밖의 후속 개선 항목으로 유지함. [GitHub concurrency 기준](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)을 대조함.

운영 사전 점검에서 차량 bind 4개 항목의 UID/GID가 1000:1000으로 표시되고 OAuth volume 3개 항목은 10001:10001로 확인됨. bind는 9p·metadata 비활성이므로 `chown`의 실제 효과는 별도 확인하며 mount 옵션을 변경하지 않음. 사용자는 4개 항목에 대한 기존 소유권 명령 실행을 추가 승인함. 전역 원복 소스와 실제 실행 앱 파일이 불일치하여 차량 단독 원복을 실제 image ID 기준으로 보완함. 실패 target writer 중지·기존 소유권 snapshot 복구 후 image-only override를 적용하며, 다른 이미지나 Docker API 불확실 상태에서는 추가 교체를 중단함. 정상 복구를 목표 배포 성공으로 표시하지 않음. 다른 서비스·혼합 배포의 원복 정책은 기존 상태를 유지함.

첫 운영 실행은 이미지 빌드 후 소유권 사전검사에서 중단됨. Alpine BusyBox `find`가 GNU 전용 `-uid/-gid`를 지원하지 않아 OAuth 소유권을 확인하지 못했으며, writer 중지 전 실패하여 기존 차량 컨테이너·이미지·mount·소유권·K3s4종은 그대로 유지됨. 이미 PR #416이 병합된 뒤 발견한 호환 오류이므로 후속 PR에서 소유권 조건을 GNU/BusyBox 공통의 숫자 `-user/-group`로 보완함. 검사 실패를 허용하거나 OAuth 승인을 확대하지 않으며, 같은 원인 운영 실패는 현재 1회로 기록함. 앱·이미지 빌드 입력이 같아 기존 전체 앱/K3s 검증을 재사용하고, 실제 Alpine 명령 경계와 유지관리 전체·필수 PR/main CI를 다시 확인한 뒤 승인된 차량 배포를 재실행함.

이미지의 CA 인증서·시간대 데이터는 [고정 버전의 공식 Python 이미지 정의](https://github.com/docker-library/python/blob/2a3b794c223ab067d122719541cdd54a068732a5/3.12/alpine3.24/Dockerfile)를 대조함. PR CI와 최종 커밋의 검증 이미지 sidecar를 완료 근거로 확인하며, 저장소 병합·N100 동기화·이미지 반입·운영 교체·외부 health는 별도 상태로 기록함. 운영 적용의 최종 SHA·실제 이미지·health·검토 결과는 이 보완 PR의 최종 운영 결과에서 확인함. 저장소 검사 성공을 운영 적용 완료로 해석하지 않음.

## 추가 개선의 저장소·운영 경계

아래 개선의 운영 이미지·소스·설정을 적용함. 적용 성공과 신규 이미지의 첫 정기 백업 성공은 별도로 판정함.

| 개선 | 구현 내용 | 운영 상태 |
|---|---|---|
| 포트폴리오 편집 보호 | 내용 버전·프로세스 간 잠금, 오래된 저장 409, 원문 보존·명시적 최신 내용 비교, 줄바꿈 정규화와 동일 요청 재전송 보호 | 코드 적용. 포트폴리오 편집용 `PORTFOLIO_ADMIN_PASSWORD` 미설정으로 실제 편집 로그인은 미검증 |
| 준비 상태 일치 | Book·YouTube 신규 설치 readiness `/ready`, liveness `/health`. 기존 배포·원복 자산의 legacy readiness `/health`는 읽기 호환 | 현재 앱의 `/ready` 유지, 신규 기본값 소스 동기화 완료. 앱 재시작 없음 |
| 관측 저장·디스크 경보 | Prometheus 7d + 3GB 보관, DiskPressure/PVC 부족 규칙과 Telegram 라벨, 읽기 전용 지표·규칙 coverage 감사 | 로드된 규칙·실제 `1w or 3GiB` 보관 기준 확인. 호스트 연속 지표·단말 수신 미검증 |
| 백업 정리 표시 | 다섯 서비스의 정리 시각·보존 수·확정 삭제 수·확정 회수 bytes·고정 실패 사유. 구형·불명확 값은 확인 필요 | 소비자·생산자 적용, 고정값 일치·구형 증적 호환 확인. 신규 정기 실행 대기 |

운영 적용은 소스·이미지와 백업 비실행 확인 → Relay → Portal 소비자 호환 확인 → 독립적인 모니터링 설정·규칙 적용 → 공유 잠금 안의 백업 이미지·host 소스 정합화 → 원본 데이터·복원 시각 보존과 외부 health 확인 순서로 수행함. 새 Relay는 기존 통계 없는 증적을 허용하지만 구형 Relay는 새 증적 필드를 거부하므로 생산자 선적용을 금지함. 사용자의 운영 배포 승인에 따라 기존 리소스의 이미지·허용 필드만 변경함. 네 CronJob은 UID·전체 spec 조건부 변경과 서버 dry-run을 통과했고 공유 잠금 안에서 소스와 이미지를 정합화함. 기존 여덟 경보에 두 경보만 추가하고 Prometheus는 설정 reload로 보관 한도를 반영함. 자격 증명 Secret·PVC·백업 일정·Caddy·중지된 권한/정책 작업은 변경하지 않음. Operator 생성 설정 갱신은 모니터링 설정의 종속 반영이며 자격 증명 변경과 구분함.

| 역할 | 담당·모델 | 검토 범위 |
|---|---|---|
| 주 담당 | 현재 세션 | 포트폴리오·통합·의미 있는 커밋·문서·PR/CI |
| 백업 구현 | gpt-6.1-sol / medium | 생산자·Relay·관리자 화면과 데이터 경계 |
| 운영 설정 구현 | gpt-6.1-sol / high | 준비 상태·모니터링 계약과 규칙 검증 |
| 독립 전문 검토 | gpt-6.1-sol / high | 전체 diff·경합·구형 호환·보호 대상·운영 순서 |

독립 구현 2개와 전문 검토를 분리해 4명이 수행함. 같은 파일을 동시에 수정하지 않고 Relay의 디스크 문구는 백업 담당이 통합함. 독립 검토에서 확인한 CRLF 버전 불일치는 수정 후 회귀 검증함. 운영 적용은 주 담당과 gpt-6.1-sol/high 전문 검토 담당의 2명으로 수행했으며, 적용 절차·실패 경계와 실제 이미지/설정 증적을 독립 대조함. 단계별 성공 여부는 관련 검사·전체 9개 묶음·필수 PR/main CI로 구분함.

## 추가 보안 검증

- 실제 관리자 로그인 응답에서 운영 모드 플래그가 없는 경우 세션 쿠키의 `Secure` 누락을 확인함. 관리자·포트폴리오·파일함의 쿠키 정책을 공통 기준으로 보완하고 사용자 승인 후 Portal만 운영 교체함. 실제 공개 HTTPS의 관리자·파일함 로그인 응답에서 `Secure`·`HttpOnly`·`SameSite=Lax`를 확인함. 포트폴리오는 전용 비밀번호 미설정과 별도로 동일 이미지의 격리 시험에서 보호 동작을 확인함. 비밀번호·운영 모드·세션 범위와 기존 데이터는 변경하지 않음.
- Telegram 시험 메시지 1건은 기존 SRE 개인 채팅에 전송했고 API 수락과 사용자 단말 수신을 모두 확인함. 기존 네 서비스의 최신 백업 알림 전달 원장도 대조함.
- Windows 디스크 지표는 기존 수집기→system-agent 경로에서 수집 시각 증가와 정상 상태를 확인함. 이 확인을 Prometheus 물리 호스트 시계열·디스크 경보 연결 완료로 확대하지 않음.
- 배포된 이미지의 임시 파일·임시 인증을 사용한 격리 시험에서 로그인·버전·CRLF 정규화·409 충돌·원문/초안 보존·재전송 보호를 확인함. 운영 편집용 비밀번호 미설정은 유지하며 실제 인증 활성화와 구분함.

## 운영 승인 경계

일반 개발은 AGENTS.md에 따라 구현·검증·검토·PR/CI·병합까지 진행함. 새로운 운영 변경은 대상·동작·순서를 준비한 뒤 유효한 승인을 확인함. Secret·PVC·운영 데이터·bootstrap·scheduler·Caddy·통신 정책을 일반 개발 범위로 확대하지 않음. 추가 Windows 권한·Caddy 전환·통신 차단 정책 작업은 중지 상태이며 자동 재개하지 않음.

## 후속 조치

### DevOps 로컬 실습

성능·용량 분석 → 장애 진단·복구 → 배포 표준화 순서로 진행함. 클라우드와 새 VM 환경 재구축은 제외함. 1단계는 제품 검색 함수를 로컬 샘플 서버와 연결하는 [통합 검색 성능 실습](search-performance-lab.md)이며 운영 앱·데이터·N100 설정은 변경하지 않음. 로컬 36셀·측정 1,080건의 고정 계약과 정리를 통과했고 전체 9개 검사 묶음은 최종 유효 결과 기준 2,700건 통과·기존 promtool 미설치 1건 건너뜀임. [검증 결과와 원본](reviews/20261017_통합검색성능실습_검증결과.md)에 근거·한계·실패 보완을 기록함. 저장소 PR·CI·병합은 로컬 실습과 별도로 확인함. 2단계 [로컬 장애 진단·복구 실습](incident-recovery-lab.md)은 실제 검색 지연·SQLite BUSY/FULL, 실패 원자성·동일 요청 재전송·소유 자원 정리를 구현함. 검증 및 저장소 반영 상태는 [2단계 검증 기록](reviews/20261017_장애진단복구실습_검증결과.md)과 해당 PR에서 구분함. 3단계 [로컬 배포 표준화 실습](deployment-standard-lab.md)은 Git 고정 릴리스·실제 Book HTTP 재배포·readiness 오류 후 1회 롤백·변조 사전 차단을 구현함. 같은 앱 소스의 프로세스 재배포이며 새 코드 업그레이드·컨테이너·무중단·운영 배포 성공을 뜻하지 않음. 실측·검증·PR 반영은 [3단계 기록](reviews/20261017_배포표준화실습_검증결과.md)과 해당 PR을 기준으로 구분함. 세 단계 모두 운영 배포는 수행하지 않음.

후속 네 항목은 DB 잠금 분석·사례 보고서·포트폴리오/면접 자료·실제 다른 앱 버전의 컨테이너 교체임. [DB 실습지](20261018_DB잠금_실습지.md)와 [면접 답변](20261018_DevOps_면접답변.md)을 준비하고 [컨테이너 실습](container-release-lab.md)에서 실제 두 버전 교체·역방향 읽기/쓰기·readiness 실패 롤백 각3회, 총9회를 통과함. 소유 컨테이너24개·volume9개·이미지2개를 정리했고 DB 잠금1회 추가 시연도 통과함. [검증 원본과 한계](reviews/20261018_컨테이너버전교체_검증결과.md)에 근거를 기록함. 최종 검사·저장소 반영은 해당 PR에서 확인하며, 자동 실행을 사용자의 직접 수행 경험으로 표현하지 않음. N100 운영 변경은 범위 밖임.

서버의 정기 백업·모니터를 유지하고 신규 이미지의 첫 정기 실행과 기간 경과 삭제는 실제 증적으로 판정함. 누락·실패는 기존 서버 모니터가 감시하므로 매일 ChatGPT로 수동 확인할 필요는 없음. 새 기능이나 운영 변경은 필요성이 확인된 경우에만 범위와 성공 기준을 정함. [운영 참조](operations-reference.md)·[차량 자동화](../car-care-worker/tools/automation/README.md)·[면접 자료](portfolio-devops.md)를 참조함.
