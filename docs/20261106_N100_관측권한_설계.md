## 핵심 요약

현재 구현은 Windows 전체 관측 후 Linux 전체 관측과 합성 검증을 순차 실행함. 원본 Windows 관측은 유효 정량1회에서2,114.838ms에 만료됐으며 기본 서비스·작업·프로세스 열거 합계도 이번 순차 표본에서2,492.601ms임. 기본 열거만의 시간과 전체 guard 비용을 구분해야 하며, 단일 표본으로 모든 구현의2초 달성 불가를 단정하지 않음.

**선행 구현 후보는 매 요청의 완전한 실측을 유지하는 수집 경로 최적화임.** 상주 감시·증분 캐시로 쓰기 권한을 허용하는 경로는 선택하지 않음. 원본과 동등한 전체 조회·파일 검증·조회자 신원·재검증을 유지할 수 있는지 맥 격리 시험과 Windows 격리 시험에서 먼저 입증해야 함. 최적화가 실패하면 계속 차단하며 시간 상한을 늘리지 않음.

| 결정 | 수용 조건 | 현재 결과·비고 |
|---|---|---|
| 진단과 권한 증명을 분리함 | 느린 진단 결과는 참고·준비 자료로만 사용함. lease·승격·쓰기 open에는 사용하지 않음 | Windows 읽기 component·Linux 원본 collector·offline composite 진단까지 맥 격리 구현함. native 수용은 별도임 |
| 전체 실측 우선 최적화 | 같은 요청 안의 중복 읽기 제거·조회 묶음화·독립 수집 병행을 후보로 비교함 | 성능·완전성 모두 미검증임 |
|2초 경계 유지 | 외부 guard가 요청 발행 전부터 최종 확인까지 전체 비용을 측정함. DB 보호 증명과 기존 전후 관측도 별도로 생략하지 않음 | 구성요소별2초를 더해 전체 상한으로 인정하지 않음 |
| 증분 감시는 보조 수단임 | 손실·재연결·수집 실패는 차단 사유로 쓸 수 있으나 이벤트 부재를 전체 정상 증명으로 쓰지 않음 | heartbeat·현재 timestamp만으로 complete를 만들지 않음 |
| 조회 권한은 별도 수용함 | 조회 범위·원본 신뢰·실행 신원과 결과 비공개성을 모두 검증함 | 관리자 토큰만으로 수용하지 않음 |

현행 Windows 관측은 proof당1회이며 Linux는 동일1.5초 Budget에서2회 전체 snapshot을 비교함. controller 동작 전후의 재관측은 별도 경계이며, 구성요소별 상한을 합산해 전체 상한으로 인정하지 않음.

### 2. 요청별 신선도 계약

아래는 후속 구현의 요구사항이며 현재 구현 완료를 뜻하지 않음. 진단 자료와 실제 권한 증명을 다른 형태로 구분하고, 진단 자료를 권한 검증 함수가 받아들이는 호환 경로를 두지 않아야 함.

| 순서 | 요구사항 | 거절 조건·비고 |
|---:|---|---|
|1 | 원본·승인·조회자 신뢰를 확인한 뒤 요청별 nonce와 단조 시작 시각을 발급함 | 기존 proof·시작 전 snapshot·다른 요청의 memoization 사용 금지 |
|2 | 해당 요청 이후 실제 provider 전체를 조회함 | worker별 성공이 있어도 필수 provider 하나라도 실패·누락이면 전체 실패임 |
|3 | 결과의 source·boot/process 신원·cluster/generation·config를 대조함 | boot·프로세스 시작·engine·배포판·권한·조회 대상 변경은 새 원본 대조 전 실패임 |
|4 | 요청 중 변경·교체와 provider 간 모순을 검출함 | 병행 조회가 원자 snapshot을 제공한다고 가정하지 않음. 기존 전후 재검증 또는 동등한 증명을 유지함 |
|5 | 최종 소비 시점에 원래 deadline·nonce·승인 만료를 다시 확인함 | 늦게 끝난 자식·순서가 바뀐 응답·wall clock 역행으로 신선도를 연장하지 않음 |
|6 | 단일 사용 후 또는 오류 시 해당 proof를 폐기함 | 이전 성공을 다음 갱신·승격·open의 fallback으로 사용하지 않음 |

정적 실행 파일·서명·설정 값도 요청 간 재사용하지 않는 것이 첫 구현의 기본임. 요청 안의 재사용도 동일 경로 문자열만으로 허용하지 않음. 같은 객체·원본 bytes를 확인하고 사용 전후 교체·내용 변경을 검출할 수 있는 경우에만 동등성 시험 대상으로 삼음. symlink/reparse·hardlink·in-place 수정·서명 검증과 hash 간 교체를 포함해 검증하지 못하면 해당 최적화를 채택하지 않음.

### 3. 성능 구현 순서

| 단계 | 구현·시험 대상 | 완료 기준·비고 |
|---:|---|---|
|1 | 비권한 진단에서 service/task/process와 registry/hash/signature, 기존 running WSL 배포판의 reader 프로세스 시작 경계, Linux provider, 합성 검증을 분리 측정함 | 배포판을 기동하지 않음. 수집 실패를 유지하며 원본·probe·준비/수집 시간·불완전 시도를 구분함. 진단이 proof를 반환하지 않음 |
|2 | Windows Task 조회와 프로세스/서비스 조회의 묶음 호출 후보를 격리 환경에서 원본과 대조함 | 비활성·숨김·서브폴더·COM action·잘못된 참조·비공개 process·부분 응답까지 원본과 동등하게 실패/완료해야 함 |
|3 | Windows와 Linux처럼 독립적으로 시작 가능한 읽기를 제한된 worker로 병행하는 후보를 비교함 | 요청 nonce 이후 시작·전체 deadline 공유·출력 제한·부모 종료 시 자식 정리·전체 수집 및 재검증 보존. 실제 controller 부모 신원도 다시 설계/검증함 |
|4 | 요청 내 중복 hash/서명 제거 후보를 제한적으로 비교함 | 같은 관측의 검증된 객체에 한정하고 교체 시험을 통과함. 공유 캐시나 다음 요청 재사용 금지 |
|5 | Windows 격리 native 시험 후 승인 범위 안에서 N100 읽기 전용 성능 수용을 수행함 | 전체2초·동등한 보안 거절·7앱/PG/보호 프로세스 경계·자원/외부 health를 함께 확인함 |

단계2~4는 후보이며 무조건 모두 채택하지 않음. 단일 worker에서 실패했던 호출을 병행한다고 권한·완전성 실패가 해소되지는 않음. N100 기존 strict3회 시도는 같은 실패를 더 반복하지 않으며 새로운 구현·격리 검증·독립 검토 없이 다시 호출하지 않음. 새 성능 시험은 시도 예산과 중단 조건을 사전에 정하고, 한두 번의 성공으로 장시간·피크 수용을 선언하지 않음.

상주 observer는 초기 graph·변경 이력·요청 신선도를 분리하는 향후 후보일 뿐임. Windows registry/task/service/process 및 코드 파일, Linux Docker/Kubernetes/systemd/cron/process/mount 전체에 대한 변경 누락 방지·재연결·overflow·조회 권한 변동·TOCTOU 경계가 입증되지 않았으므로 현재 제어기에 연결하지 않음. 이벤트 기반 invalidation만 추가해도 캐시를 권한 proof로 승격할 수 없음.

### 5. systemd 환경 파일 지원의 선행 조건

`collect_systemd`는 `EnvironmentFiles`가 비어 있지 않으면 현재 명시적으로 거절함. 이 거절만 제거하면 파일 변경이 provider pin에 반영되지 않을 수 있으므로 지원 완료가 아님. 현재 경로 파싱 결과0개는 환경 파일 부재의 증거가 아님.

| 조건 | 후속 구현 기준 | 미지원 시 처리 |
|---|---|---|
| 구조화된 원본 | 파일 경로·필수/선택 여부·순서를 손실 없이 파싱함. 실제 지원 systemd 출력 형식을 fixture와 원본 문서로 고정함 | 임의 whitespace split·추측 파싱 금지, 차단함 |
| 경로 의미 | 복수 파일·escape·선택 파일 부재·specifiers·glob·drop-in 변경을 명시 지원하거나 거절함 | 모르는 형식을 빈 목록으로 처리하지 않음 |
| 원본 파일 | 신뢰한 소유자·상위 경로·종류·link/교체 방어와 크기/시간 예산을 검증함 | 읽기 불가·중간 경로 변경·권한 실패를 부재와 구분해 차단함 |
| 자료 비공개 | 원문을 실행·source·환경 변수 주입·출력하지 않음. 구성 pin에 필요한 원본 결합만 내부 처리함 | env 비밀값을 문서·로그·승인 파일로 복제하지 않음 |
| 의미와 권한 | raw bytes hash가 안전한 환경 내용이나 제한된 DB/OAuth 역할을 증명하지 않음 | credential-bearing 관리/앱 프로필은 별도 검증 전 거절 유지함 |
| 재검증 | 파일 내용·부재→생성·교체·unit reload·drop-in 변경을 연속 관측에 반영함 | 읽은 디스크 파일이 실행 중 프로세스 환경과 같다고 단정하지 않음 |

## 검토 결과

최초 PR #496은 설계 문서와 기존 문서 연결만 수행함. 이후 아래 별도 비권한 진단 도구·시험을 추가했으며 기존 제어 runtime·workflow·운영 plan/approval은 변경하지 않음. native 수용 실패를 해소한 것으로 처리하지 않음. 전문 검토자는 구현에 참여하지 않고 실제 원본과 최종 diff의2초·권한·운영 보호 경계를 검토함. 최종 검증·검토·PR/main 결과는 해당 PR에 기록함.

## 후속 조치

### Windows 기본 열거 진단 — 맥 구현

별도 도구 [n100_ha_windows_diagnostic.py](../infra/k8s/tools/n100_ha_windows_diagnostic.py)와 [PowerShell driver](../infra/k8s/tools/n100-ha-windows-diagnostic.ps1)를 추가함. source helper와 driver의 외부 SHA를 모두 요구하며, 원본 helper 전체를 실행하지 않고 `Get-LegacyWindowsObservation`의 정확한 서비스·작업·프로세스 조회 pipeline AST만 추출함. 함수 중복·query 중복·query 변경·parse 오류·pin 불일치는 조회 전에 거절함. source의 parent/argv 검사를 우회한 전체 guard 실행 경로를 만들지 않음.

| 구분 | 실제 구현 범위 | 한계·비고 |
|---|---|---|
| 실행 | `--collect-local --source-sha256 <검토한 helper SHA> --driver-sha256 <검토한 driver SHA>`를 명시한 Windows 로컬 실행만 지원함 | 원격 접속·WSL 시작·root·ACL·서비스·DB·plan/approval·Go 없음. 이번 N100 실행은 미수행임 |
| 원본 결합 | 읽은 helper bytes를 pin한 후 메모리 전달하며, 검증한 driver bytes를 encoded command로 실행함 | 파일 경로를 다시 실행해 hash 이후 교체되는 경로는 사용하지 않음. 운영 bundle에는 포함하지 않음 |
| 환경 | Windows 시스템 디렉터리 API로 찾은 PowerShell·시스템 module 경로·최소 환경만 사용함. 호출자 SystemRoot/PATH/PSModulePath를 실행 경로 선택에 사용하지 않음 | Windows PowerShell5.1 native 동작·현재 N100 권한 및 module 호환 수용은 확인 필요임 |
| 결과 | 각 query의 정렬 포함 시간·개수 또는 `query_failed/count=null`만 기록함 | `kind=ha-enumeration-diagnostic`, `authority=false`, `ready=false`; `complete/verified/nonce` 권한 응답을 생성하지 않음 |
| 시간·출력 | 준비부터 남은8초를 자식에 전달하고 반환 후 전체 경과를 재확인함. stdout16KiB 상한·stderr 폐기·입력 제한·자기 자식 종료와 I/O thread 회수를 확인함 | OS 프로세스 생성/파일 읽기 자체의 강제 중단을 보장하지 않음. 종료/회수 시간은 별도이며 실패 시 정상 측정으로 반환하지 않음. 기존 권한 경로2초는 변경 없음 |
| 동등성 시험 | 실제 원본 AST foreach의 조회 결과 전체 속성·순서·호출 인자를 같은 fixture로 대조함 | 숨김/비활성/하위 폴더/COM 작업·null process 경로 보존과 같은 개수의 다른 내용 거절을 시험함. Windows provider native 동등성 수용은 아님 |
| 분리 시험 | 원본 최상위/guard 함수 본문을 실행하지 않음. 기존 composite/WindowsFence는 진단 JSON을 거절함 | 진단 결과를 권한 proof로 변환하는 호환 경로 없음 |

새 fixture는 PowerShell이 없으면 skip하지 않고 실패함. 맥에서는 실제 PowerShell parser·pipeline을 쓰되 Windows provider만 합성 대역으로 교체함. 시간 수치는 합성 조회의 실행 시간이므로 N100 성능 근거가 아님. 최종 검사 수·검토·PR/main 결과는 구현 PR에 기록함.

### 전체 읽기 단계 진단 — 맥 격리 구현

Windows·Linux·합성 단계의 남은 진단과 연결 실패 시험을 한 변경으로 추가함. 각 도구의 `measured`는 해당 진단 계산이 끝났다는 의미이며 native 전체 graph·권한·서비스 전환 수용이 아님. 모든 결과는 `authority=false`, `ready=false`로 고정하고 원본 권한 receipt를 내보내지 않음.

| 도구 | 실제 실행 경계 | 결과·시간 해석 |
|---|---|---|
| [Windows component](../infra/k8s/tools/n100_ha_windows_profile.py) / [PS driver](../infra/k8s/tools/n100-ha-windows-profile.ps1) | 검토한 helper 전체 SHA hard pin 후 읽기 helper10개, 원본3종 foreach 본문과 startup 구간만 추출함. registry·파일 hash·서명·Task XML 호출을 계측함 | caller/parent 신원 구간과 guard/reader/DB는 로드하지 않음. 원본 동작 전체를 실행한 것으로 표현하지 않음 |
| Windows context | 비공개 실제 plan 대신 분류용 sentinel root를 사용하며 `ownParent=false`로 검증하지 않은 부모 프로세스를 제외하지 않음. 서비스 PID/이미지 관계는 유지함 | 서로 분리한 component마다 원본2초 Watch를 새로 사용함. 실제 전체 guard의 공유2초 성능과 다르며 현재 권한 검사를 완화하지 않음 |
| Windows metrics | query/component는 입력 raw row 수, startup은 원본 map 항목 수를 기록함. 중첩 helper의 calls는 시도 수, count는 성공 operation 수이며 실패 후 count=null을 유지함 | 중첩 registry/hash/signature/XML 경과 시간은 inclusive임. 재귀 누적은 wall time보다 클 수도 있으며 합산하거나 전체 시간과 비교해 수용하지 않음. query 실패 시 종속 component는 not_run임 |
| Windows 실행 한도 | 고정 시스템 PowerShell·최소 환경·검증 bytes 메모리 실행을 사용함.8초 collection budget, 입력256KiB, 출력16KiB/line·16line·64KiB 누적을 제한함 | OS spawn/파일 I/O 자체 강제 중단과8초 이내 cleanup 완료는 보장하지 않음. timeout에는 검증한 마지막 progress만 blocked 상태로 보존하며 정상 완료로 승격하지 않음. malformed/초과 출력은 폐기함 |
| Windows 진행·회수 |7단계 전후14 progress와 최종 report1개를 전송함. 소유한 자식을 종료하며 reader/writer가 자기 pipe를 닫도록 함 | 살아 있는 reader가 buffered pipe lock을 가진 경우 parent가 close로 다시 무한 대기하지 않음. stdout 상속 descendant fixture에서도 bounded cleanup_incomplete를 반환하고 거절함. 기존 프로세스를 광범위하게 종료하지 않음 |
| [Linux collector](../infra/k8s/tools/n100_ha_linux_diagnostic.py) | 고정 경로의 source bytes와 외부 SHA를 확인해 메모리 모듈을 만들고, 원본 evaluate를 호출함. 실제 collector·provider·I/O·validation·stability·signal을 감쌈 | 원본 root gate와 같은1.5초 Budget 안의2회 snapshot·검증·digest·signal 복구를 유지함. 계측 overhead도 해당 예산을 소비함 |
| Linux 시간/권한 | 입력 전달·source 읽기/compile·decode 준비는 evaluate timer 밖임. CLI는 Linux에서만 원본 reader로 실행하며 root/sudo fallback 없음 | 전체 standalone 실행이1.5초라는 의미가 아님. Docker socket·K3s 관리 키·root 조회의 관리 능력이 읽기 API 호출로 최소화되는 것도 아님 |
| [Offline composite](../infra/k8s/tools/n100_ha_composite_diagnostic.py) | 검토한 validator SHA를 hard pin하고 원본 verify를 실행한 뒤 반환 receipt를 즉시 폐기함 | 준비 시간과 verify 호출 시간을 분리함.2초 초과 계산은 blocked임. Windows/WSL/IPC/DB/live freshness 성능이나 실제 승인 증거가 아님 |

Linux와 composite 입력은 기존 request JSON을 stdin으로만 받고1MiB를 초과하면 거절함. source·원본 request·secret/env·경로·계정·원본 예외는 출력하지 않음. Linux 거절 이유는 검토한 source의 literal deny reason으로 제한하며 나머지는 고정 오류 분류로 출력함. `--collect-local` 또는 `--validate-offline`과 검토한 source SHA를 명시해야 하며 출력물을 plan·approval·lease 증명으로 바꾸는 호환 경로는 없음.

| 격리 검증 | 확인한 내용 | native로 확대하지 않을 범위 |
|---|---|---|
| Windows 원본 대조 | helper·foreach 본문·startup·고정 interop 선언의 실제 AST 원문, raw task/process 결과·실제 파일 hash·registry 재귀·서명/참조 호출·Task XML 실패를 대조함 | registry 등 Windows 전용 provider의 Mac 부재는 원본과 동일 실패로 남김. 실제 Windows5.1 provider 동등성은 확인 필요임 |
| Linux 원본 대조 | 실제 collect_snapshot/_collect_snapshot 본문을 합성 provider 경계로 실행하여2회 순서·같은 Budget·root 거절·부분 실패·1.5초 signal 및 기존 timer 보존·복구를 확인함 | 실제 root/K3s/Docker 관리 조회는 이번 맥 시험으로 수용되지 않음 |
| 연결·거절 시험 | 원본 Linux의 두 snapshot 검증 receipt를 합성 입력에 연결해 원본 composite를 실행함. Linux 진단 보고서를 receipt 자리에 넣으면 거절됨 | 진단 결과끼리 합성해도 권한이 생기지 않음. fake approval·provider는 실제 운영 승인이나 현장 증거가 아님 |
| 비공개성·실패 | pin/중복 JSON/형식·원본 mutation·timeout·오류·report 치환을 확인하고 private canary가 출력되지 않음을 검사함 | 합성 fixture 실행 시간은 N100 성능 측정으로 사용하지 않음 |

후속 읽기 전용 Windows 소유자 메타데이터에서 Python 후보1개·상위9개에 current5/system2/administrators1/TrustedInstaller1, 기존 기준의 비신뢰 쓰기 규칙0·reparse0을 확인함. 경로·계정·SID는 출력하지 않았고 ACL/소유자/실행 권한은 변경하지 않음. **TrustedInstaller를 발견했다는 이유만으로 현재 trust allowlist를 확대하거나 실행을 허용하지 않음.** 소유자 위치·실행 신뢰·비공개 marker·Linux 전체 reader 및 third-party process 분류 수용은 여전히 별도임.

**첫 미완료 수용은 실제 Windows 병목 해소와 전체 관측2초·권한·EA 경계 확인임.** 검토한 PR #498 소스를 메모리에서 실행한 읽기 전용 진단에서 Windows services 조회288건은1403.7403ms, 다음 tasks 조회 진입 후 외부8초 제한으로 중단됨(전체8198.4449ms, 소유한 자식 정리 확인). tasks 완료 시간이나 전체2초 수용으로 해석하지 않음. 기존 실행 중 WSL 기본 UID1000은 `complete_linux_reader_required`로 거절됐으며 provider 조회는0회임. 부팅·예약 작업·bootstrap·Hyper-V 상태·보호 프로세스 수 전후 대조는 일치했고 Portal 전후 각3회는 HTTP200임. 개별7앱 health·EA 거래 지연·피크 자원은 확인 필요임. 새 진단은 기존 strict 조회3회 제한을 우회한 전체 guard 재시도가 아님. UID0·ACL·runtime 신뢰·EA 분류·서비스·VM·Hyper-V·재부팅을 임의로 변경하지 않음. 실제 운영 변경은 대상·되돌림·실행 순서를 준비하고 적용 직전에 사용자 확인을 받음.

### Kubernetes 조회 캐시 쓰기 차단 — 2026-11-07

| 구분 | 변경·검증 | 비고 |
|---|---|---|
| 문제 | API 조회만 해도 kubectl 기본 discovery/HTTP cache가 디스크 파일을 생성할 수 있음 | HOME을 존재하지 않는 경로로 지정하는 것만으로 root 쓰기를 막지 못함 |

| 보존 | 원본 TLS·kubeconfig 검증, shared1.5초, 두 스냅샷, root 거절, 조회 실패 거절을 유지함 | root 승인·권한 확대·N100 설치가 아님 |

| 남은 경계 | 기존 root로 한 번 조회하는 제안도 아직 승인·실행되지 않음 | Windows timeout·전체2초 수용과 별개임 |
