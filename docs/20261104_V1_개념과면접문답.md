# V1 개념과 면접 문답 — 하나씩 이해하는 14단계

작성·대조일: 2026-11-04. [학습 안내와 최근 변경](20261104_V1V2_학습안내.md)을 먼저 보면 전체 지도를 알 수 있습니다. 이 자료는 「DevOps 취업 경험 항목 찾기」 채팅의 정리·배포 완료 보고, PR #482·#483, 현재 코드·문서를 함께 대조했습니다.

V1은 N100에서 실행하는 개인 서비스입니다. 아래 답변은 프로젝트 동작을 설명하는 연습문입니다. 본인이 직접 한 작업은 실제 범위에 맞춰 말하고, 자동 실행·독립 검토 결과를 본인의 수동 장애 대응 경험으로 바꾸지 않습니다.

## 1단계. V1은 어떤 프로젝트인가?

**한 줄 핵심: 개인 데이터를 관리하는 앱과, 그 앱을 안전하게 운영하는 장치를 함께 만든 프로젝트입니다.**

책 메모·영상 메모·뉴스·파일·차량 정보를 관리합니다. Portal은 각 서비스로 가는 입구이자 검색 결과를 모아 보여주는 창구입니다. Book·YouTube·Crawler는 각자 기능과 데이터를 관리합니다.

```text
사용자 → Portal
          ├ 책 검색 요청 → Book
          ├ 영상 검색 요청 → YouTube
          └ 뉴스 검색 요청 → Crawler
```

서비스를 나누면 따로 수정·재기동하기 쉬워지고 한 서비스 실패가 다른 기능에 미치는 영향을 줄일 수 있습니다. 다만 모두 같은 N100을 쓰므로 자원 부족이나 장비 장애는 함께 영향을 줄 수 있습니다.

**면접 질문 1. V1 프로젝트를 설명해 주세요.**

> 개인 데이터를 관리하는 여러 서비스를 N100 한 대에서 운영하는 프로젝트입니다. Portal에서 각 서비스와 통합 검색을 연결하고, 저장 중복·편집 충돌·배포·관측·백업 복구도 함께 다뤘습니다. 단일 장비이므로 물리적인 고가용성 구성은 아닙니다.

이해 확인: “한 서비스의 실패 영향을 줄임”과 “어떤 장애에서도 서로 영향이 없음”은 같은 말인가요? **다릅니다. 공유하는 호스트 자원은 공통 장애점입니다.**

근거: [README](../README.md), [면접 요약](portfolio-devops.md).

## 2단계. 서버·이미지·컨테이너는 무엇인가?

**한 줄 핵심: 이미지는 실행 재료, 컨테이너는 그것으로 실제 실행한 앱입니다.**

N100은 실제 컴퓨터입니다. Windows에서 WSL2로 Ubuntu Linux 환경을 사용합니다. 앱 코드와 필요한 라이브러리를 이미지로 묶고, 그 이미지를 실행해 컨테이너를 만듭니다. Dockerfile에는 이미지를 만드는 방법을 적습니다.

Compose는 여러 컨테이너의 실행 설정을 묶어 관리합니다. K3s는 Kubernetes 배포판으로 앱의 배치·준비 상태·교체·저장소 연결을 관리합니다. V1 웹 앱 4개는 K3s에, 차량관리·SystemAgent·HomeOps 같은 보조 서비스는 Compose에 있습니다.

**면접 질문 2. 왜 K3s와 Compose를 같이 사용하나요?**

> 웹 앱은 Deployment·readiness·PVC로 관리하고, 호스트에 가까운 보조 작업은 Compose로 나눴습니다. 두 경로를 쓰므로 실행 주체를 확인해 같은 데이터를 쓰는 앱이 양쪽에서 중복 실행되지 않도록 했습니다.

이해 확인: 이미지가 같으면 데이터도 같나요? **아닙니다. 연결한 설정·Secret·저장소가 달라질 수 있습니다.**

근거: [운영 참조](operations-reference.md), [실행 주체 검사](../scripts/runtime-service-state-reader.py).

## 3단계. 사용자 요청은 어떻게 앱에 도착하는가?

**한 줄 핵심: 외부 요청은 여러 전달 구간을 거치므로, 어디까지 도착했는지 나눠 봐야 합니다.**

DNS는 도메인 이름을 접속 대상과 연결합니다. HTTPS의 TLS는 통신 암호화와 상대 인증에 사용합니다. 로그인 권한 확인은 앱에서 별도로 처리합니다.

```text
브라우저 → Cloudflare Tunnel → Caddy → K3s Service → 앱
```

Caddy는 요청을 알맞은 내부 앱에 전달하는 reverse proxy입니다. Service는 교체되는 Pod 앞의 접속점입니다. Portal은 NodePort를 통해 진입하고, 차량 OAuth callback은 Caddy를 거치지 않는 별도 Tunnel 경로입니다.

앱에서는 FastAPI가 요청·입력 검증을 처리하고 Jinja2로 HTML을 만듭니다. 세션·쿠키로 로그인 상태를 이어갑니다. 쿠키의 Secure·HttpOnly·SameSite, Origin 검증은 각각 다른 조건을 제한하므로 인증 하나로 모두 해결되는 것은 아닙니다.

**면접 질문 3. 서비스에 접속이 안 되면 무엇부터 확인하나요?**

> 어떤 요청이 어디까지 도달했는지부터 확인합니다. DNS·Tunnel·Caddy·Service·앱을 나누어 상태와 로그를 보고, 내부 앱 정상과 외부 접근 정상을 구분합니다. 상태 코드 하나만 보고 바로 재시작하지 않습니다.

이해 확인: Caddy가 응답했다고 Book의 저장까지 정상인가요? **아닙니다. 요청 전달·앱 처리·저장 성공은 별도로 확인합니다.**

근거: [공개 요청 경로](cloudflare-tunnel.md), [Book 요청 처리](../book-memo/app/main.py).

## 4단계. 검색을 동시에 하고 기다림을 제한하는 이유

**한 줄 핵심: 서로 독립적인 조회는 동시에 요청하고, 느린 대상 때문에 전체가 계속 기다리지 않게 합니다.**

책·영상·뉴스 검색이 각각 1초라면 순서대로 할 때는 대략 3초, 동시에 할 때는 대략 1초를 기다릴 수 있습니다. 다른 처리 비용을 제외한 설명용 예시입니다. 병렬 조회도 가장 늦은 요청의 영향을 받으므로 최대 대기 시간이 필요합니다.

V1 검색에는 1.5초의 조회 대기 예산이 있습니다. 정상 결과는 유지하고 시간 초과한 대상의 실패를 구분합니다. 전체 브라우저 응답을 반드시 1.5초 안에 끝낸다는 보장은 아닙니다.

```text
Book: 응답 없음 → 책 검색 실패 표시
YouTube: 성공 → 영상 결과 표시
Crawler: 성공 → 뉴스 결과 표시
```

“검색 성공·0건”과 “검색 자체 실패”도 다릅니다. 실제로 복구 중임을 확인하지 않았다면 “복구 중”이라고 표시하지 않습니다. 또한 책 등록 뒤 발급된 ID로 메모를 저장하는 작업은 앞선 결과가 필요하므로 순서를 지켜야 합니다.

**면접 질문 4. Book 검색만 응답하지 않으면 어떻게 처리하나요?**

> 정해진 시간까지만 기다리고 Book의 시간 초과를 표시합니다. 정상 응답한 영상·뉴스 결과는 유지합니다. 결과 0건과 조회 실패를 구분하고 확인되지 않은 복구 상태는 안내하지 않습니다.

이해 확인: 모든 작업을 병렬로 하면 되나요? **아닙니다. 앞 작업의 결과가 필요한 작업은 순차 처리합니다.**

근거: [실제 검색 코드](../portal-web/app/services/global_search.py).

## 5단계. SQLite와 트랜잭션

**한 줄 핵심: SQLite는 별도 DB 서버 없이 쓰는 DB이고, 트랜잭션은 관련 변경을 함께 확정하는 단위입니다.**

개인용 서비스에서는 별도 DB 서버를 운영하는 부담을 줄일 수 있습니다. 테이블이 많다고 무조건 다른 DB가 필요한 것은 아닙니다. 동시 쓰기·다중 서버 접근·복제·고가용성 요구를 보고 판단합니다.

혼자 사용해도 두 탭의 저장, 중복 클릭, 응답 지연 후 재시도가 겹칠 수 있습니다. 사용자 한 명과 요청 한 건은 다릅니다. SQLite의 쓰기 잠금 때문에 다른 요청이 기다리거나 실패할 수 있습니다.

트랜잭션은 메모 변경과 요청 처리 기록처럼 관련된 변경을 모두 확정하거나 모두 취소하게 묶습니다. 메모만 저장되고 처리 기록이 빠지면 나중 재시도에서 이미 저장했는지 구분하기 어렵습니다.

**면접 질문 5. 왜 SQLite를 선택했고 어떤 제약을 고려했나요?**

> N100 한 대의 개인 서비스라 별도 DB 서버의 운영 부담을 줄이려고 선택했습니다. 대신 동시 쓰기 잠금·트랜잭션·백업 일관성을 관리합니다. 여러 서버의 쓰기나 복제 요구가 커지면 저장 방식을 재검토하겠습니다.

이해 확인: DB 파일을 Git에 넣어 관리하나요? **아닙니다. 소스와 운영 데이터 영역을 분리합니다.**

근거: [메모 저장](../book-memo/app/services/book_service.py), [DB 오류 응답](../book-memo/app/services/database_errors.py).

## 6단계. 메모 ID·요청 ID·버전은 다른 것

**한 줄 핵심: 메모 ID는 대상, 요청 ID는 저장 작업, 버전은 편집의 기준 시점을 나타냅니다.**

| 값 | 답하는 질문 | 설명용 예시 |
|---|---|---|
| 메모 ID | 어느 메모를 바꾸나? | 메모 10번 |
| 요청 ID | 어느 저장 작업인가? | 요청 A |
| 예상 버전 | 어떤 상태를 보고 편집했나? | 버전 1 |

실제 요청 ID는 UUID입니다. 여기의 A·B는 이해를 돕는 축약 표기입니다.

```text
요청 A: 메모 10번에 “3장까지 읽음” 저장
 → 서버 저장 완료, 성공 응답만 유실
 → 같은 내용을 다시 보냄: 요청 A 유지
 → 서버가 이미 처리한 결과를 찾아 재수정하지 않음

다음 수정: “4장까지 읽음”으로 내용을 바꿔 저장
 → 새로운 작업이므로 요청 B 사용
 → 이 응답도 유실되어 같은 내용을 재전송: B 유지
```

서버는 ID만 보지 않고 작업 종류와 payload 해시도 비교합니다. payload는 저장 판단에 쓰는 입력 묶음이며 메모 ID·본문·예상 버전 등도 들어갑니다. 같은 ID에 다른 입력을 보내면 충돌로 거부합니다. ID가 없으면 이 요청 기반 중복 보호를 보장하지 않습니다.

다른 탭의 편집 충돌은 별도 문제입니다. A 탭이 버전 1을 보고 저장해 버전 2가 됐다면, B 탭의 새로운 요청이라도 예상 버전 1의 편집은 거부합니다. 입력은 유지하고 최신 내용과 비교할 기회를 줍니다.

**면접 질문 6. 저장 성공 응답을 못 받으면 재시도할 때 어떻게 하나요?**

> 같은 작업이면 같은 요청 ID와 입력으로 재시도합니다. 이미 처리한 요청이면 결과 식별자를 재사용해 다시 수정하지 않습니다. 저장 데이터와 처리 기록은 같은 트랜잭션에 넣고, 새로운 편집의 충돌은 버전 검사로 따로 처리합니다.

이해 확인: “4장까지 읽음”을 B로 보낸 뒤 내용 변경 없이 다시 보내면? **B 그대로입니다.** 새 ID를 만들면 같은 작업의 재전송이라는 연결이 끊깁니다. 이 보호는 지정된 저장 경로의 것이며 모든 HTTP 응답 바이트를 그대로 재전송하거나 전체 시스템의 exactly-once를 보장한다는 뜻은 아닙니다.

근거: [ID·해시·버전 검사](../book-memo/app/services/write_safety.py), [저장 트랜잭션](../book-memo/app/services/book_service.py), [브라우저 ID 유지](../book-memo/app/static/js/form-drafts.js), [회귀](../tests/book_memo/test_memo_recovery.py).

## 7단계. Pod·Service·준비 상태·저장소

**한 줄 핵심: 앱이 실행되는 것, 요청을 받을 준비가 된 것, 데이터가 남는 것은 각각 확인해야 합니다.**

Pod는 컨테이너를 실행하는 Kubernetes 기본 단위입니다. Deployment는 원하는 Pod 수와 교체를 관리하고 replica는 사본 수입니다. Service는 실제 연결할 준비된 Pod 앞의 접속점입니다. namespace는 논리적인 구분입니다.

readiness는 요청 수용 준비를, liveness는 재시작 판단에 쓰는 상태를 검사합니다. Running이라고 모든 기능이 정상인 것은 아닙니다. PV/PVC는 저장 공간과 그 사용 요청으로 Pod와 데이터의 수명을 분리합니다. Job은 완료되는 작업, CronJob은 일정에 따라 Job을 만드는 선언입니다.

Book·YouTube·Crawler는 단일 writer를 유지합니다. Portal만 공유 상태·파일 쓰기 조정·온라인 snapshot을 검증한 제한 롤링 중 최대 2개를 허용합니다. Pod 수를 늘리는 것만으로 쓰기 안전성이나 물리 HA가 생기지는 않습니다. 파일 생성도 “존재 확인 후 쓰기” 사이에 경합이 생길 수 있어 배타적 생성 등 별도 보호를 씁니다.

**면접 질문 7. Pod가 Running인데도 서비스가 실패할 수 있나요?**

> 가능합니다. readiness, Service의 연결 대상, 통신, DB와 실제 업무 동작은 별도로 확인해야 합니다. PVC 데이터가 남아 있는지와 잘못된 동시 writer가 없는지도 봅니다.

이해 확인: PVC가 있으면 백업이 없어도 되나요? **아닙니다. 디스크 손실·오삭제·논리 손상을 위한 복구 사본은 별도입니다.**

근거: [K3s 운영](../infra/k8s/README.md), [writer 경계](operations-reference.md), [파일 저장](../portal-web/app/services/file_store.py).

## 8단계. 새 코드가 실제 서비스가 되기까지

**한 줄 핵심: 코드 검사, 서버 동기화, 이미지 공급, 실행 교체, 기능 검증을 따로 확인합니다.**

Git commit은 소스의 특정 시점입니다. 이미지는 그 소스로 만든 실행물이고 digest는 이미지 내용을 식별합니다. tag는 이름이라 다른 내용을 가리킬 수 있습니다. Mac ARM64와 N100 AMD64도 구분합니다.

```text
PR·검토·CI → main → 배포 분류
 → 승인 범위의 정확한 소스 동기화·이미지 공급·실행 교체
 → readiness·업무 동작·데이터·health 확인
```

11월 4일 정리에서는 **기존 수동 Compose 배포 도구**의 fetch와 강제 reset을 없앴습니다. 현재는 별도 절차에서 CI·승인을 확인하고 동기화한 뒤, 도구가 승인된 40자리 SHA와 HEAD·origin/main 일치, main 브랜치, 깨끗한 작업공간을 검사합니다. 도구가 알아서 CI 성공이나 사용자 승인을 조회해 주는 것은 아닙니다.

안전 자동배포 도구와 K3s 이미지 교체 경로는 별개입니다. 수동 Compose 도구가 모든 앱의 배포를 대신하거나 이번 학습 문서가 운영 실행을 승인하는 것은 아닙니다.

**면접 질문 8. 배포 도구에서 강제 reset을 제거한 이유는 무엇인가요?**

> 배포 중 검토하지 않은 코드로 바뀌거나 로컬 작업이 지워지는 일을 막기 위해서입니다. 소스 동기화와 배포 실행을 분리하고 승인된 정확한 커밋과 깨끗한 작업공간에서만 실행하도록 했습니다. 조건이 다르면 덮어쓰지 않고 중단합니다.

이해 확인: CI 성공이면 N100 배포도 끝났나요? **아닙니다. 실제 이미지·실행 상태·기능을 별도로 확인해야 합니다.**

근거: [수동 배포 도구](../scripts/deploy-n100.sh), [안전 자동배포](n100-github-auto-deploy.md), [최근 정리](20260921_프로젝트보완_개발계획.md#저장소-정리와-검증-실행-범위-개선).

## 9단계. 검사를 줄였는데 어떻게 안전을 유지하는가?

**한 줄 핵심: 검사 결과를 무시하는 대신, 변경 영향에 맞는 검사를 선택합니다.**

차량 파서만 바꿨는데 관련 없는 Portal 화면 검사까지 항상 실행하면 중복 비용이 생길 수 있습니다. 최근 정리는 서비스 검사와 maintenance를 기본으로 하고, 필요한 quality·browser를 선택하게 했습니다. Portal 변경은 Portal 쪽 검사, Book·YouTube 변경은 해당 브라우저 검사를 연결합니다.

공용 런타임·인프라·의존성·분류가 불명확한 변경은 전체 검사로 넓힙니다. 문서만 바뀌면 문서·링크·참조 계약을 검사합니다. 검사 목록의 빠진 파일·중복 배정을 확인하고, 빠져 있던 JavaScript 회귀 검사도 소유 테스트에 연결했습니다.

**면접 질문 9. CI 선택 실행은 검사를 생략하는 것 아닌가요?**

> 변경 영향이 분명한 경우 관련 검사로 범위를 정하는 것입니다. 공용 변경이나 영향이 불명확하면 전체 검사를 유지하고, 테스트 누락·중복 배정도 검증합니다. 실패를 성공으로 처리하거나 필수 보안·배포 정책을 끄는 방식으로 줄이지 않았습니다.

이해 확인: 검사 실행 개수가 줄었다는 사실만으로 품질 개선을 증명하나요? **아닙니다. 필요한 계약이 계속 검증되는지 확인해야 합니다. 시간 절감률도 실제 측정 없이 말하지 않습니다.**

근거: [검사 선택](../tests/run_service_tests.py), [검사 원본 목록](../tests/ci_test_matrix.json), [CI 연결](../.github/workflows/ci.yml).

## 10단계. 운영 의존성과 테스트 의존성은 왜 나누는가?

**한 줄 핵심: 서비스를 실행할 때 필요한 패키지와 검사할 때만 필요한 패키지는 다를 수 있습니다.**

운영 의존성은 앱 실행에, 테스트 의존성은 테스트 도구에 필요합니다. 운영 이미지에 검사 전용 패키지까지 넣으면 관리할 패키지와 취약점 점검 범위가 늘어날 수 있습니다.

최근 정리에서는 Portal의 미사용 requests를 제거하고, SystemAgent·Crawler·HomeOps에서 TestClient용 httpx를 운영 requirements에서 CI 테스트 의존성으로 이동했습니다. **Portal의 httpx는 실제 검색에 사용하므로 유지합니다.** 이름이 같다고 모든 서비스에서 지우는 방식은 아닙니다. 호출하지 않는 차량 파서 함수 2개도 제거했습니다.

중지된 백업 CronJob은 다른 실행기가 템플릿으로 사용할 수 있습니다. 멈춰 있다는 이유만으로 삭제하면 안 됩니다. 복귀 이미지·백업 증거·설치 도구도 같은 이유로 실제 참조를 확인해야 합니다.

**면접 질문 10. 미사용 패키지나 코드를 어떻게 판단했나요?**

> 호출·import·실행 경로와 테스트 용도를 확인했습니다. 운영에서 안 쓰지만 테스트에 필요한 것은 테스트 쪽으로 옮기고, 실제로 쓰는 패키지는 유지했습니다. 백업 템플릿이나 복귀 자산도 현재 실행 중인지보다 참조와 복구 역할을 보고 보존했습니다.

이해 확인: requirements에서 줄인 항목 수만큼 메모리가 절약됐다고 말할 수 있나요? **아닙니다. 실행 비용·이미지 크기·취약점 변화는 각각 측정해야 합니다.**

근거: [Portal 요구 패키지](../portal-web/requirements.txt), [테스트 패키지](../tests/ci_test_matrix.json), [PR #482](https://github.com/Len-Yoon/personal-server/pull/482).

## 11단계. 지표·알림·SLO는 무엇을 확인하는가?

**한 줄 핵심: 화면이 열린다는 사실과 업무가 정상이라는 사실을 구분합니다.**

Prometheus는 지표 수집·질의, PromQL은 지표 계산, Grafana는 시각화를 맡습니다. Alertmanager와 Relay는 알림 전달 경로를 구성합니다. 수집 성공과 Telegram 단말 수신은 다른 증거입니다.

외부 health는 사용자 접근 경로를, 뉴스 freshness는 마지막 정상 수집이 얼마나 오래됐는지를 봅니다. 뉴스 페이지가 200이어도 수집은 멈췄을 수 있습니다. SLI는 품질 측정값, SLO는 기간·조건을 정한 목표, SLA는 고객과의 약속, 에러 버짓은 허용 실패 여유입니다.

일일 기록 30개나 짧은 오류 0회만으로 장기 SLO를 증명하지 않습니다. 같은 기준·관측 기간·분모·결측을 확인해야 합니다. 이번 학습 문서에서 SLO 누적이나 11월 4일 자연 수집 결과를 새로 조회하지는 않았습니다.

**면접 질문 11. HTTP 200이면 정상이라고 말해도 되나요?**

> 그 요청의 응답은 확인했지만 수집 최신성·저장·인증된 기능·외부 경로까지 모두 증명한 것은 아닙니다. 무엇을 정상으로 측정할지 정의하고 지표와 실제 업무 확인을 함께 사용합니다.

이해 확인: 지표가 없으면 값이 0인가요? **아닙니다. 미관측과 실제 0은 다릅니다.**

근거: [SLI·SLO 기준](slo-baseline.md), [최근 관측 범위](portfolio-devops.md).

## 12단계. 백업과 복원·코드 원복은 무엇이 다른가?

**한 줄 핵심: 이전 코드를 실행하는 것과 과거 데이터를 되살리는 것은 다른 작업입니다.**

이미지 rollback은 코드를 되돌립니다. DB·PVC 데이터는 자동으로 과거로 돌아가지 않으므로 이전 코드와 현재 스키마·데이터가 호환되는지 확인합니다.

백업은 복구 사본을 만들고 복원은 그 사본을 사용할 수 있게 되살립니다. V1은 Portal 온라인 snapshot → Book → YouTube → Crawler → 차량 DB 순서로 실행합니다. 암호화 원격 사본을 재다운로드해 무결성과 격리 복원을 확인하고, 안전 조건을 충족한 뒤 보관 정책으로 정리합니다. 암호화는 내용 보호, checksum은 바이트 변경 확인입니다.

RTO는 복구 시간 목표, RPO는 허용 데이터 손실 시간 범위 목표입니다. DR에는 데이터 외에도 장비·이미지·설정·권한·키 준비가 필요합니다. 별도 Linux VM의 합성 Book 복구를 실제 N100 전체의 물리 DR로 확대하지 않습니다.

**면접 질문 12. 백업 파일이 있으면 복구할 수 있다고 말해도 되나요?**

> 같은 원격 사본을 다시 받아 복호화·무결성·격리 복원을 확인해야 합니다. 앱 실행에 필요한 이미지·설정·권한도 필요합니다. 이미지 원복·데이터 복원·전체 환경 복구의 범위를 따로 확인합니다.

이해 확인: 이번 새 이미지 적용이 새 백업·복원 성공도 증명하나요? **아닙니다. 기존 백업 보존과 새 백업 실행 성공은 다릅니다.**

근거: [백업 운영](operations-reference.md#차량-db-백업과-자동-보관), [복원 의존성](20261027_V1_배포원복_복원의존성점검.md).

## 13단계. 이번 실제 배포와 실패·복귀 사례

**한 줄 핵심: 실패를 감지하고 이전 정상 실행으로 돌아간 뒤, 원인을 확인해 다시 적용하는 것도 배포 설계의 일부입니다.**

11월 4일 별도 운영 승인으로 PR #482의 소스 `e8b491e1ba4658697b85ea3040f0644478414d50`을 N100에 동기화했습니다. Portal·Crawler·SystemAgent·HomeOps·CarCare의 정확한 AMD64 이미지 5개를 반입하고 실제 실행을 교체했습니다. 결과 문서 커밋 `50f31aa`와 실행 소스 버전은 다릅니다.

CarCare 첫 적용은 새 이미지의 revision label(이미지에 붙은 소스 버전 표식) 상속을 검증기가 차이로 판단해 이전 healthy 실행으로 자동 복귀했습니다. 이후 정확한 이미지의 기본 label을 기대값에 반영하고 재적용했습니다. 환경·mount·네트워크·소유권 검사는 유지했습니다. 모르는 label을 전부 허용하거나 원본 실패를 지운 것은 아닙니다.

운영 결과에는 5개 실행 소스·Deployment 9개·중복 writer 부재·보호 자원·HomeOps 인증 진단을 대조한 독립 검토가 있습니다. Portal은 외부 health 3회, Crawler는 Service의 health/ready 각 3회로 구분합니다. 10초 간격 표본은 전체 시간 무중단이나 Crawler의 외부 공개 경로 검증을 뜻하지 않습니다. 이전 이미지·복귀 tag는 보존하고 검증된 중지 컨테이너·전송 파일만 정리했습니다.

**면접 질문 13. 배포가 한 번 실패했는데 최종 성공으로 판단한 근거는 무엇인가요?**

> 첫 실패와 자동 복귀를 보존한 뒤 정확한 원인이 이미지 기본 label 비교임을 확인했습니다. 기대값만 최소 보완하고 재적용했으며 실행 소스·정상 상태·보호 자원·중복 writer 부재·정해진 health를 다시 확인했습니다. 첫 시도가 성공했다고 바꾸거나 검사를 꺼서 통과시키지는 않았습니다.

이해 확인: 새 이미지 HIGH/CRITICAL 0이면 모든 보안이 보장되나요? **아닙니다. 해당 이미지·스캔 시점의 검사 결과입니다.**

근거: [운영 결과 기록](20260921_프로젝트보완_개발계획.md#저장소-정리의-n100-운영-반영--2026-11-04), [PR #483](https://github.com/Len-Yoon/personal-server/pull/483).

## 14단계. 장애를 설명하고 면접 답변을 만드는 방법

**한 줄 핵심: 증상·가설·근거·조치·사후 확인을 순서대로 말합니다.**

“안 됐는데 재시작하니 됐다”에서 끝나면 어떤 문제가 해결됐는지 알기 어렵습니다. 요청이 어디까지 갔는지, 로그·이벤트·지표에서 무엇을 봤는지, 왜 그 조치를 선택했는지 설명해야 합니다.

HomeOps와 bootstrap의 복구도 대상·조건·간격·횟수·실행 주체를 제한합니다. 상태가 불명확하거나 반복 실패하면 중단하고 판단을 넘깁니다. 호스트 전체 장애에는 같은 호스트의 감시도 한계가 있습니다.

면접 답변은 **문제 → 선택 이유 → 동작 → 검증 → 한계**의 다섯 문장으로 연습합니다. 테스트 3,275개, 문서 검사 357개, 새 이미지 스캔, 운영 health 표본은 각각 대상이 다른 기록이며 합산해 하나의 성과로 만들지 않습니다. 본인이 직접 수행한 사례는 따로 말합니다.

최근에는 검토 도구가 같은 실행의 요청 기록과 완료 기록을 서로 다른 실행으로 오인하는 문제도 보완했습니다. 도구·서버·인자가 같은 경우에만 연결하고 원본과 결과 해시는 보존했습니다. 검증 도구의 판정도 원본 근거와 대조해야 하며, 로그를 고치거나 검토자 독립성 검사를 끄는 방식으로 해결하지 않습니다.

**면접 질문 14. 이번 정리에서 가장 중요하게 배운 점은 무엇인가요?**

> 필요한 코드·의존성·검사와 복구 자산을 실제 사용 기준으로 구분해야 한다는 점입니다. 검사 선택은 안전 계약을 유지하면서 하고, 배포는 정확한 버전과 기존 상태를 보존하며 진행해야 합니다. 저장소 성공과 운영 성공, 자동 검증과 개인 경험도 구분합니다.

이해 확인: 학습 자료를 읽은 것이 직접 장애 대응 완료인가요? **아닙니다. 직접 근거를 읽고 판단한 결과를 남겨야 합니다.**

근거: [직접 학습 계획](20261026_V1_고도화학습계획.md), [운영 경계](operations-reference.md).
