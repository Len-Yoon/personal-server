## 2. 핵심 요약

Relay는 `personal-server` namespace의 Book Memo·YouTube Memo·Crawler 전용 상태 ConfigMap 세 개만 고정 조회함. `running` 상태가 5시간을 넘으면 장기 실행 경보를 보내고, 이후 같은 run ID가 `failed` 또는 `completed`로 바뀌면 별도 결과 알림을 보냄. 정상적으로 전달 기록이 저장되면 같은 사건은 재전송하지 않음. Telegram 전송 성공 후 전달 기록 저장이 실패하면 다음 polling에서 중복 전송될 수 있으므로 정확히 1회 전달은 보장하지 않음. 초기 빈 상태·형식 오류는 알리지 않음. 알림에는 Book Memo·YouTube Memo·News Hub 뉴스 수집기 중 고정 사용자 대상과 상태·영향만 포함함. 원격 경로·암호문 digest·증적 원문·내부 주소는 포함하지 않음.

상태별 전달 기록은 기존 Relay 상태 ConfigMap의 서비스별 별도 key에 저장함. Relay의 `base.yaml`을 다시 적용하면 기존 중복 방지 상태가 초기화될 수 있으므로 이 변경의 운영 적용에는 사용하지 않음.

## 3. 상세 내용

| 대상 | 상태 ConfigMap | Relay 전달 기록 key | 성공 증적 scope |
|---|---|---|---|
| Book Memo | `book-pvc-backup-state` | `book_backup_delivered_run_ids` | `book-memo` |
| YouTube Memo | `youtube-pvc-backup-state` | `youtube_backup_delivered_run_ids` | `youtube-memo` |
| News Hub 뉴스 수집기 | `crawler-pvc-backup-state` | `crawler_backup_delivered_run_ids` | `crawler-worker` |

| 단계 | 계약 | 확인 기준 |
|---|---|---|
| 상태 조회 | 위 세 고정 ConfigMap과 정확한 6개 문자열 key만 수용함 | 실행 ID·UTC 시각·stage·잠금·증적 일관성 검증. 외부 입력으로 대상 선택 불가 |
| 장기 실행 | `running`과 같은 run ID의 잠금이 5시간 이상 유지됨 | Job의 4시간 deadline에 1시간 여유를 둠. 현 runner는 `running` patch 시각을 `completed_at`에 기록하므로 해당 상태에서만 시작 시각으로 해석함 |
| 실패 알림 | `failed`, 빈 evidence, 잠금이 없거나 같은 run ID인 경우 | 서비스별 `[백업 실패]` 전송 |
| 완료 알림 | `completed`, 해제된 잠금, `completed` stage, 대상 scope와 성공·복원 증적 존재 | runner의 다중 행 증적 중 필수 4행만 검증하고 서비스별 `[백업 완료]` 전송 |
| 중복 방지 | 서비스별 전달 key에 run ID와 알림 상태를 함께 기록 | 장기 실행 후 최종 결과를 별도 전달하고 Portal 전달 key 보존 |
| 전송 실패 | Telegram 성공 전에는 사건 ID를 기록하지 않음 | 다음 polling에서 재시도. 상태 기록 실패도 성공으로 간주하지 않음 |
| 조회 불가 | 임의 상태를 추측하지 않고 오류 종류만 로그에 남김 | 동일 서비스·오류는 최초 및 1시간 간격으로 경고하고 조회 복구 시 제한을 초기화함. 해당 서비스 알림은 미검증이며 운영 확인 필요 |

## 4. 운영 적용·검토 결과

| 순서 | 작업 | 운영 경계 |
|---:|---|---|
| 1 | Relay와 세 백업 상태 ConfigMap, writer·PVC·외부 health, Git/N100 revision 사전 확인 | 읽기 전용 |
| 2 | `pvc-backup-reader.yaml`의 Role·RoleBinding만 적용하고 Relay SA의 세 상태 CM `get` 권한 확인 | `base.yaml`·상태 CM·Secret 재적용 금지 |
| 3 | 새 Relay 불변 digest 이미지를 승인된 절차로 반입하고 A8 `sre-telegram-update.sh --check`, `--apply` 수행 | 기존 Relay 상태 보존·롤백 검증 |
| 4 | 세 서비스별 수동 백업·복원과 장기 실행·실패·완료 알림, 중복 방지, Portal/Relay 외부 health 검증 | writer/PVC 조작은 별도 승인 범위 필요 |
| 5 | 각 CronJob 자동 실행 여부를 서비스별로 판단 | 각 Secret·원격 ACL·수동 성공·실제 알림 검증 선행 |

2026-09-27 N100 읽기 전용 사전점검에서는 세 writer가 각각 1/1 Ready이고 PVC는 Bound·1Gi로 조회됐으나, 세 전용 백업 runtime Secret은 아직 존재하지 않았음. 기존 Portal 백업 Secret은 별도이며 값 조회·복제하지 않았음. 각 서비스의 실제 Relay 운영 연동과 자동 실행은 전용 Secret 준비, 원격 ACL 확인, 수동 백업·복원 성공과 실제 알림 검증 뒤에만 진행함.

이 PR에서 N100 동기화·이미지 반입·RBAC 적용·Relay 갱신·실제 Telegram 전송·자동 실행은 수행하지 않음.

## 5. 확인 필요 사항

- 운영 적용 전 세 상태 ConfigMap과 Relay 상태 key를 읽기 전용 확인 필요. 기존 `base.yaml` 전체 재적용 금지.
- 상태 ConfigMap 조회 불가와 장기 실행 알림의 실제 Telegram 전달·중복 방지는 N100에서 별도 승인 후 검증 필요.
- 세 runner의 `--go`가 상태 ConfigMap의 잠금·`running` 게시까지 도달한 후 발생한 사전검사 실패는 `failed`로 보고할 수 있음. CronJob/Pod 시작 전 실패, scratch 초기화 실패, 상태 ConfigMap 자체 접근 실패처럼 잠금 게시 전 발생한 오류는 Relay의 상태 기반 알림으로 검출할 수 없으므로 Job 실패를 별도로 확인해야 함. `--check`는 읽기 전용 사전검사이며 알림을 게시하지 않음.
- 각 전용 runtime Secret이 현재 N100에 없으므로 승인된 저장소에서 준비하고 수동 백업 성공·실패 알림, 원격 공유 ACL 확인 전 자동 스케줄 활성화 금지.
- 격리 복원은 파일 내용·SQLite/JSON 검증이며 소유권·권한을 포함한 운영 복구 drill을 대체하지 않음.
