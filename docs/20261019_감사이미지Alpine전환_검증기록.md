## 2. 핵심 요약

동일 Debian 갱신 후 남은 HIGH 44건을 해소하기 위해 고정 Python 3.11 Alpine 기반으로 전환함. bash·GNU coreutils·kubectl·CA·tzdata와 UID/GID 10001, 읽기 전용 실행·기존 entrypoint를 유지함. 이 문서는 적용 준비 시점의 검증과 허용 범위를 기록하며, 최종 병합·운영 결과는 해당 PR 완료 기록으로 구분함.

## 4. 검토 결과

구현자 검사와 독립 검토를 구분함. 최종 코드 검토자는 대상 소스를 작성하지 않고 실제 diff·보안 원본·이미지와 소스 연결·CI 결과를 직접 대조하고 고정 대상 receipt를 발급함. 운영 검토자는 실제 SSH 읽기로 활성 Job 없음·현재 UID/spec·보호 상태·외부 health를 확인하고, 적용 이후 같은 기준으로 재검증함. 엄격 코드 receipt는 운영 SSH 검토와 별도 증거임.

## 5. 확인 필요 사항

OS/APK·Python 스캔 통과는 알려지지 않은 취약점 부재를 보증하지 않음. 실제 정기 감사 성공과 격리 fixture 성공을 구분하며, 이번 시험에서 실제 복구 fault·운영 ConfigMap 상태·Telegram 알림을 발생시키지 않음. 이전 작업의 로컬 백업 경고 집계 및 system-agent 복구 이전 Config 동일성 한계를 이번 변경으로 해결했다고 확대하지 않음.

## 6. 운영 적용 및 복구

정확한 PR/main CI 성공 후 N100 저장소를 fast-forward하고, 검증한 manifest를 import·canonical digest 등록함. 감사 Job이 활성 상태가 아님을 각 변경 직전 다시 확인함. 세 CronJob 각각 UID·resourceVersion·container name·기존 이미지를 CAS 검사하여 이미지 한 필드만 변경하고 이미지 외 전체 spec를 대조함. 세 리소스의 전역 원자성을 주장하지 않으며 실패 시 본인이 적용한 UID/이미지와 이미지 외 spec가 일치하는 변경만 역순으로 보상함. 일정·suspend·RBAC·Secret·PVC·기존 복구 Deployment·relay 상태·다른 서비스를 변경하지 않음.

## 7. 후속 조치

기존 service account의 원래 권한을 추가하지 않는 임시 command override probe는 고정 읽기 API·시간대·증적 검증만 수행하고 실제 감사 entrypoint를 실행하지 않음. 시험 Job/Pod와 전용 반입 파일을 정리하고, 독립 사후 검토에서 이미지·소스·spec·보호 지문·외부 health 3회·임시 자원 잔존 0을 확인함. 실제 운영 이미지와 원복 이미지는 보존함. 최종 CI·병합·적용·정리 결과는 PR 완료 기록에 남김.
