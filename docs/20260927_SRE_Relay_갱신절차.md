## 2. 핵심 요약

기존 `sre-telegram-install.sh --apply`는 새 리소스 생성용이며 기존 리소스가 있으면 실패함. 이미 설치된 Relay의 애플리케이션 이미지는 `infra/k8s/tools/sre-telegram-update.sh`로 갱신함. 이 도구는 사전에 반입된 `REPOSITORY@sha256:<64자리 digest>`만 받으며 `monitoring/sre-telegram-relay` Deployment의 `relay` 컨테이너 이미지 필드만 JSON Patch로 변경함. 상태 ConfigMap·Secret·RBAC·Service·PrometheusRule·Helm release는 수정하지 않음.

## 3. 상세 내용

### 3.1 작업 경계와 실행 순서

| 순서 | 작업 | 성공 기준 | 비고 |
|---:|---|---|---|
| 1 | 승인 범위·현재 Git/N100 revision과 외부 health 확인 | 이미지 갱신 대상과 rollback 이미지가 확정됨 | N100 변경 전 운영 승인 필요 |
| 2 | 별도 승인된 절차로 새 Relay 이미지를 N100 containerd에 반입 | `sudo -n k3s ctr -n k8s.io images list -q`에 **정확한 digest 참조**가 존재함 | 기존 `infra/k8s/tools/k3s-app-image-import.sh --go`는 검증한 OCI archive의 digest 별칭을 등록함. 갱신 도구는 build/import를 수행하지 않음 |
| 3 | `--check` 또는 `--dry-run` 실행 | `sre_telegram_update=CHECK_PASS` | 두 옵션은 동일한 읽기 전용 사전점검임. API 서버 dry-run patch도 실행하지 않음 |
| 4 | `--apply` 실행 | `sre_telegram_update=PASS` | Deployment 이미지 필드 하나만 변경함 |
| 5 | Relay·Portal 외부 health 확인 | Relay 검증과 Portal health 10초 간격 3회 성공 | 실제 운영 적용 시 수행함 |

```bash
bash infra/k8s/tools/sre-telegram-update.sh --check --image 'REPOSITORY@sha256:DIGEST'
bash infra/k8s/tools/sre-telegram-update.sh --apply --image 'REPOSITORY@sha256:DIGEST'
```

위 예시의 `DIGEST`는 64자리 소문자 또는 대문자 16진수로 대체해야 함. 정확한 이미지 참조가 containerd에 없으면 변경 전 차단됨. 기존 이미지도 containerd에 남아 있어야 자동 복구 가능함. `:latest` 등 가변 태그는 대상 이미지로 거부됨.

### 3.2 사전 점검·변경·복구

| 항목 | 처리 | 비고 |
|---|---|---|
| 사전 상태 | Deployment UID·resourceVersion·기존 이미지·replica·전략·pull policy와 기존 Ready Pod imageID를 메모리에서 확인함 | 전체 Deployment/Secret을 파일이나 출력으로 저장하지 않음 |
| 사전 health | 단일 replica Ready, `Recreate`, `imagePullPolicy: Never`, 기존 Pod 이미지·imageID, 기존 Relay 검증을 요구함 | 이상 상태에서는 patch 전 중단함 |
| 동시 변경 방지 | JSON Patch의 resourceVersion·기존 이미지 `test` 이후 이미지 `replace`를 수행함 | 다른 작업이 먼저 변경하면 patch 실패함 |
| 적용 검증 | rollout, Deployment UID·digest 이미지 참조·Ready, Pod imageID 존재, 기존 `sre-telegram-verify.sh` 통과를 요구함 | Relay health·서비스 노출·RBAC·Prometheus target 포함. imageID와 manifest digest의 대응 관계는 별도 CRI 검증 대상임 |
| 자동 복구 | 변경 후 실패 또는 중단 시 현재 이미지가 해당 목표 이미지일 때 기존 이미지로 다시 patch·rollout·검증함 | 복구 Pod imageID가 사전 스냅샷과 정확히 같아야 PASS이며, 제3자가 다른 이미지로 변경했으면 덮어쓰지 않음 |
| 복구 불확실 | `sre_telegram_rollback=UNVERIFIED`를 출력하고 실패 상태를 유지함 | 실제 상태를 읽기 전용으로 확인하고 별도 운영 판단 필요 |

`sre_telegram_rollback=PASS`는 원래 이미지와 사전 Pod imageID로 돌아와 검증까지 통과했음을 뜻함. `NOT_NEEDED`도 현재 이미지·Pod imageID와 Relay 검증을 재확인한 경우에만 출력함. 변경 명령의 응답이 불완전해도 도구는 실제 Deployment 이미지를 다시 조회한 뒤 복구 여부를 결정함. 상태 ConfigMap의 알림 중복 방지 기록은 갱신·복구 과정에서 보존됨.

### 3.3 제외 범위

| 대상 | 처리 | 이유 |
|---|---|---|
| `sre-telegram-relay-state` ConfigMap | apply·replace·patch 금지 | 알림 상태 데이터 보존 |
| Relay runtime Secret·Alertmanager 설정 Secret | 조회·수정 금지 | 자격 증명 경계 보존 |
| RBAC·Service·PrometheusRule·Helm | 갱신 대상 아님 | 변경별 검토·복구 절차가 별도로 필요함 |
| N100 이미지 build/import, K3s 전체 restart | 이 도구에서 수행하지 않음 | 별도 승인된 운영 단계 |

## 5. 확인 필요 사항

- 실제 운영에 사용할 digest 이미지의 출처·반입·containerd 정확한 참조 및 이전 이미지 보존을 적용 직전 확인 필요.
- RBAC·Service·PrometheusRule 또는 Alertmanager 설정 변경은 이 도구 범위가 아니며 별도 설계·승인 필요.
- `UNVERIFIED` 발생 시 Deployment 이미지·Pod 상태·외부 health를 확인하고 운영자 판단 필요.

## 6. 후속 조치

1. PR CI·독립 검토를 통과한 뒤 실제 N100 적용 대상·이미지·순서에 대한 운영 승인을 확인함.
2. 승인된 이미지 반입 후 `--check`, `--apply`, Relay 검증, 외부 health를 순서대로 수행함.
3. 저장소 병합·N100 동기화·이미지 반입·수동 검증·자동 실행 활성화·외부 health를 별도로 기록함.
