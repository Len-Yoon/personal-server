## 2. 핵심 요약

앞부분의 예측·가설·확인 순서를 먼저 작성하고 해설과 대조함. 실행은 격리된 임시 DB만 대상으로 하며 운영 DB·서비스·스토리지를 변경하지 않음. 실습 성공과 본인의 문제 해결 능력 입증은 별도임.

## 4. 참고 해설: 작성 후 대조

| 단계 | 소스에 근거한 해석 | 비고 |
|---|---|---|
| 잠금 주입 | 별도 `lock_actor` 프로세스가 같은 fixture DB에 `BEGIN IMMEDIATE`를 실행하고 트랜잭션을 유지함 | 문구를 흉내 낸 오류가 아님 |
| 실패 관측 | 다른 프로세스가 실제 제품 `update_memo`를 호출함. 제품 함수도 `BEGIN IMMEDIATE`로 쓰기를 시작하며 기본 코드 5를 관측함 | `SQLITE_BUSY=5`, 다른 DB 연결과의 쓰기 경쟁 |
| 대기 원인 | 제품 `_connect()`는 `sqlite3.connect(DB_PATH)`로 timeout을 지정하지 않아 기본 약 5초 대기를 사용함 | 기존 실측 탐지 5.206417~5.218806초는 호출·통신 비용도 포함 |
| 실패 원자성 | 실패 뒤 관련 8개 테이블의 논리 snapshot을 baseline과 비교함 | `unchanged=true`, DB 파일 바이트 해시 비교와 구분 |
| 잠금 해제 | 잠금 프로세스에서 `rollback()` 후 연결을 닫음 | 서비스 전체 재시작·DB 삭제 필요 없음 |
| 복구 확인 | 같은 요청 ID·같은 내용·같은 expected_version=1로 제품 함수를 두 번 호출함 | 최종 version=2·revision=1·write_request=1, 고정 요청의 단일 적용 |
| 보존·정리 | 기존 자료·`integrity_check` 정상, 소유 자식 종료와 임시 fixture 삭제를 확인함 | 모든 쓰기 경로의 보장을 뜻하지 않음 |

| 구분 | BUSY 실습 | FULL 실습 | 비고 |
|---|---|---|---|
| 기본 오류 코드 | 5 (`SQLITE_BUSY`) | 13 (`SQLITE_FULL`) | SQLite 확장 코드는 하위 8비트로 대조 |
| 주입 방식 | 다른 연결이 실제 writer 잠금 보유 | 연결별 `max_page_count`를 현재 page_count로 제한 | 고정 로컬 실습 |
| 확인 순서 | 연결·트랜잭션·잠금 보유·대기 설정 | page_count·page_size·max_page_count·파일시스템 상태 | 코드 13만으로 호스트 디스크 고갈 확정 불가 |
| 해제 동작 | 잠금 소유 연결 rollback·close | 페이지 제한 완화 | 이번 FULL은 OS ENOSPC 미재현 |

## 5. 검토 결과

해설은 실제 actor·제품 코드와 측정 원본을 대조함. 2026-10-18 11:28에 소스 `c8759902dbcd61cacf73ce9aeaf2da07b74e1a53`·dirty=false로 신규 1회 자동 재실행을 통과함. 탐지 5.200274초·자동 원인 확인 0.001699초·조치 후 복구 확인 0.028249초이며 코드 5·unchanged·단일 적용·무결성·정리를 확인함. 기존 3회와 신규 1회의 분모는 합치지 않음. 자동 원인 확인 시간은 미리 알려진 장애의 snapshot 검사 시간이며 사람의 수동 RCA·MTTR로 사용하지 않음.

## 6. 확인 필요 사항

사용자의 직접 예측·진단·재실행·설명 수행 여부는 확인 필요함. 운영 잠금 원인, 실사용자 영향, HTTP 오류 처리와 운영 알림은 이번 실습 범위 밖임.
