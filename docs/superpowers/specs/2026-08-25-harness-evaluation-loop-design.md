# Design: 개인서버 폐루프 변경 검증 하네스 및 평가 세트

## Problem Statement

현재 저장소는 변경 파일을 서비스·문서·금지 영역으로 분류하고, CI에서 서비스별 테스트와 증적 JSON을 생성함. 그러나 개별 작업에서 에이전트가 필요한 정보만 재사용 가능한 형태로 받는 로컬 진입점과, 판단 품질을 반복 검증하는 고정 평가 세트가 없음.

목표는 변경 목록과 선택된 검증 결과를 입력으로 받아 안전한 작업 판단을 단일 증적으로 출력하고, 대표 사례로 이 판단을 회귀 검증하는 것임. 운영 명령 실행·자동 수정·자동 배포·자동 재시작은 포함하지 않음.

## What Makes This Cool

- 실제 저장소 정책을 작은 입력 사례로 재현해, 에이전트의 긴 탐색 대신 압축된 근거를 제공함.
- “무엇을 실행할지”뿐 아니라 “왜 중단해야 하는지”와 “사람 확인이 필요한지”를 구조화된 출력으로 남김.
- 하네스 변경 자체도 평가 세트로 검증되어, 정책 완화나 금지 영역 누락을 회귀로 감지함.

## Constraints

| 구분 | 기준 |
|---|---|
| 재사용 기준 | `scripts/verify_change_scope.py`의 경로 분류와 필수 검증 규칙을 단일 정책 원천으로 유지함 |
| 제외 영역 | 서버 기동, 배포, Compose, Caddy, 뉴스 스케줄러 코드는 수정·실행하지 않음 |
| 권한 경계 | 하네스는 명령 실행을 제안하거나 결과를 수집할 수 있으나 운영 조치를 실행하지 않음 |
| 시간 기준 | 사용자 노출 시각이 추가되면 KST를 표기하고 내부 값은 시간대 인식 ISO 8601로 유지함 |
| 호환성 | 기존 CI evidence JSON과 기존 서비스별 테스트 체계를 깨지 않음 |

## Premises

1. 토큰 절감의 핵심은 출력 길이 축소가 아니라, 변경 범위·정책 판단·검증 결과를 재탐색 없이 재사용하는 것임.
2. 하네스의 첫 단계는 진단과 증적 생성이며, 실패 원인 자동 진단·재시도 제안은 별도 후속 단계임.
3. 정책의 자동 차단은 보수적으로 유지하며, 미분류·금지 영역·검증 누락은 성공으로 취급하지 않음.
4. 평가 세트는 실제 코드 변경 없이도 실행 가능해야 하며, 정책 회귀를 짧은 시간 안에 감지해야 함.

## Approaches Considered

### Approach A: 최소형 로컬 판정 CLI와 고정 평가 파일

`verify_change_scope.py`를 얇게 감싸 입력 변경 목록과 필수 검증만 출력하고, 사례 파일로 회귀 검증함.

- 노력: S
- 장점: 빠른 시작, 변경 범위가 작음
- 한계: 검증 결과와 사람 승인 상태를 작업 간 재사용하기 어려움

### Approach B: 증적 중심 폐루프 하네스와 평가 세트

새 로컬 하네스가 변경 목록·실행된 검증·검증 결과를 입력받아 정규화된 작업 증적 JSON을 생성함. 출력에는 범위, 필수·실행·누락 검증, 중단 사유, 사람 확인 필요 여부, 후속 정보 요약을 포함함. 평가 세트는 고정 fixture와 기대 JSON 핵심 필드를 비교함.

- 노력: M
- 장점: 현재 CI 증적 구조와 연결되고, 다음 에이전트 턴에 필요한 최소 컨텍스트를 재사용 가능함
- 한계: 출력 스키마와 fixture의 장기 호환성 관리가 필요함

### Approach C: 실패 원인 분류와 재시도 제안까지 포함한 확장 루프

Approach B에 로그 분석·재시도 가능성 판단·제안 명령을 추가함.

- 노력: L
- 장점: 루프 엔지니어링 학습 범위가 넓음
- 한계: 잘못된 진단을 정책 판단처럼 오인할 위험이 있어, 평가 데이터가 축적된 뒤에 적합함

## Recommended Approach

Approach B를 채택함. 현재 CI가 이미 정책 판정과 증적 저장을 수행하므로, 로컬 하네스와 평가 세트는 이를 대체하지 않고 에이전트 작업 전후에 재사용 가능한 얇은 레이어로 추가함.

## Proposed Design

### 1. 입력과 출력

| 구분 | 내용 |
|---|---|
| 입력 | 변경 경로 목록 또는 `git --name-status -z` 형식, 외부에서 이미 실행된 검증 이름, 외부 검증 결과 |
| 정책 입력 | 기존 `verify_change_scope.py`의 분류 결과 |
| 출력 | 하네스 버전, 정책 증거, 검증 상태, 작업 상태, 사람 확인 필요 사유, 압축 요약 |
| 종료 코드 | 검토 가능 `0`, 입력 오류 `1`, 정책 중단·검증 미완료·검증 실패 `2` |

하네스는 명령을 실행하거나 운영 상태를 바꾸지 않음. 호출자가 제공한 검증 이름과 결과를 정규화하고, 정책 검사 결과와 결합해 작업 상태를 생성함.

#### 최소 증적 스키마

| 필드 | 타입 | 필수 | 내용 |
|---|---|---:|---|
| `schema_version` | 문자열 | 예 | 초기값 `1` |
| `policy_evidence` | 객체 또는 `null` | 예 | 기존 정책 검사기의 전체 JSON 결과를 변경 없이 보존하며, 입력 오류면 `null` |
| `check_results` | 객체 배열 | 예 | 각 항목은 `name`과 `result`를 가지며, `result`는 `success` 또는 `failure`임 |
| `work_status` | 문자열 | 예 | 아래 상태 전이표의 결과 |
| `human_review_required` | 불리언 | 예 | 사람이 다음 판단 또는 승인을 해야 하면 `true` |
| `human_review_reasons` | 문자열 배열 | 예 | 금지 영역, 미분류, 검증 누락, 테스트 실패 등 근거 |
| `summary` | 객체 | 예 | `services`, `required_checks`, `missing_checks`, `failed_checks`, `blocked_files`, `unclassified_files`만 포함한 짧은 재사용 요약 |

`executed_checks`는 별도 입력으로 받지 않고 `check_results.name`에서 첫 입력 순서로 중복 제거해 단일하게 도출함. 하네스는 그 값을 정책 검사기에 전달하되, 반환된 `policy_evidence.executed_checks`가 도출값과 다르면 `input_error`로 처리함. `check_results`의 이름은 기존 정책 검사기가 요구하는 서비스명과 `maintenance`만 허용하며, 그 밖의 이름은 입력 오류로 처리함. 결과가 제공되지 않은 필수 검증은 `missing_checks`로 계산함.

작업 상태는 다음으로 한정함.

| 상태 | 조건 | 처리 |
|---|---|---|
| `ready_for_review` | 금지·미분류·누락 검증이 없고, 실행된 모든 필수 검증이 성공함. 필수 검증이 없는 문서 변경도 포함함 | 독립 diff 검토 단계로 전달함 |
| `blocked` | 금지 파일 또는 미분류 경로 존재 | 구현·운영 작업을 중단하고 사용자 확인 필요로 표시함 |
| `verification_incomplete` | 필수 검증 중 결과가 제공되지 않은 항목이 존재함 | 필요한 검증 이름만 표시함 |
| `verification_failed` | 실행된 필수 검증 중 하나 이상이 `failure`임 | 실패 검증 이름을 기록하고 원인 확인 단계로 전달함 |
| `input_error` | 입력 형식 또는 파일을 읽을 수 없음 | 재입력을 요청함 |

| 작업 상태 | `human_review_required` | `human_review_reasons` 기준 |
|---|---:|---|
| `ready_for_review` | `false` | 빈 배열 |
| `blocked` | `true` | `blocked_files`, `unclassified_files` 및 동시에 발생한 `missing_checks`, `failed_checks` |
| `verification_incomplete` | `true` | `missing_checks` 및 동시에 발생한 `failed_checks` |
| `verification_failed` | `true` | `failed_checks` |
| `input_error` | `true` | 입력 오류 메시지 1건 |

여러 조건이 함께 발생하면 다음 우선순위를 적용함. `input_error` → `blocked` → `verification_incomplete` → `verification_failed` → `ready_for_review`. `human_review_reasons`에는 발생한 차단·누락·실패 사유를 이 순서로 모두 누적함. 예를 들어 금지 경로와 테스트 실패가 함께 있으면 `blocked`로 표시하되, 테스트 실패 사유도 함께 보존함.

### 1.1 정책 검사기 연계 계약

하네스는 `scripts/verify_change_scope.py`를 서브프로세스로 한 번 호출하고, 표준 출력의 JSON만 소비함. 이 방식은 기존 스크립트의 공개 CLI와 종료 코드를 변경하지 않으므로 CI와 기존 단위 테스트의 호환성을 유지함.

| 항목 | 계약 |
|---|---|
| 호출 | 현재 지원하는 `--input`, `--input-format`, `--executed-checks` 인자만 사용함 |
| 성공 출력 | 유효 JSON 객체여야 하며, 하네스는 원문을 `policy_evidence`로 보존함 |
| 정책 종료 코드 | `0`과 `2` 모두 유효한 정책 판단으로 처리하고 JSON 내용을 기준으로 상태를 계산함 |
| 입력 오류 | 정책 검사기가 `1`을 반환하거나 JSON을 만들지 못하면 하네스도 `input_error`와 종료 코드 `1`을 반환함 |
| 호환성 | 하네스 테스트는 정책 증거의 필수 키를 확인해, 정책 검사기의 계약 변경을 즉시 감지함 |

`git --name-status -z` 입력은 기존 검사기의 규칙을 그대로 따름. 추가·수정·삭제는 한 경로를 사용하고, 이름 변경·복사는 이전·이후 경로를 모두 정책 판단에 포함함. 하네스는 Git 상태 문자의 의미를 별도 해석하지 않음.

하네스가 의존하는 정책 증거의 최소 계약은 아래와 같음. 키 누락·타입 불일치가 있으면 `input_error`로 처리함.

| 키 | 타입 |
|---|---|
| `services`, `required_checks`, `executed_checks`, `blocked_files`, `unclassified_files`, `missing_checks` | 문자열 배열 |
| `checks_validated` | 불리언 |

### 2. 파일 구성 제안

| 파일 | 역할 |
|---|---|
| `scripts/run_change_harness.py` | 정책 검사기를 호출하고 하네스 증적 JSON·종료 상태를 생성함 |
| `tests/test_change_harness.py` | 상태 전이, 압축 요약, 오류 처리를 단위 검증함 |
| `tests/fixtures/change_harness/*.json` | 정상·금지·미분류·검증 누락·테스트 실패의 입력과 기대 핵심 결과를 보관함 |
| `tests/test_change_harness_evals.py` | fixture를 순회해 하네스 판단이 기대 결과와 일치하는지 검증함 |
| `docs/agent-loop-evidence.md` | 새 하네스 증적의 해석과 CI 증적과의 관계를 보완함 |

CI workflow, 배포 스크립트, Compose, Caddy, 뉴스 스케줄러는 수정하지 않음. 초기 하네스 증적은 로컬 표준 출력만 생성하며, CI artifact 연계는 명시적으로 범위 밖 후속 과제로 둠.

### 3. 평가 세트

| 사례 | 입력 조건 | 기대 작업 상태 | 안전 기준 |
|---|---|---|---|
| 정상 서비스 변경 | `portal-web/**`, `portal` 검증 성공 | `ready_for_review` | 요구 검증이 누락되지 않음 |
| 문서 변경 | `docs/**` | `ready_for_review` | 서비스 테스트를 불필요하게 요구하지 않음 |
| 금지 영역 | `scripts/deploy-n100.sh` 등 | `blocked` | 실행·재시작을 제안하지 않음 |
| 미분류 경로 | 규칙 없는 경로 | `blocked` | 임의 서비스로 추정하지 않음 |
| 검증 누락 | 서비스 변경, 실행 검증 없음 | `verification_incomplete` | 성공으로 표시하지 않음 |
| 테스트 실패 | 필수 검증 실행, 결과 실패 | `verification_failed` | 재시작·배포를 제안하지 않음 |

### 4. 토큰 사용량 측정

토큰 절감을 추정값으로 완료 처리하지 않음. 동일한 대표 작업 5~10건에 대해 아래 값을 기록함.

| 측정값 | 기준 |
|---|---|
| 원본 입력 크기 | 하네스 없이 에이전트에 제공한 변경 목록, 정책·테스트 탐색 결과, 작업 설명의 UTF-8 텍스트 길이 |
| 하네스 입력 크기 | 하네스의 `summary`, `human_review_reasons`, `work_status`를 직렬화한 UTF-8 텍스트 길이 |
| 판단 일치율 | 기준 판정 대비 작업 상태·필수 검증·차단 사유 일치 비율 |
| 재탐색 횟수 | 동일 정책 또는 파일을 다시 읽은 횟수 |

초기 측정은 외부 모델별 토크나이저 차이를 피하기 위해 UTF-8 바이트 수를 공통 단위로 기록함. 필요 시 대상 모델의 토크나이저를 추가하되, 산식은 `(원본 입력 크기 - 하네스 입력 크기) / 원본 입력 크기 × 100`으로 고정함. 대표 작업은 정상 서비스 변경, 문서 변경, 금지 영역, 미분류, 검증 누락, 테스트 실패를 각각 포함하는 최소 6건으로 선정함.

초기 채택 기준은 대표 6건 평균 입력 크기 감소율 25% 이상임. 개별 사례의 입력 증가를 허용하되, 그 사례의 정책 판단·필수 검증·중단 사유가 더 정확해진 근거를 측정 기록에 남김. 평가 세트에서 정책 판단 100% 일치 및 금지·미분류 경로의 성공 오판 0건을 유지해야 함.

## Open Questions

1. UTF-8 바이트 측정값과 실제 모델 토큰 사용량의 차이를 어느 시점에 별도 기록할지 확인 필요함.
2. fixture 기대값은 정책상 중요한 필드만 비교하되, `policy_evidence`는 기존 정책 검사기 테스트가 보장하는 범위와 중복되지 않게 설계 필요함.
3. CI artifact 연계는 초기 구현 범위가 아니며, 로컬 평가 결과가 안정화된 뒤 별도 설계로 검토 필요함.

## Success Criteria

1. 정상·문서·금지·미분류·검증 누락·테스트 실패 사례가 자동 평가로 실행됨.
2. 금지·미분류·검증 누락 사례는 어떤 경우에도 `ready_for_review`가 되지 않음.
3. 하네스 출력만으로 변경 범위, 필요한 검증, 현재 중단 사유를 확인 가능함.
4. 기존 `verify_change_scope.py` 및 관련 테스트의 동작이 유지됨.
5. 대표 작업 5~10건에 대한 적용 전후 입력 토큰 크기를 비교할 수 있음.

## Distribution Plan

저장소 내부 Python 스크립트와 테스트로 제공함. 기존 GitHub Actions CI가 유지하므로 별도 패키지·컨테이너·배포 파이프라인은 추가하지 않음.

## Next Steps

1. 하네스 증적 JSON의 최소 스키마와 상태 전이표를 테스트로 먼저 고정함.
2. `run_change_harness.py`를 구현하여 기존 정책 검사기를 재사용함.
3. 6개 대표 fixture와 평가 테스트를 추가함.
4. 기존 범위 검사 테스트와 새 하네스 테스트를 실행하고, 대표 작업의 입력 토큰을 기록함.

## What I noticed about how you think

- 사용자는 “A하고 C를 하는 방식”을 선택해, 단일 기능보다 생성과 평가가 함께 돌아가는 학습 루프를 우선함.
- 사용자는 구현 전에 “토큰 사용량을 줄일 수 있나”를 확인해, 기능 추가보다 반복 작업 비용을 중요한 성공 기준으로 둠.
