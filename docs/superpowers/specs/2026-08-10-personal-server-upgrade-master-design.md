## 핵심 요약

개인 서버는 모든 정보를 모아보는 화면이 아니라 필요한 정보만 빠르게 판단하고, 나머지는 필요할 때 찾는 개인 작업 공간으로 고도화함.

텔레그램은 고정밀 즉시 알림, 뉴스 허브는 넓은 보관·탐색 채널로 분리함. 수집 주기는 현재 15분을 유지하며 스케줄러를 변경하지 않음. 파일함은 Windows 탐색기에 익숙한 사용 흐름을 우선하고, 관리자 상태는 실제 호스트 수집 시각과 화면 조회 시각을 구분함. 모든 화면은 Editorial Atlas 디자인 시스템을 공유하되 화면의 목적에 맞는 레이아웃을 사용함.

## 최종 사용자 경험

| 영역 | 목표 사용자 경험 | 성공 기준 |
|---|---|---|
| 텔레그램 | 꼭 봐야 할 나스닥 사건만 즉시 확인함 | 건수 상한 없이 최상위 사건만 발송하고, 반복·일상 기사는 미발송 |
| 뉴스 허브 | 나스닥 관련 기사를 넓게 보관하고 필요할 때 필터링함 | 기사마다 관련성 등급과 포함 이유를 확인함 |
| 파일함 | 폴더와 파일을 탐색기처럼 빠르게 찾고 작업함 | 목록/아이콘 보기, 정렬, 검색, 다중 선택과 키보드 조작이 명확함 |
| 관리자 상태 | 데이터가 실제 언제 수집됐는지 신뢰할 수 있음 | 호스트 수집 시각, 화면 조회 시각, 오래됨 상태가 분리됨 |
| 포털/서비스 UI | 개인용 서비스가 하나의 정돈된 제품처럼 느껴짐 | 공통 색상·타이포그래피·상태·포커스 규칙이 적용됨 |
| 하네스 실습 | AI 작업을 예측 가능하게 통제함 | 역할·파일 범위·테스트·리뷰·회고가 각 변경에 남음 |

## 뉴스 정책

### 채널 분리

| 채널 | 역할 | 포함 범위 |
|---|---|---|
| 뉴스 허브 | 넓은 보관 및 탐색 | 나스닥, 미국 기술주, 반도체, AI, 금리·환율 등 영향 요인 |
| 텔레그램 | 고정밀 즉시 알림 | 시장 판단에 직접 영향을 주는 최상위 사건만 |

### 텔레그램 즉시 알림 기준

다음 세 범주만 즉시 알림 후보로 분류함.

1. 연준 결정, 금리, CPI/PCE, 고용처럼 결과가 발표된 거시 이벤트
2. 미국 기술주·반도체 전반에 영향을 주는 수출 제한, 대형 규제, 공급 충격
3. 시장 전체 반응이 예상되는 대형 돌발 사건

다음은 뉴스 허브에만 보관하고 텔레그램으로 보내지 않음.

- 일반적인 개별 종목 등락
- 애널리스트 의견, 목표주가, 통상적 전망
- 반복 기사와 단순 해설
- 나스닥 직접 영향이 불분명한 일반 세계 경제 기사

### 알림 안전장치

- 동일 URL, 동일 핵심 사건의 후속 기사는 중복 발송하지 않음.
- 알림에는 제목, 출처, 발행 시각, 분류 이유, 원문 링크를 표시함.
- 초기 배포 후 2주간 발송 결과를 기록하고, 사용자가 유용/불필요로 판단한 사례를 기준으로 규칙을 보정함.

## 구현 순서와 의존성

0. 하네스 기준선 및 회귀 테스트
1. 관리자 상태 수집 시각 정정
2. 뉴스 분류·텔레그램 정책
3. 파일함 탐색기 UX
4. Editorial Atlas 메인 화면
5. 뉴스·파일함·관리자 상태 화면 공통 UI 확장
6. 전체 회귀·브라우저 QA·리뷰

| 단계 | 책임 | 수정 가능 영역 | 완료 게이트 |
|---:|---|---|---|
| 0 | 기준선 | 테스트·계획·검증 기록 | 기존 회귀 테스트 결과 기록 |
| 1 | 상태 신뢰성 | portal-web 상태 표시와 테스트 | 호스트 수집 시각을 우선 표시하고 오래됨을 명시 |
| 2 | 뉴스 판단 | crawler-worker 분류·알림·화면·테스트 | 수집 주기 변경 없이 고정밀 알림 정책 충족 |
| 3 | 파일 UX | portal-web 파일 라우터·템플릿·스타일·테스트 | 기존 보안 정책을 유지한 탐색기형 작업 흐름 |
| 4 | 메인 UX | 포털 메인 템플릿·스타일·테스트 | 기존 서비스 진입과 통합 검색을 보존 |
| 5 | 서비스 UX | 뉴스·파일함·관리자 템플릿·전용 스타일 | 공통 디자인 규칙과 화면별 목적을 함께 충족 |
| 6 | 독립 검증 | 테스트·브라우저 QA·리뷰 기록 | 기능, 보안, 반응형, 접근성 회귀 없음 |

## 하네스 엔지니어링 실행 규칙

| 역할 | 책임 | 변경 권한 |
|---|---|---|
| 구현 에이전트 | 한 작업의 코드·테스트·자체 검토 | 할당된 파일만 변경 |
| 작업 리뷰 에이전트 | 명세 준수와 코드 품질 판정 | 코드 변경 금지 |
| 최종 리뷰 에이전트 | 단계 간 충돌, 보안, 회귀 위험 판정 | 코드 변경 금지 |
| 조정 에이전트 | 계획, 작업 경계, 검증 기록 관리 | 승인된 수정만 지시 |

각 작업은 다음 순서를 반드시 따름.

1. 현재 동작을 보존하는 실패 테스트를 작성함.
2. 테스트가 기능 부재로 실패하는지 확인함.
3. 최소 구현으로 테스트를 통과시킴.
4. 해당 작업 범위의 회귀 테스트를 실행함.
5. 독립 리뷰를 통과한 뒤 다음 작업으로 진행함.
6. 커밋, 검증 결과, 리뷰 결과를 작업 원장에 기록함.

## 공통 제약

- 서버 기동 영역과 스케줄러 구현은 수정하지 않음.
- 현재 15분 수집 주기를 변경하지 않음.
- Telegram bot token, chat ID, 비밀번호 등 비밀값을 코드·문서·테스트 출력에 기록하지 않음.
- 공개 화면에 실제 파일 경로, 보안 이벤트, 인증 전 관리자 상태를 노출하지 않음.
- 삭제, 업로드, 다운로드, 관리자 인증의 기존 보안 정책을 약화하지 않음.
- UI 변경은 전용 CSS 클래스 범위로 적용해 다른 서비스의 기존 동작을 깨지 않음.

## 확인 필요 사항

- 나스닥 관련성 등급의 실제 사례를 2주간 관찰한 뒤 세부 키워드와 예외 규칙을 보정할 필요가 있음.
- 텔레그램은 일일 건수 상한을 두지 않으며, 분류 기준이 과도하게 넓어지지 않는지 실제 발송 결과를 기준으로 조정 필요.
- 파일함의 Windows형 UX는 목록/아이콘 보기와 정렬을 1차 범위로 하고, 폴더 업로드·드래그 이동은 별도 검토 필요.
- 메인 화면을 제외한 세부 서비스 화면은 기능 변경 작업 완료 후 동일 디자인 시스템으로 순차 적용 필요.

## 후속 조치

1. 단계 1~5 각각의 파일별 구현 계획을 작성함.
2. 전체 계획 검토 후 격리 워크트리에서 순차 구현함.
3. 각 단계의 독립 리뷰와 테스트 결과를 작업 원장에 기록함.
