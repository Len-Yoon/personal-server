## 2. 핵심 요약

전체 학습 순서는 성능·용량 분석 → 장애 진단·복구 → 배포 표준화임. 클라우드와 새 VM 환경 재구축은 제외함. 본 설계는 첫 단계 중 실제 통합 검색 함수의 동작을 로컬에서 측정하는 실습으로 한정함. DB 쓰기 잠금·제한 저장소 부족 훈련과 배포 표준화는 후속 단계에서 별도 설계함.

실제 `search_all` 함수를 고정 샘플 응답의 로컬 HTTP 서버 세 개와 연결함. 제품 코드 변경 없이 정상·지연·HTTP 실패 조건을 측정함. 이 결과는 검색 집계 함수와 테스트 서버를 포함한 로컬 실측이며 Portal 화면·실제 서비스 DB·N100 운영 용량·사용자 SLO를 증명하지 않음.

## 3. 상세 내용

### 3.1 기존 코드에서 확인한 사실

| 항목 | 확인 내용 | 비고 |
|---|---|---|
| 병렬 처리 | 세 검색 대상에 asyncio task를 생성함 | news·youtube·books |
| HTTP 클라이언트 | 검색 호출마다 `httpx.AsyncClient`를 생성·종료함 | 병목 여부는 미확정 |
| 대기 예산 | task 대기는 1.5초이며 미완료 task를 취소·회수함 | 함수 전체 wall time의 1.5초 상한을 뜻하지 않음 |
| 실패 표현 | 실패 대상은 빈 items와 `unavailable`로 반환함 | HTTP 성공과 기능 전체 성공을 구분할 필요가 있음 |
| 화면 경로 | `GET /?q=…`에서 검색 함수 호출 후 템플릿을 렌더링함 | 이번 측정에는 라우팅·템플릿·브라우저 시간이 포함되지 않음 |

### 3.2 대안과 선택

| 대안 | 장점 | 제약·선택 | 비고 |
|---|---|---|---|
| 실제 검색 함수 + 로컬 HTTP 서버 | 제품 동작을 그대로 호출하고 고정 조건을 반복할 수 있음 | 1차 선택. 실제 DB·웹 화면의 성능을 측정하지 못함 | 최소 범위의 진단 |
| Portal 및 실제 앱의 전체 격리 배치 | 라우팅·템플릿·DB를 함께 측정할 수 있음 | 1차 결과에서 필요성이 확인되면 확대함 | 데이터·의존성 준비 비용 증가 |
| 운영 공개 주소에 부하 주입 | 운영 경로를 측정함 | 선택하지 않음. 현재 범위에 운영 부하 시험이 포함되지 않음 | 실제 지표 오염·자원 경합 |

### 3.3 구성과 데이터 흐름

`실습 CLI → 실제 search_all → 로컬 샘플 HTTP 서버 3개 → 결과 검증 → JSON 증적`

| 구성요소 | 책임 | 비고 |
|---|---|---|
| 실습 실행기 | 인자 검증, 환경 격리, 프로세스 수명·제한 관리 | 기존 Portal 테스트용 Python 환경 활용, 새 도구 설치는 기본 요구가 아님 |
| 샘플 서버 프로세스 | 세 포트를 loopback에만 바인딩하고 고정 JSON·지연·503 응답 제공 | 실행 중 할당한 포트만 사용함. 이벤트 루프를 블로킹하지 않는 서버 구현 |
| 검색 부하 프로세스 | 실제 모듈을 로드하고 지정한 동시성만큼 검색 호출 | 샘플 서버와 프로세스를 분리해 단일 이벤트 루프 경합을 줄임 |
| 증적 집계기 | 개별 요청과 셀별 통계·무효 사유·정리 결과 기록 | 제품 모듈을 수정하지 않음 |

샘플 데이터는 고정 query·고정 결과 세트로 구성하며 모든 URL은 `#`를 사용함. 개인 데이터·인증·외부 API를 사용하지 않음. 서버는 readiness 확인 후 측정을 시작하며 실행 종료 시 이 실행이 소유한 자식 프로세스만 정리함.

### 3.4 환경·접속 경계

| 경계 | 규칙 | 비고 |
|---|---|---|
| 검색 대상 | 부모 환경의 세 SEARCH_URL을 상속하지 않고 실행기가 할당한 `127.0.0.1` 포트로 모두 덮어씀 | 외부 대상 URL 입력 옵션 없음 |
| demo 모드 | 자식 환경에서 `DEMO_MODE`를 명시적으로 비활성화함 | 샘플 함수 우회 방지 |
| 프록시 | 자식 환경의 HTTP(S)·ALL 프록시 변수를 대소문자 모두 제거하고 loopback을 NO_PROXY로 설정함 | 제품의 HTTP 클라이언트 코드는 변경하지 않음 |
| redirect | 소유 샘플 서버는 redirect를 반환하지 않음 | 타 프로세스가 포트를 선점하면 readiness·소유 확인 실패로 중단함 |
| 파일 | 지정한 신규 결과 파일에만 증적을 기록하며 기존 파일을 덮어쓰지 않음 | 원시 응답·부모 환경·개인 경로·계정·비밀값 저장 금지 |
| 운영 | N100 접속·K3s/Compose 적용·Secret/PVC·Caddy·scheduler·알림을 변경하지 않음 | 동일 호스트 실습도 운영 자원 경합 가능하므로 로컬 맥을 기본으로 함 |

### 3.5 시나리오와 측정 행렬

| 시나리오 | 샘플 서버 동작 | 기대 결과 | 비고 |
|---|---|---|---|
| normal | 세 대상 모두 고정 결과 반환 | 세 대상 status=ok, 고정 데이터 일치 | 지연 의도 주입 없음 |
| delayed | books만 500ms 지연 후 정상 반환 | 세 대상 status=ok | 부하에서 예산 초과 시 관측 결과로 기록함 |
| timeout | books만 2초 지연 | 정상 두 대상 보존, books=unavailable | 전체 함수가 정확히 1.5초에 끝난다고 단정하지 않음 |
| http_failure | books가 503 반환 | 정상 두 대상 보존, books=unavailable | 응답 자체의 도달 실패와 구분함 |

기본 행렬은 4개 시나리오 × 동시성 1·5·10 × 반복 3회임. 한 셀은 준비 호출 5건 뒤 측정 호출 30건을 고정 작업자 수로 수행함. 준비 호출은 통계에서 제외하고 별도 집계함. 셀 사이에는 미완료 요청·샘플 핸들러 정리를 확인하고 준비 상태를 다시 검증함. smoke 모드는 normal·동시성 1·반복 1·측정 5건으로 제한함.

이 방식은 closed-loop 동시성 시험임. 지연이 늘면 주입 요청률도 낮아지므로 고정 도착률에서의 과부하·대기열 또는 최대 RPS를 증명하지 않음. 고정 동시성에서 관측한 처리량으로만 보고함. 30건의 p99는 표본 한계를 표시하며 신뢰성 있는 tail latency 추정으로 표현하지 않음.

### 3.6 지표와 결과 판정

| 지표 | 산정·기록 방식 | 비고 |
|---|---|---|
| 지연시간 | 각 호출을 monotonic clock으로 측정하고 nearest-rank 방식의 p50·p95·p99, min·max를 셀별 산정 | 서로 다른 셀의 percentile을 평균하지 않음 |
| 처리량 | 측정 완료 호출 수 / 첫 측정 호출 시작부터 마지막 호출의 성공·실패·안전 deadline 확정까지의 wall time | warm-up·서버 기동 시간 제외. 계획·시작·완료·취소 건수를 각각 기록하며 미시작·취소를 완료 건수에 넣지 않음 |
| 전체 정상 비율 | 세 대상 모두 ok이며 고정 결과와 일치한 호출 / 전체 측정 호출 | HTTP 상태만으로 성공 처리하지 않음 |
| 부분 실패 비율 | 한 대상 이상 unavailable인 호출 / 전체 측정 호출 | timeout·503 시나리오에서는 의도된 결과임 |
| 계약 위반 | 예상 결과 불일치·미처리 예외·정상 대상 유실 건수 | 의도된 실패와 구분함 |
| 자원 | 셀마다 부하·샘플 서버 프로세스를 새로 생성하여 CPU user/system 시간과 종료 시 high-water RSS를 수집함 | macOS/Linux 단위를 정규화함. 준비 호출을 포함한 셀 수명 전체의 값이며 순간 피크나 호스트 전체 자원 사용률이 아님 |
| 실행 정보 | 기준 Git SHA·dirty 여부, 실행기 버전, Python·httpx 버전, OS 종류·아키텍처, 행렬·시간·샘플 해시 | 호스트명·사용자명·절대 개인 경로 제외 |
| 시각 | UTC 시간대 인식 ISO 8601로 저장함 | 표시 시 Asia/Seoul 사용 |

정상·지연 시나리오의 높은 부하에서 unavailable이 발생하면 이를 숨기거나 실험 자체를 무효화하지 않고 관측된 저하로 기록함. 저동시성 normal smoke에서의 불일치, 부하 프로세스 중단, 잘못된 설정, 서버 준비 실패, 표본 누락, 미확인 자원 정리는 실험 무효로 기록함. timeout·503의 정상 대상 결과 손실은 계약 위반으로 기록함. 실행 종료 코드는 실험 유효성·계약 검사 결과를 나타내며 지연시간 숫자만으로 CI 성능 합격을 결정하지 않음.

개별 지연 표본과 고정 상태값을 남겨 통계를 다시 계산할 수 있게 함. 실패해도 가능한 범위의 부분 증적과 종료 이유를 보존하고 정상 결과로 표시하지 않음. CPU/RSS 취득 실패는 해당 지표 미측정으로 명시함. 응답 본문·검색어 원문·환경 전체·예외 원문은 저장하지 않음.

### 3.7 제한·중단·정리

기본 상한은 동시성 10, 셀당 측정 30건, 반복 3회, 전체 실행 600초임. 600초는 전체 행렬 완료 보장 시간이 아닌 강제 중단 상한이며, 도달하면 미실행 셀·부분 표본·무효 사유를 기록함. 상한을 초과하는 입력은 실행 전에 거부함. 각 호출의 별도 안전 deadline은 5초로 두며, deadline 도달은 제품의 자체 timeout과 구분해 기록함. 추가 반복·상한 변경은 후속 설계에서 근거를 확인함.

부모는 SIGINT/SIGTERM·전체 deadline·자식 비정상 종료를 처리하고 자신이 시작한 자식만 종료·회수함. 정리에는 별도 최대 10초를 허용하며 종료 요청 후 5초 대기, 생존한 소유 자식만 강제 종료 후 최대 5초 회수함. 따라서 600초 제한 이후 정리 시간을 포함한 목표 종료 상한은 610초임. 핸들러·연결 종료와 포트 해제를 확인함. 소유 확인 실패 시 임의 PID 종료·기존 파일 삭제·포트의 타 프로세스 종료를 하지 않음. 정리 실패는 실행 실패와 잔여 자원을 기록하고 자동 재실행하지 않음.

### 3.8 병목 판단과 개선 절차

1. 먼저 baseline 행렬을 수집하고 시나리오별 지연·오류·CPU·메모리·샘플 서버 병목 가능성을 분리함.
2. 요청별 HTTP 클라이언트 생성은 가설로만 취급함. 샘플 서버나 부하 발생기 포화, 실행 환경 변동을 먼저 확인함.
3. 병목 근거가 확보된 경우에만 가장 작은 개선 후보 하나를 제안함. 공유 클라이언트 도입은 수명·동시성·종료·테스트 격리 설계를 포함한 별도 제품 변경으로 다룸.
4. 개선을 수행하면 baseline과 같은 환경·샘플·행렬로 재측정하고 회귀 검사 및 독립 검토를 수행함. 운영 성능 향상으로 확대 해석하지 않음.
5. 개선할 근거가 없으면 측정 결과와 현재 한계로 마무리함. 수치 향상을 위해 데이터·표본·실패를 제외하지 않음.

## 4. 검토 결과와 구현 검증 기준

현재 제품 코드와 라우팅을 읽어 설계의 기준을 확인함. 독립 전문 검토(gpt-6.1-sol / high)는 APPROVE이며 치명·중대 설계 결함이 없음을 확인함. 비차단 권고인 측정 분모·셀별 자원 귀속·정리 제한시간을 본문에 반영함. 성능 수치·실습 성공은 아직 확인하지 않음.

| 검증 | 성공 기준 | 비고 |
|---|---|---|
| 통계 단위 검사 | 빈 표본 거부, nearest-rank 경계, 처리량·분모, 단위 변환 검증 | 장시간 성능 기준을 테스트에 고정하지 않음 |
| 안전 경계 검사 | 오염된 URL·demo·proxy 환경을 차단하고 소유 포트만 사용함 | 외부 요청 없이 검증함 |
| 실제 로컬 smoke | 실제 제품 함수와 세 HTTP 서버를 통과하고 고정 결과를 확인함 | 가짜 함수 결과만으로 대체하지 않음 |
| 실패·정리 검사 | 503·timeout·중도 종료·준비 실패·결과 파일 충돌·자식 종료 후 자원 회수 확인 | 소유하지 않은 프로세스 보존 |
| 관련 회귀 | 통합 검색 기존 테스트 통과 | 제품 코드 변경이 없어도 실제 모듈 로드 영향 확인 |
| 저장소 검사 | 변경 경로 하네스, 선택된 테스트·정적 검사·필수 CI | 공용 도구·소유 불명 테스트 분류 시 전체 9개 묶음 수행 |
| 독립 검토 | diff·측정 분모·격리·종료 경로·증거 표현을 독립 확인함 | 구현 파일 동시 수정 금지 |

구현 예상 경로는 `scripts/search-performance-lab.py`, `tests/test_search_performance_lab.py`와 실습 사용 문서임. 경로 분류 결과에 따라 파일 배치를 확정하며 CI workflow를 변경하거나 필수 검사를 줄이지 않음. baseline 수집은 로컬에서 수행하며 장시간 행렬을 일반 CI에 추가하지 않음.

## 5. 확인 필요 사항

| 항목 | 처리 방침 | 비고 |
|---|---|---|
| 사용자 설계 검토 | 본 문서 검토 뒤 구현 계획을 구체화함 | 이번 작업은 설계 단계 |
| 실제 병목 | baseline 실측 후 판단함 | 클라이언트 생성·서버 포화 모두 미확정 |
| 실행 가능 환경 | 구현 착수 시 기존 Portal Python 환경과 로컬 socket 사용 가능 여부 확인 | 막히면 성공으로 표현하지 않음 |
| 자원 지표 한계 | 프로세스별 누적 CPU·high-water RSS만 1차 측정함 | 순간 피크 분석은 필요성 확인 후 확대 |
| 운영 적용 | 현재 계획에 포함하지 않음 | N100 동기화·이미지 반입·훈련·배포 미승인 |

## 6. 후속 조치

설계 자체 검수와 독립 읽기 전용 검토를 수행하고 사용자에게 설계 문서를 제시함. 검토 후 구현 계획을 작성하며 1단계 baseline부터 수행함. 후속 장애·배포 단계의 세부 설계는 1단계에서 확인한 지표·실패 조건을 재사용함.

역할은 주 담당의 설계·통합과 독립 검토 담당의 측정 정확성·격리 경계 검토로 분리함. 현재 문서는 구현·운영 완료 기록이 아니며, 실제 검토·검증 결과는 완료 시 별도로 기록함.
