## 2. 핵심 요약

앞선 자동 실습을 근거와 한계가 연결된 학습 자료로 정리하고, 실제 Git 코드가 다른 Book 앱 두 버전을 이미지로 빌드해 교체·데이터 읽기/쓰기·롤백을 실측함. 사용자가 직접 수행한 진단·사람의 MTTR은 확인되지 않았으므로 만들어 쓰지 않음. 실습지는 본인 작성란과 참고 해설을 분리하고, 사례는 에이전트 실행·자동 검증을 명시함.

| 대안 | 판단 | 비고 |
|---|---|---|
| 기존 자동 원본을 개인 경험처럼 재작성 | 제외함 | 직접 수행·사람의 진단 시간 증거 없음 |
| 근거 문서+새 실측+격리 Docker 교체 | 채택함 | 네 요청을 한 학습 결과로 연결함 |
| 실제 N100 서비스 버전 교체 | 제외함 | 운영 승인 범위 밖 |

## 3. 상세 내용

### 3.1 역할과 파일 경계

주 담당은 `container_release_lab.py`·`container_probe.py`·통합 회귀·원본·통합 문서를 담당함. Docker 구현 Sol medium은 `container_runtime.py`와 전용 테스트만, 문서 담당 Sol medium은 DB 실습지·사례·면접 자료·기존 portfolio만 수정함. 전문 검토 Sol high는 Docker 소유 자원·전이·버전/데이터 근거·원본·개인 경험 표현을 읽기 전용으로 검토함. 같은 파일은 동시에 수정하지 않음.

### 3.2 DB 분석과 문서

기존 `incident_recovery_lab.py --scenario sqlite_busy --repeats 1`을 깨끗한 고정 소스에서 새로 실행함. 원본의 code5·잠금/해제·snapshot 보존·동일 요청 적용1회·정리를 사례에 연결함. 예측·가설·검사 순서·본인 관찰은 빈 실습지에 남기고 해설은 별도 구분함. 면접 답변은 구현·자동 검증 범위로 작성하며 운영 장애 수동 복구·개인 MTTD/MTTR·대규모 운영 성과를 확정하지 않음.

### 3.3 실제 앱 버전과 빌드

v1 앱은 `d0a60639ccef6d8acdf821528baf88a1bb6af578`, v2 앱은 실행 시 현재 HEAD를 사용함. 고정 저장소의 조상 커밋만 허용하고 임의 ref는 CLI로 받지 않음. v1에는 휴지통 영구 삭제 API가 없고 v2에는 존재함. 실제 app/main.py·book_service.py 파일 해시와 HTTP OpenAPI route 유무로 코드 차이를 확인함.

두 이미지 모두 현재 HEAD의 Dockerfile·requirements를 사용하여 앱 코드 차이를 검증함. 과거 전체 의존성 환경을 재현했다고 표현하지 않음. Git 실행 환경은 고정하고 기존 bounded archive/경로·link·크기 검증을 재사용함. 임시 root의 `.container-lab-owner` 아래 신규 v1/v2 context만 만들며 manifest에 app/build commit·전체 파일 해시·payload digest를 기록함. 빌드 전 manifest·inventory를 재검증함.

각 이미지에는 실행별 owner·kind·앱/빌드 SHA·주요 소스 해시 라벨을 설정함. 이미지 inspect의 `sha256:` image ID로 실행하며 mutable tag를 실행 대상으로 쓰지 않음. 로컬 image ID와 registry manifest digest를 구분함. 기본 이미지·빌드 캐시는 정리 대상이 아님.

### 3.4 Docker 실행 경계

현재 Docker context/DOCKER_HOST가 로컬 Unix socket일 때만 고정 endpoint를 메모리에서 사용함. 경로·환경 전체·계정·credential·오류 원문은 증적에 기록하지 않음. `LocalDocker(owner, deadline, interrupted)`가 모든 Docker 작업을 제한된 argv·환경·출력·시간으로 실행함. shell·arbitrary command·외부 URL/DB/PID/volume/image/ref 입력을 CLI로 받지 않음.

실행은 network=none, host port 없음, rootfs read-only, user10001:10001, cap-drop ALL, no-new-privileges, pids64·memory256MiB·CPU1, /tmp tmpfs16MiB와 소유 named volume의 /app/data만 사용함. Docker socket·호스트 경로는 mount하지 않음. Dockerfile이 소유한 /app/data의 volume 초기화·실제 UID 쓰기 가능 여부를 실측함. 빌드에는 고정 공개 의존성 다운로드가 필요할 수 있으나 runtime 외부 통신은 사용하지 않음.

HTTP는 같은 컨테이너 안의127.0.0.1:8003에 fixed docker exec Python probe로 요청함. host·외부 ingress 검증으로 표현하지 않음. probe는 실제 Book 서비스 함수로 fixture를 생성·수정하고 HTTP health/readiness/OpenAPI/책 읽기를 확인함. uvicorn과 exec 프로세스는 공존하므로 OS 프로세스1개라는 표현은 쓰지 않음. 이전 버전 컨테이너의 종료·회수를 확인한 뒤 다음 버전을 시작하여 두 앱 버전 컨테이너가 동시에 실행되지 않게 함.

### 3.5 세 시나리오

| 시나리오 | 전이 | 검증 | 비고 |
|---|---|---|---|
| upgrade | v1 seed→정상 종료→v2 정상→실제 memo 수정·동일 요청 재전송 | startup 전후 snapshot 동일, v2 memo version2·revision1·request1, HTTP 새 내용 | 두 source·feature 차이 확인 |
| roundtrip | v1→v2 write→v2 종료→v1 재구동→v1 read/write | v1이 v2 저장 snapshot을 그대로 읽고 version3·revision2·request2로 수정, 동일 요청 단일 적용 | 같은 schema 범위의 역방향 읽기/쓰기 |
| readiness_failure | v1 정상→v2 잘못된 probe의 실제404→v2 종료→v1 1회 복구 | v2 user write 없음, seed snapshot 보존·정상 HTTP | deployment=false, rollback=true, drill valid=true |

고정 책·메모의 관련8테이블 논리 snapshot·schema hash·integrity·기존 책/보조 자료 hash를 대조함. v2/v1 수정은 의도한 내용·버전·이력·요청 원장 변화만 허용함. schema hash가 바뀌면 실패하며 자동 DB downgrade/restore를 하지 않음. destructive migration·모든 새 데이터 형식의 호환성을 주장하지 않음. 롤백은 시나리오당1회이며 실패하면 반복하지 않음.

### 3.6 소유 자원·상한·정리

`LocalDocker`는 info/build/volume/start/stop/probe/cleanup만 제공함. 리소스 이름은 owner 기반으로 생성하고 mutation 전에 등록함. 기존 이름은 성공한 조회로 부재를 확인한 경우에만 생성하며, 응답 소실은 inspect로 실제 상태를 확인하고 blind retry하지 않음. 모든 변경·정리는 known name/ID와 owner label을 함께 검증함. 불일치하면 해당 자원을 건드리지 않고 실패함.

CLI는 명시적 `--run --output`, 기본 각1회·최대각3회, 전체 기본900초·최대1800초임. 빌드 단일300초·일반 Docker15초·stop 유예5초, cleanup 별도90초를 적용함. CLI는 전용 프로세스 그룹으로 실행하며 정상 종료·deadline/interrupt 모두 해당 그룹의 자손을 회수하고 이미 생성됐을 수 있는 이름을 조회해 정리함. 기존 결과·symlink는 덮어쓰지 않으며 부분 JSON·미완료 횟수를 남김.

정리는 소유 컨테이너 stop/상태 확인/rm→소유 volume rm→소유 image rm 순서로 수행하고 부재를 확인함. broad prune·다른 자원의 stop·force 삭제는 하지 않음. 컨테이너가 남으면 volume을 삭제하지 않음. 소유 자원 잔여·불명확 상태·정리 실패는 실습 성공으로 기록하지 않음. 이미지 삭제는 --no-prune을 사용하며 외부 tag/digest 참조가 있으면 ID 삭제를 보류함. 기본 이미지·빌드 캐시(이번 다운로드·생성분 포함)는 보존함. 빌드 응답이 불명확하면 tag 부재만으로 성공 처리하지 않고 unknown_builds 잔여로 기록함. uvicorn의 정상 SIGTERM 처리 후 종료 코드0 또는143만 허용하며 실행 중·OOM·137·오류 상태는 거부함.

## 4. 검증 기준

source 혼동·context 변조·비소유 리소스·원격 endpoint·이전 컨테이너 실행 중 다음 start·응답소실·rollback 실패/반복 금지·deadline·signal·output 보존·정리 실패 회귀를 작성함. 단위 회귀는 Docker 경계를 격리해 CI에서 수행하고 실제 Docker 빌드·컨테이너 실측은 별도 원본으로 기록함. 새 테스트2개 모듈을 Book 목록·기대값에 등록하고 전체9개·문서·구문·diff·하네스·전문 검토·PR/main CI를 수행함.

## 5. 확인 필요 사항

사용자의 실제 수동 분석·사람의 복구 시간, 운영 배포·외부 ingress·다중 노드·무중단·breaking schema migration·registry 서명/manifest digest·과거 전체 runtime 재현은 미검증임. Docker actual run 성공과 mocked unit test 성공을 구분함.

## 6. 후속 조치

네 산출물과 원본을 같은 PR에 연결하고 검증 후 병합·main 검사·불필요한 브랜치 정리를 수행함. 운영 배포는 하지 않음. 기존 명시적 네 작업 연속 진행 승인에 따라 같은 범위 설계 승인 질문을 반복하지 않음.
