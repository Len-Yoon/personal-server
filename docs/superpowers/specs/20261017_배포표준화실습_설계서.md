## 2. 핵심 요약

Git HEAD의 Book 앱을 임시 릴리스 디렉터리에 추출하고 해시·설정·출처를 고정함. 실제 FastAPI/uvicorn 프로세스를 순차 교체하며 정상 재배포, 잘못된 readiness 설정의 실패와 1회 롤백, 변조 파일의 사전 차단을 검증함. 기존 N100 배포 스크립트·정책은 수정하지 않음.

| 대안 | 판단 | 비고 |
|---|---|---|
| 문서 템플릿만 추가 | 제외함 | 실제 전이·데이터 보존 증거 부족 |
| 실제 제품 앱의 격리 로컬 프로세스 릴리스 | 채택함 | 기존 의존성 환경 재사용, CI 재현 가능 |
| 기존 Docker/K3s 운영 파이프라인 변경 | 제외함 | 운영 배포·정책 승인 범위 밖 |

같은 Git 커밋의 동일 앱 payload를 다른 릴리스 식별자·probe 설정으로 다시 배포함. 새로운 앱 기능 업그레이드·컨테이너 이미지 빌드·무중단 배포·K3s rollout의 실측으로 주장하지 않음.

## 3. 상세 내용

### 3.1 역할과 파일

주 담당은 `deployment_standard_lab.py` 감독기·`release_actor.py` 실제 앱 실행·통합 테스트·문서를 담당함. 구현 담당 Sol medium은 `release_artifact.py`와 `tests/test_release_artifact.py`만 수정함. 전문 독립 검토 Sol high는 소스·경로·프로세스·단일 writer·데이터·롤백 결과를 읽기 전용으로 검토함. 같은 파일을 동시에 수정하지 않음.

### 3.2 릴리스 계약

`build_release(destination, commit, release_id, readiness_path)`는 소유 표시 `.release-lab-owner`가 있는 부모의 신규 디렉터리만 생성함. 고정 저장소의 full40 SHA에서 `book-memo/app/**`, Dockerfile, requirements.txt만 추출함. tar는 쓰기 전 전체 검증하며 links·device·경로 탈출·중복·크기 초과를 거부함. archive 최대8MiB, payload 최대4MiB, 파일 최대256개임.

manifest는 schema_version=1, service=book-memo, source_commit, release_id(baseline/candidate/unready), readiness_path(/ready 또는 /__lab_missing_readiness), files 경로별 SHA256, payload_digest(정규 JSON files), release_digest(자기 digest 제외 manifest의 정규 JSON)임. `verify_release(path, expected)`는 독립적으로 보관한 expected와 manifest·전체 파일 해시·목록을 비교하며 누락·추가·변조·symlink·hardlink를 차단함. build/extract 대상은 작업 트리 파일이 아닌 Git blob임.

### 3.3 프로세스와 데이터

부모는 새 임시 root·마커·DB 경로와 소유 loopback socket을 생성함. actor는 제한된 환경과 import 경로를 구성한 뒤 릴리스의 실제 Book 앱을 import하고 uvicorn으로 구동함. startup lifespan과 실제 /health·/ready HTTP를 검증함. 제품 소스·실습 외 DB에 접근하지 않음. 임의 URL·DB·PID·Git ref·명령을 CLI로 받지 않음. 자격 증명은 만들거나 복사하지 않음.

seed와 snapshot은 actor 내 실제 book_service 함수를 사용함. 고정 책·메모를 생성하고 관련 전체 테이블의 논리 snapshot hash와 integrity_check, 메모 내용·버전을 대조함. 이전 actor를 정상 종료·회수한 후에만 후보를 시작하여 DB writer를 겹치지 않게 함. 후보 startup이 DB를 바꿨다면 보존 검사 실패로 기록하며 자동 DB downgrade/restore는 하지 않음.

### 3.4 시나리오

| 시나리오 | 실행 | 성공 기준 | 비고 |
|---|---|---|---|
| redeploy | baseline 정상·seed → 이전 actor 종료 → 후보 동일 소스 새 릴리스 정상 구동 | /health·/ready 200, fixture 보존, active=candidate | deployment_succeeded=true |
| readiness_failure | 정상 baseline 종료 → 잘못된 readiness 경로 후보 구동 → 실제 HTTP404 확인 → 후보 종료 → baseline 1회 재구동 | 실제 앱 health200·설정 probe404, baseline readiness200·보존·정리 | deployment_succeeded=false, rollback_succeeded=true, drill valid=true |
| artifact_tamper | baseline 정상 → 후보 app 파일 변조 → preflight 거부 | baseline actor를 교체하지 않고 계속 정상·보존 | deployment_succeeded=false, rollback 미실행, drill valid=true |

baseline 확인 전 주입하지 않음. 재배포·롤백에는 각각 실제 artifact preflight를 수행함. rollback은 최대1회이며 실패하면 추가 시작·복구를 하지 않고 실습 실패를 기록함. baseline이 종료되지 않으면 후보를 시작하지 않음. 마지막 정상 릴리스는 readiness·보존 검증 뒤에만 갱신함.

### 3.5 상한·증거·정리

기본 각1회·최대각3회, 전체 deadline 기본/최대180초, IPC 응답12초, 단계당 HTTP probe 최대5초임. 요청은 loopback 고정 포트에서 redirect/proxy 없이 수행하고 응답 크기·시간을 제한함. 자식 종료 유예5초+terminate/kill/reap5초를 허용함. 강제 종료된 actor는 배포 성공으로 처리하지 않음. 살아 있는 자식이 있으면 fixture를 지우지 않음. SIGINT/TERM·무응답·start 실패·비정상 종료·정리 실패는 valid=false와 부분 JSON으로 남김. 기존 결과 파일·symlink 출력은 덮어쓰지 않음.

이벤트마다 UTC aware ISO8601과 부모 monotonic 경과 시간을 기록함. 고정 단계는 preflight, baseline, candidate preflight, 이전 종료, 후보 시작/검증, rollback 시작/검증, 데이터 검증, cleanup이며 실제 수행한 것만 기록함. `valid`는 알려진 실습 계약 충족 여부이고 실제 후보 배포 결과 `deployment_succeeded`와 분리함. 소스 SHA·dirty·runtime Python/SQLite/uvicorn/FastAPI·requirements hash·payload/release digests를 보관함. 개인 경로·환경 전체·에러 원문·본문은 기록하지 않음.

## 4. 검토·검증 기준

실제 HTTP 앱 교체·readiness 실패·롤백·불변 릴리스·DB 보존을 검사함. 환경 오염, 비소유 경로·tar 탈출·변조·출력 보존, 중복 writer 방지, rollback 실패 재시도 금지, child crash·무응답·시그널·정리 실패 회귀를 포함함. 새 테스트를 Book 목록·기대값에 배정하고 전체9개 검사·문서·구문·diff·하네스·전문 독립 검토·필수 PR/main CI를 실행함.

## 5. 확인 필요 사항

컨테이너/이미지 digest·운영 GitOps/CD·실제 운영 DB 마이그레이션·새 코드 버전 간 호환성·무중단·성능·외부 health는 미검증임. 기존 의존성 환경을 재사용하며 독립 이미지로 패키지 재현성을 증명하지 않음.

## 6. 후속 조치

Runbook·실측 원본·검증 결과를 같은 PR에 보관하고 운영 변경 없이 병합·main 검증·브랜치 정리를 수행함. 기존 승인에 따라 설계·계획의 같은 범위 승인 질문을 반복하지 않음.
