## 2. 핵심 요약

실습 CLI 하나가 세 시나리오를 각각 baseline → 주입 확인 → 실제 실패 관측 → 원인 증거 확인 → 제한된 해제 → 재시도·보존 확인 → 정리 순서로 실행함. 기본 반복은 시나리오당 1회, 최대 3회임. 결과에는 시간선·검증 항목·중단·잔여 자원 여부를 기록함.

새 진단 하위 시스템이므로 설계를 문서화함. 사용자의 기존 3단계 계획과 “다음 단계 진행해”, 중간 승인 없는 일반 개발 기준에 따라 같은 범위의 설계·계획·구현·검토·PR/CI·병합을 연속 수행함. 새로운 운영 변경은 이 승인에 포함하지 않음.

## 3. 상세 내용

### 3.1 대안과 선택

| 대안 | 판단 | 비고 |
|---|---|---|
| 실제 제품 함수 + 소유 로컬 fixture | 채택함. 변경하지 않은 검색 함수와 Book 저장 함수를 호출함 | 실제 SQLite 오류·로컬 HTTP로 재현 |
| 전체 앱 HTTP·인증·컨테이너 구성 | 후속 필요 시 검토함 | 이번에는 앱 HTTP 상태·화면·쿠키를 검증하지 않음 |
| 호스트 디스크 채우기·운영 중지 | 제외함 | 별도 mount·sudo·실제 데이터 접근 없음 |

### 3.2 구성과 소유 경계

주 담당은 `book-memo/tools/incident_recovery_lab.py`의 부모 감독기, `incident_search.py`의 검색 actor와 통합 테스트·문서를 담당함. DB 구현 담당은 `incident_sqlite.py`와 해당 actor 테스트만 수정함. 독립 Sol high 검토 담당은 파일을 수정하지 않고 전체 diff·금지 영역·프로세스 정리·분모·상태 전이를 검토함.

부모가 신규 TemporaryDirectory와 loopback socket을 확보하고 spawn 자식에게 명시적으로 전달함. DB 파일과 상태는 이 디렉터리 아래 고정된 신규 파일만 사용함. CLI에는 외부 URL·DB 경로·임의 SQL·임의 PID 입력이 없음. 부모 환경을 자식에 복사하지 않고 필요한 PATH·demo=0·proxy 제외·소유 DB 경로만 설정함. 제품 모듈은 환경 격리 후 import함. 제품 코드·운영 auth·Secret·PVC·Caddy·scheduler·배포 도구는 변경하지 않음.

### 3.3 시나리오

| 시나리오 | 주입·탐지 | 해제·검증 | 비고 |
|---|---|---|---|
| dependency_timeout | 동일 소유 서버의 books만 정상→2초 지연 전환 후 실제 `search_all`로 unavailable 확인 | 동일 서버를 정상으로 되돌리고 세 결과·고정 데이터 확인 | news·youtube 보존. 설정 ack 뒤 관측 시작 |
| sqlite_busy | 별도 소유 locker 프로세스가 실제 Book fixture DB에서 BEGIN IMMEDIATE, 제품 update_memo에서 SQLITE_BUSY 관측 | 소유 locker rollback·종료 뒤 같은 요청 ID 재시도·재전송, version+1·기존 데이터·중복 없음 확인 | 제품 기본 SQLite timeout 유지 |
| sqlite_full | 실습 프로세스 내부에서 실제 제품 연결을 감싸 매 연결에 max_page_count를 읽어 확인하고 적용. 현재 page_count를 한도로 고정한 뒤 64KiB 고정 메모 쓰기로 SQLITE_FULL 관측 | 제한을 현재 페이지+64로 높이고 같은 요청 재시도·재전송, 실패 원자성·새 내용·중복 없음·integrity_check 확인 | OS ENOSPC·호스트 디스크 포화 실습 아님 |

DB 초기 자료는 고정 책·메모 1건임. 제품 `book_service`를 실제 호출하되 DB_PATH는 신규 fixture로만 지정함. 용량 제한 연결 wrapper는 실습 자식에만 적용하고 예외를 만들어 던지지 않음. baseline snapshot과 실패 직후 논리적 내용·버전·관련 테이블을 대조하며 파일 전체 해시만으로 보존을 판정하지 않음. 복구 뒤 요청 재전송이 메모·수정 이력·write_requests를 중복 생성하지 않아야 함.

SQLITE_FULL과 SQLITE_BUSY는 구조화된 SQLite 기본 오류 코드를 확인함. 문자열이 비슷하거나 다른 I/O 오류가 발생한 것을 목표 오류 성공으로 처리하지 않음. 오류 원문·메모 내용·환경 전체·개인 경로는 증적에 넣지 않음.

### 3.4 실행 제한과 정리

전체 실행 상한은 기본·최대 180초, 한 IPC 명령의 응답 상한은 12초임. 기본 총 3회, 최대 9회 실행함. 호스트 저장소는 채우지 않으며 각 DB fixture는 최대 4MiB의 파일 합계를 확인함. 고정 메모 요청은 64KiB, SQLite page_size는 실제 값을 검증하고 page_count 상한은 1MiB 이내일 때만 주입함. 예상 범위를 벗어나면 주입 전에 중단함.

부모는 자신이 직접 시작한 actor·locker만 종료·회수함. 전체 deadline·SIGINT/SIGTERM·자식 비정상 종료에서도 정리를 수행함. 종료 유예 5초와 terminate/kill·회수 추가 5초를 합쳐 최대 10초를 허용함. 자식 정상·비정상 종료와 실제 회수를 구분하며 정리 실패는 성공으로 기록하지 않음. 자식이 남으면 사용 중 디렉터리를 삭제하지 않고 잔여 상태를 보고함. 사용자·운영 파일을 검색하거나 지우지 않음.

기존 결과 파일·symlink는 덮어쓰지 않고 신규 JSON만 생성함. 결과 저장 불가·상한 초과는 fixture·socket 생성 전에 차단함. 부분 결과를 보존하며 미실행 시나리오를 완료로 세지 않음. 소유 자식 회수 후에만 TemporaryDirectory를 삭제하고 부재를 확인함.

### 3.5 증거와 시간 해석

이벤트는 `baseline_verified`, `fault_applied`, `failure_observed`, `cause_evidence_verified`, `recovery_action_started`, `recovery_action_completed`, `recovery_verified`, `cleanup_verified`로 고정함. 각 전이는 실제 ack·관측·검증이 끝난 뒤 부모의 monotonic 경과 시간과 UTC ISO 8601 시각을 기록함. 건너뛴 단계를 성공으로 채우지 않음.

| 지표 | 정의 | 비고 |
|---|---|---|
| 탐지 소요 | fault 적용 ack→실제 실패 응답 관측 | probe·IPC 포함 |
| 자동 원인 확인 소요 | 실패 관측→오류 코드·상태·보존 증거 확인 | 알려진 주입의 기계적 검증, 사람의 RCA 시간 아님 |
| 조치 후 복구 확인 소요 | recovery_action_started→정상 쓰기·읽기·재전송 또는 검색 결과 확인 | 정리 시간 제외 |
| 손실·중복 | fixture의 기존 데이터 보존·요청 적용 1회·정확한 버전 검증 | 서비스 전체 RPO=0으로 해석하지 않음 |

RTO/RPO·운영 MTTD/MTTR·알림 전달·Prometheus 경보 발화·실사용자 영향은 측정하지 않음. 결과는 자동 훈련의 관측 시간이며 평균·백분위로 서비스 신뢰성 목표를 만들지 않음. 소스 Git SHA·dirty·실행기/제품 모듈 해시·Python/httpx/SQLite 버전을 기록함.

## 4. 검토·검증 기준

실제 로컬 HTTP 전환과 SQLite 오류를 검사함. 무관한 프로세스·DB·결과 파일 보존, 오염된 환경, wrong error code, 응답 없음·시작 실패·SIGTERM·부분 증적·중복 요청·논리 snapshot·정리 실패를 회귀로 확인함. 새 테스트를 Book CI 목록과 명시적 기대값에 함께 배정하고 전체 9개 묶음·문서 검사·정적 검사·하네스·독립 검토·필수 PR/main CI를 수행함. 최초 실패는 보존하고 해당 원인의 수정 재실행은 3회 이내로 제한함.

## 5. 확인 필요 사항

실제 오류·복구·시간은 구현 뒤 실측으로 확인함. SQLite 제한의 연결별 적용과 rollback 뒤 상태를 실제 버전에서 검사함. OS filesystem ENOSPC와 앱 HTTP 오류 페이지는 이번 증거에 포함하지 않음. 사람의 수동 진단은 Runbook의 별도 연습이며 자동 실행 성공으로 대신하지 않음.

## 6. 후속 조치

이 설계에 대응한 구현 계획·실습 도구·회귀·Runbook·실측 원본을 같은 브랜치와 PR에 묶음. 운영 배포 없이 저장소 반영까지 검증함. 배포 표준화는 3단계 후속 범위로 남김.

기술 근거: [SQLite max_page_count](https://www.sqlite.org/pragma.html#pragma_max_page_count), [SQLite result codes](https://www.sqlite.org/rescode.html). 원본 문서를 확인했으며 오류 코드가 같다는 이유로 OS 디스크 포화를 실측했다고 표현하지 않음.
