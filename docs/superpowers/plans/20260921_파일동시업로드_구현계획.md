# 파일 동시 업로드 안전성 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. 단계별 체크박스로 기록함.

**Goal:** F05 동일명 동시 업로드가 기존 파일을 덮어쓰거나 실패 요청이 승자 파일을 삭제하지 않도록 함.

**Architecture:** 저장 파일을 exclusive create(`xb`)로 원자 생성함. 생성 실패는 쓰기 실패 cleanup과 분리하고, 실제 생성한 요청만 자기 파일을 정리함. 기존 용량·감사·일괄 rollback·HTTP 응답 계약은 유지함.

**Tech Stack:** Python pathlib/unittest, FastAPI TestClient, 추가 의존성 없음.

**Spec:** [상위 계획](../../20260921_프로젝트보완_개발계획.md) F05 및 사용자의 단계별 검증·커밋·PR·CI 확인·병합·연속 진행 승인.

## Global Constraints

- 변경 코드 `portal-web/app/services/file_store.py`, 테스트 `tests/test_portal_security.py`, `tests/test_file_access.py`, 관련 계획 문서만 수정함.
- 주 담당은 계획·하네스·PR·CI, 구현 담당은 코드·회귀, 독립 검토 담당은 파일 소유권·cleanup 경계 검토. 같은 파일 동시 수정 금지.
- 실제 파일함·운영 데이터·N100·bootstrap·scheduler·CI 설정은 변경하지 않음. 임시 디렉터리만 검증함.
- 사용자에게 원래 한국어 충돌 메시지를 유지하고 OS 예외의 절대 파일 경로를 노출하지 않음. 기존 HTTP 충돌 409, 크기 오류 400을 보존함.
- symlink 교체·외부 파일 삭제/재생성 같은 별도 위협모델 확대는 제외함. F05는 앱 업로드 간 같은 이름의 생성 경쟁을 해결함.
- 새 코드가 만든 파일만 예외 정리하고 사전에 있거나 다른 요청이 생성한 파일은 지우지 않음.
- RED/GREEN 로그와 실제 검사 결과를 남기고 관련 실패가 남으면 커밋·병합하지 않음. 운영 배포는 제외함.

## Review Focus

1. 두 요청이 사전 존재 검사를 동시에 통과한 경우 성공이 정확히 하나인가.
2. `xb` 자체가 실패한 요청의 cleanup이 승자 파일을 삭제하지 않는가.
3. 크기 초과·read 예외·audit 예외에서 자기 파일은 정리되고 다른 파일은 보존되는가.
4. 일괄 업로드 후속 충돌·합계 초과 시 기존 파일을 보존하는가.
5. 새 원자 생성 실패가 절대 서버 경로를 HTTP 오류에 노출하지 않는가.

### Task 1: 원자 파일 생성과 cleanup 회귀

**Files:** Modify `portal-web/app/services/file_store.py`; Test `tests/test_portal_security.py`, `tests/test_file_access.py`.

**Interfaces:** `save_upload(relative_path, upload) -> int`, `save_uploads(relative_path, uploads) -> int`와 기존 router 응답을 유지함.

- [x] Step 1: 실패 테스트를 먼저 추가함. `Path.open`을 대상 경로와 쓰기 모드에만 한정하여 barrier를 두고 두 요청 모두 생성 직전 도착하도록 함. 실제 파일 open/write는 원본을 호출함. 서로 다른 payload·BytesIO 사용, worker 결과·오류 수집 및 join timeout 확인. 기대: 성공 1, FileExistsError 1, 최종 내용=성공한 payload. 수정 전 실패 로그를 보존함.

```python
self.assertEqual(len(successes), 1)
self.assertEqual(len(conflicts), 1)
self.assertEqual(destination.read_bytes(), payloads[successes[0]])
```

- [x] Step 2: 원자 생성과 소유권 경계만 최소 수정함. open 성공 전에는 cleanup 블록에 진입하지 않는 방식 또는 정확한 created 플래그를 사용함. `FileExistsError`는 기존 한국어 메시지로 변환함.

```python
try:
    output = destination.open('xb')
except FileExistsError:
    raise FileExistsError('이미 같은 이름의 파일이 있습니다.') from None
try:
    with output:
        while True:
            chunk = upload.file.read(CHUNK_SIZE)
            if not chunk:
                break
            size += len(chunk)
            if size > MAX_UPLOAD_BYTES:
                raise ValueError(f"파일은 {MAX_UPLOAD_BYTES // CHUNK_SIZE}MB 이하만 업로드할 수 있습니다.")
            output.write(chunk)
except Exception:
    destination.unlink(missing_ok=True)
    raise
```

size 초기값과 chunk 루프의 기존 검증 계약을 유지함. audit 실패의 기존 cleanup을 유지함.

- [x] Step 3: 기존 동일명 거절 테스트에 내용 보존을 추가하고, 크기·read·audit 예외에서 자기 파일만 삭제됨을 검증함. 일괄 합계 초과 400과 후속 파일 충돌 409에서 이전에 저장한 요청 파일만 rollback되고 원래 파일 내용은 유지되는지 확인함. 경쟁으로 발생한 409 메시지에 절대 경로가 없음을 확인함.
