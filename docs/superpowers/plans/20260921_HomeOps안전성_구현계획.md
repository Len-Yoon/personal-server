# HomeOps 실행 안전성 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. 체크박스로 실행 결과를 기록함.

**Goal:** F02~F04를 함께 해결하여 인증된 내부 scan만 실행하고, 승인 1건으로 재시작이 중복 실행되지 않으며, 정상 관측이 장애 연속성을 끊도록 함.

**Architecture:** 기존 Portal 앱과 SQLite 안에서 해결함. 내부 scan의 기존 secret 검증을 재사용하고 Origin 없는 정확한 POST에만 예외를 둠. 승인 선점은 DB 트랜잭션에서 수행하고 외부 작업은 commit 이후에만 실행함. 서비스별 관측 상태는 정상 이력 생략 여부와 독립적으로 저장함.

**Tech Stack:** 기존 Python/FastAPI/unittest/SQLite, 의존성 추가 없음.

**Spec:** [상위 계획](../../20260921_프로젝트보완_개발계획.md) 8절, [종합 점검](../../reviews/20260921_프로젝트_종합점검보고서.md)의 F02~F04. 사용자가 이번 턴에서 로컬 코드·테스트 준비를 명시 승인함.

## Global Constraints

- 주 담당: 계획·문서·검증 통합, 구현 담당: 코드·테스트, 독립 담당: 보안·동시성·DB 호환 검토. 동일 파일 동시 수정 없음.
- 변경 후보는 `portal-web/app/main.py`, `portal-web/app/routers/admin.py`, `portal-web/app/services/homeops.py`, `tests/test_homeops.py`임.
- 기존 1차 F01 변경을 보존함. bootstrap·scheduler·Docker 실행 구현·K3s·Secret·PVC·운영 DB·N100은 수정하거나 호출하지 않음.
- 새 비밀값·자격 증명 생성 없음. 테스트는 고정 fixture만 사용하고 실제 HTTP·Telegram·Docker 호출 없음.
- 기존 일반 unsafe 요청 Origin 정책, 허용 서비스, 재시작 동작과 제한을 보존함.
- SQLite 추가 테이블은 CREATE TABLE IF NOT EXISTS로 생성하며 기존 행을 삭제·수정하는 마이그레이션을 하지 않음. 운영 DB에는 실행하지 않음.
- 시간은 UTC aware ISO 8601. 화면·알림 형식은 변경하지 않음.
- 커밋·push·PR·병합·배포 없음. 재검증은 같은 수정에 최대 3회, 관련 테스트를 먼저 실행함.

## Review Focus

1. 유효 secret이 있어도 cross-origin·다른 path·다른 method가 Origin 검사를 우회하지 않는가.
2. 서로 다른 HomeOpsService 인스턴스의 같은 승인 동시 실행과 재생성 후 재요청이 실제 restart 1회에 그치는가.
3. 실행기 응답 유실·health 조회 실패·프로세스 재시작 후 consumed 승인을 재사용하지 않는가.
4. 정상 관측 후 프로세스가 바뀌어도 카운터 초기화가 유지되고 서비스별 상태가 섞이지 않는가.
5. 정기 scan 활성화 후 동시 요청이 자동 재시작 상한·cooldown을 뚫거나 오래된 장애 이력을 즉시 실행하지 않는가.

## 입력·저장·오류 경계

| 입력 | 기대 결과 | 저장·외부 경계 | 비고 |
|---|---|---|---|
| Origin 없음 + 유효 scheduler secret + 정확한 POST path | 200·scan 실행 | 기존 handler 인증 유지 | 기존 scheduler 변경 없음 |
| secret 없음·오류·미설정 | 403·scan 미실행 | 비밀값 응답·로그 출력 없음 | same-origin도 handler 인증 필수 |
| cross-origin 또는 null·빈 Origin | 403 | 일반 CSRF 정책 유지 | header 존재와 부재 구분 |
| 같은 승인 동시 요청 | 하나만 선점·실행 | DB commit 후 executor 호출 | 프로세스 전역 lock에 의존하지 않음 |
| executor 응답 유실 | consumed 상태 유지·동일 승인 재실행 차단 | 불확실한 결과를 성공으로 표시하지 않음 | 자동 retry 금지 |
| 장애·정상 교대 | 재시작 없음 | 정상도 관측상태 저장 | 정상 incident 이력은 생략 가능 |
| 진짜 3연속 장애 | 기존 정책 범위 내 1회 실행 | 예약·승인은 원자 처리 | cooldown·시간당 상한 유지 |
| 기존 DB | 기존 사건·승인 보존 | 추가 테이블만 초기화 | 불완전한 옛 이력을 연속장애로 승계하지 않음 |

### Task 1: HomeOps 인증·원자 승인·관측 상태 회귀

**Files:** Modify `portal-web/app/main.py`, `portal-web/app/routers/admin.py`, `portal-web/app/services/homeops.py`; Test `tests/test_homeops.py`.

**Interfaces:** 기존 `create_diagnosis(service, record_healthy=True)`, `approve_incident(incident_id, approved_by)`, `execute_approved_incident(incident_id)` 및 응답 구조를 유지함. scheduler 인증 판정은 main과 admin이 같은 함수를 재사용함.

- [x] Step 1: 실제 TestClient POST와 임시 SQLite/FakeExecutor를 이용한 실패 회귀를 추가하고 수정 전 실패를 기록함. 테스트는 public/로컬 origin 정책, 같은 승인 2개 인스턴스 경쟁, 장애·정상 교대를 포함함.

```python
response = client.post('/internal/homeops/scan', headers={'X-HomeOps-Scheduler-Secret': 'fixture-secret'})
self.assertEqual(response.status_code, 200)
self.assertEqual(len(executor.restart_calls), 1)  # 같은 승인 동시 요청을 모두 join한 뒤 확인
# unhealthy, healthy, unhealthy, healthy, unhealthy 순으로 실제 create_diagnosis 실행
self.assertEqual(executor.restart_calls, [])
```

동시성 테스트는 barrier/event로 겹침을 보장하고 timeout·worker 예외를 검사함. DB 내부 lock 취득 후 양쪽이 기다리는 barrier를 두어 교착시키지 않음. 이중 실행 관찰을 스케줄링 우연에만 의존하지 않음.

- [x] Step 2: 기존 scheduler secret 비교를 공용 판정으로 추출하고 정확한 경로·POST·Origin header 부재에만 예외 적용함. 정상 same-origin은 기존 정책을 따르되 handler에서 별도 secret 검사를 유지함.

```python
request.method == 'POST' and request.url.path == '/internal/homeops/scan' and 'origin' not in request.headers
# 위 조건과 기존 secret 검증이 모두 참일 때에만 origin 없는 scan을 통과시킴.
```

- [x] Step 3: 승인 선점과 executing 전이를 하나의 write 트랜잭션으로 수행함. 승인 유효성·만료·미소비를 검사하고 조건부 UPDATE의 rowcount가 1인 요청만 실행함. 외부 restart/notify/health 호출은 트랜잭션 밖에서 수행함.

```sql
BEGIN IMMEDIATE;
UPDATE approval_tokens SET consumed_at=? WHERE incident_id=? AND consumed_at IS NULL AND expires_at>=?;
UPDATE incidents SET status='executing' WHERE incident_id=? AND status='approved';
```

각 갱신 실패 시 전체 트랜잭션을 rollback하고 승인 불가 결과를 반환함. restart 응답 유실 또는 health 예외는 consumed 상태를 유지하여 재전송을 차단함. 승인된 incident_id 하나에 대한 보장과 executor 직접 호출의 별도 신뢰 경계를 문서로 구분함.

- [x] Step 4: 서비스별 최근 관측·연속 장애 횟수를 별도 테이블에 저장함. 정상은 0, 장애는 증가하며 record_healthy=False의 조기 반환 전에 반영함. 신규 테이블의 초기 카운터는 0으로 보수적으로 시작함. 자동승인 예약과 현재 cooldown·상한 판단은 같은 write 트랜잭션에서 실행하여 동시 scan의 중복 예약을 막음. I/O를 위해 DB lock을 오래 보유하지 않음. 카운터가 3 이상이면 후보로 판단하되 같은 서비스의 approved/executing이 있으면 예약하지 않음. 시간당 상한은 approved 예약도 포함하며, 예약 성공 시 카운터를 0으로 초기화하여 다음 자동 시도는 새 3개 장애 관측을 요구함. cooldown 중 임계치를 넘긴 상태도 기간 종료 후 다시 판단함.

```sql
CREATE TABLE IF NOT EXISTS service_observations (
  service TEXT PRIMARY KEY,
  consecutive_unhealthy INTEGER NOT NULL,
  last_status TEXT NOT NULL,
  observed_at TEXT NOT NULL
);
```

## DB 호환·되돌리기 경계

- 기존 incidents·approval_tokens를 보존하고 새 service_observations만 추가함. 과거 incident 이력으로 초기 카운터를 복원하지 않음.
- 로컬 검증은 기존 스키마 fixture에서 생성·재생성을 반복해 기존 승인 소비·행·이력을 보존하는지 확인함.
- Executor 직접 API 재전송 또는 Portal DB 유실까지 exactly-once를 보장하지 않음. 영속 중복 원장을 Executor에 추가하려면 운영 저장소 설계가 별도로 필요함.
- 실제 운영 DB 변경·rollback 명령은 수행하지 않음. 향후 코드 rollback 때 새 테이블은 삭제하지 않고 유지 가능하나, 옛 코드의 승인 경쟁·관측 결함이 재노출되므로 자동 scan 활성화 여부를 별도 운영 승인에서 검토해야 함.
